# Privileged MFA rollout and recovery

**Owner:** Barrels Grenada platform engineering

**Status:** Implementation ready for staged acceptance; no deployment activation implied

Privileged means an active superuser or an account with effective `user.manage`, including department management assignments. In `AUTH_PRIVILEGED_MFA_MODE=enforce`, staff API/cookie requests and GAA Admin/CMS admission require an encrypted enrolled authenticator and a live session that completed an authenticator or recovery-code challenge. Account security, account sign-in and logout remain reachable. Ordinary public accounts retain their existing email-verification and app-admission requirements.

`totp_enabled` records enrolment. `session.mfa_verified_at` records an actual completed challenge. Enrolment never upgrades an old password-only session. Access tokens carry their session ID; the API checks its owner, expiry, revocation, scope and MFA evidence against the live database. Session rotation and SSO preserve the original evidence. SSO redemption rechecks the source session. Disabling MFA clears evidence on every session and blocks privileged access until re-enrolment and another two-step sign-in.

## Deployment readiness gates

1. Deploy the additive migration and code with `AUTH_PRIVILEGED_MFA_MODE=disabled` (the default). Existing administrators remain able to sign in. No ephemeral encryption key or JWT-secret fallback exists.
2. Generate a dedicated Fernet key using `Fernet.generate_key()` in a secure operator environment. Store it in the deployment secret manager as `AUTH_TOTP_ENCRYPTION_KEYS`, a JSON array of strings. Provision the same keys for every API worker and retain protected backup copies separately from database backups. Do not print keys into build logs, commit them, or write local environment files in this repository. Missing keys disable new authenticator setup and are explained in account security; enforce mode refuses to start without valid keys.
3. From the FastAPI directory, with the deployment configuration supplied securely, run `uv run --no-sync --package fast-back python -m src.auth.mfa_rollout` for a dry run. Validate counts, then run the same command with `--apply` under reviewed operator change control. It validates every secret before changing any, encrypts legacy plaintext, and rewraps existing ciphertext under the first key. Never run it against a different database or while changing the key list across workers. Recovery codes are hashed, not decrypted or printed.
4. Have every privileged person enrol at the shared account `/security` page, generate recovery codes, save them securely offline, and sign in again using an authenticator. Use at least two independently operated privileged accounts for recovery acceptance; no universal password or permanent MFA-exempt account is introduced.
5. Run `python -m src.auth.mfa_rollout --check-readiness`. Require exit 0 and zero missing privileged enrolments/recovery codes, and zero unencrypted or unreadable secrets across all stored accounts. Storage readiness includes ordinary public accounts so activation cannot strand their existing authenticator sign-in. The check prints aggregate counts only. It does not establish that people saved codes or completed acceptance.
6. On staging with disposable approved accounts, enable `enforce` through reviewed configuration, then exercise password-only denial; authenticator success; one-use recovery; revoked/expired/other-owner session denial; GAA Admin handoff and rotation; CMS handoff and identity; account security access during denial; ordinary public verification/admission; and sign-out. A legacy bearer token never establishes MFA. Confirm there is no redirect loop. Verify each folded staff module uses the shared gate.
7. Record staging evidence and operator recovery ownership before requesting production activation. Production secrets, flag activation and real-user mutations are separate operational work; this code change performs none.

## Recovery acceptance and break-glass procedure

A saved recovery code replaces the authenticator at sign-in and is consumed atomically. After recovery, generate replacement codes with the account password and a current authenticator or remaining recovery code. Replacement invalidates the previous set. Recovery use, replacement, enrolment and disabling are audited without codes or secrets. Codes still work when encrypted secret decryption is unavailable, allowing the owner to disable and re-enrol after the operator restores correct storage configuration.

On a disposable staging account, prove that one saved code signs in, the same code fails on reuse, existing privileged tools become accessible, and replacement cancels old codes. Record only test identities and outcomes in the private operator evidence store. Never test destructive recovery against the currently relied-on administrator session.

If every authenticator and recovery code is lost, do not reset MFA through an ordinary administrator route or use account activation as a recovery bypass. Follow incident change control: independently confirm identity and operator authority; preserve audit evidence; repair the encryption configuration first if that is the cause. If necessary, an explicitly approved, time-limited rollback to `disabled` is an operational emergency action that temporarily removes the privileged gate globally. Record approvers, reason, start/end and affected environment privately; limit exposure and restore `enforce` only after fresh enrolment, saved codes, readiness and staging recovery acceptance. This rollback permits otherwise usable existing sessions; it does not bypass an enrolled factor at sign-in or make a lost-factor account recoverable. If no usable independently operated account remains, factor reset or restoration is a separate, explicitly approved and audited operator recovery action; it is not implemented or exercised against real accounts by this milestone. There is no built-in per-user exception or automatic fail-open fallback.

A rollback of the enforcement flag keeps this encryption-aware code and the additive schema in place. It does not decrypt stored secrets. An older image from before encrypted TOTP support expects plaintext and cannot authenticate encrypted rows, even with enforcement disabled. Do not use that image as the emergency rollback target. Before any image or database rollback, verify its encrypted-secret and session-column compatibility and its required key list against the chosen backup; use a reviewed encryption-compatible image and retain protected keys for that backup. Do not narrow the secret column, decrypt secrets into plaintext, or reset factors as a compatibility workaround.

## Encryption key rotation

The first key encrypts; subsequent keys decrypt during rotation. Deploy `[new, old]` consistently, run the dry-run and reviewed `--apply`, require zero unreadable secrets, validate authenticator/recovery sign-in, then remove the old key only after checking all rows were rewrapped and retaining the old key for old backup restoration. Losing all keys loses authenticator-secret decryption; database restoration alone cannot recover it. Fernet authenticates ciphertext, so tampered/wrong-key data fails closed.

This implementation follows [Cryptography Fernet](https://cryptography.io/en/latest/fernet/) for authenticated encryption/key rotation and [OWASP MFA recovery guidance](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html) for saved recovery and identity confirmation.
