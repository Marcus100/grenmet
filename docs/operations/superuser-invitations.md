# Superuser invitations and recovery codes (ADR-0059)

**Owner:** Barrels Grenada platform engineering  
**Last updated:** 2026-11-15

**Status:** Implemented in #1466 (ADR-0059 rule 1 and rule 5); operator steps need owner review


Moved out of `apps/api/fastapi/src/auth/AGENTS.md` to keep that file within the Codex
byte budget. The invariants stay there; this page holds the detail, the deviations and
the test map. Operator steps for the first superuser: `docs/operations/privileged-mfa.md`.

## Detail

- Recovery codes (ADR-0059 rule 3): `POST /users/me/security/recovery-codes` needs a live authenticator code or an unused recovery code, plus the password only when `account_security.has_usable_password` is true (not `password_setup_pending`; email-code accounts have none, and password sign-in refuses them). `AccountSecurityPublic.has_password` tells the Security page which fields to show. Tests: `tests/auth/test_recovery_codes_passwordless.py`.
- Superuser invitations (ADR-0059 rule 1, `superuser_invitation.py`, table `superuser_invitation`, migration `superuserinvite20261114`): create, list and revoke need `superuser_mfa.require_superuser_mfa` plus `privileged_mfa.require_mfa_session` on the bearer's session. Only the SHA-256 token hash is stored; the link is mailed through the outbox (`superuser-invitation`). Acceptance is public and needs the token and a code emailed to the invited address (`app_service._issue_code`/`_verify_code`, purpose `superuser-invite`, same limits). It creates the account if the address has none, clears any password, TOTP and sessions on an existing unverified self-registered account first (`_retire_unverified_password`, which writes its own `pw_retired` row), then grants superuser, clears `registration_pending`, sets `email_verified_at` and writes one `superuser_granted` row with the inviter, invitee and reason (reason is sensitive). The session it returns is an ordinary `auth` session with no MFA evidence. Inactive, anonymised and placeholder addresses are refused. Limits: five per inviter per hour, twenty per day. Tests: `tests/auth/test_superuser_invitation.py`.
- Superuser invitation hardening (review of #1466): acceptance locks the inviter's row and refuses unless the inviter is still an active superuser (`close_for_inviter` also revokes their open invitations when `service.update_user` deactivates or demotes them, when `service.delete_user` anonymises them, and when `baseline.service` offboards a staff credential). The mailbox code uses its own limiter key (`superuser-invite:<mailbox>`), so sign-in codes do not silence it. An unverified account is always cleared before the grant (password, authenticator, recovery codes, sessions, devices, Google, API keys; writes `pw_retired`); a verified account with an authenticator must pass `totp_code` as the emailed-code sign-in does. The `superuser_granted` row carries `retired_unverified`. Emails: every active superuser gets a `notification` on creation (`Superuser invitation sent`) and on acceptance, with no token and no reason. One open invitation per address (partial unique index); a superseded one is audited as `superseded`. Lookups are case-insensitive. The inviter reference is `ON DELETE SET NULL`. The email link carries the token in the fragment (`/superuser-invite#token=`). `purge_superuser_invitations` (daily 04:25 UTC) deletes invitations that ended over 90 days ago. Sentry's scrubber drops frame locals and request data, so the token cannot reach it (tested). Tests: `tests/auth/test_superuser_invitation.py`, `test_grant_superuser_case.py`.
- Superuser-only apps and staff approval (ADR-0059 rule 5). Deviation from the ADR wording, recorded here because the ADR file lives on `docs/adr-0059-sign-up-tiers`: (a) acceptance clears `registration_pending`, so every accepted superuser passes the GAA and GMS staff gates too (a superuser holds every permission anyway); the ADR text only lifts the gate for superuser-only apps. (b) The superuser-only exception is applied at handoff, session exchange and refresh, but NOT on API calls: `get_current_user` never passes `session_app`, and barrels-admin staff tokens carry no app claim, so a pending superuser cannot use the API with a staff token. Only the placeholder superuser (not yet approved) is affected. Fixing (b) needs staff tokens to carry the app claim; not done. Tests: `tests/auth/test_superuser_pending_staff_app.py`.
- Generic routes never grant superuser (ADR-0059 rule 1). `POST /auth/users` and `PATCH /auth/users/{id}` refuse `is_superuser: true` for every caller, superusers included, with 403 pointing to the invitation flow; `null` is 422. The field stays in the schema, so the contract is additive. Removal (`is_superuser: false` on PATCH) needs `superuser_mfa.require_superuser_mfa` and `privileged_mfa.require_mfa_session` on the bearer's session (`invitations.require_superuser_session`). `superuser_invitation.demote_superuser` then, in the same transaction as the other fields: locks the active superusers in id order, refuses with 409 when no other active superuser would remain, writes one `superuser_revoked` audit row (actor and target ids), ends every login session of the removed account (`end_sessions`: browser, CMS, app and account sessions, so their refresh secrets stop rotating), closes the account's open invitations (`close_for_inviter`), and emails the other active superusers through `_notify_superusers` (the actor and the removed account are excluded; placeholder and unverified addresses are skipped). A non-superuser manager with `user.manage` cannot change superuser status at all. Start-up creation (`database.init_db_async`), the seeds and `scripts/grant_superuser.py` use the service layer, not these routes, and are unaffected. The admin app offers no control that changes superuser status (guard test: `apps/web/gaa-admin/src/components/users/manage-user-dialog.test.tsx`, "superuser status"). Tests: `tests/auth/test_superuser_only_by_invitation.py`.
- Last active superuser guard (#1481, part 1): `superuser_invitation.guard_last_superuser` locks the active superusers in id order (`lock_active_superusers`, the same lock as `demote_superuser`) and refuses with 409 (`LastSuperuserError`) when the target is the only active superuser. It runs before any write in `service.update_user` (`is_active: false` or `is_superuser: false`), `service.delete_user` (anonymisation, so it covers `DELETE /auth/users/{id}`) and `baseline.service.offboard` (`POST /hr/setup/staff/{id}/offboard`). Accounts that are not active superusers pass untouched. Self-deletion by a superuser stays refused with 403 on both `DELETE /auth/users/me` and `DELETE /auth/users/{id}`. Tests: `tests/auth/test_last_superuser_guard.py`. HR offboarding of a superuser (#1491): `POST /hr/setup/staff/{id}/offboard` needs `hr.setup.manage` for every target, but a superuser target also needs a superuser caller whose session passed two-step sign-in (`superuser_invitation.require_superuser_session`, the same check PATCH uses). Any other caller gets 403 `Only a superuser can do this`. On that route the 409 from the guard is replaced by a generic conflict message (`baseline.service.STAFF_OFFBOARD_CONFLICT`), so an HR manager is not told the target is the only superuser; the auth routes keep the specific text. Tests: `tests/baseline/test_hr_offboard_superuser.py`. Sign-out on demotion (#1481, part 2): the `superuser_revoked` audit row also carries `sessions_ended`, the sorted ids of the sessions deleted (ids only, no secrets). Not changed by demotion: remembered devices (they only drive new-sign-in alerts, not a credential), API keys (organisation-scoped integration credentials, not the person's sign-in; revoke them through the organisation), and `cms_access` (a separate grant; a CMS sign-in still needs it). Known residual: a bearer access token already issued stays valid for its remaining lifetime (15 minutes for session-backed tokens; `sid` is checked only for MFA evidence). The demoted account loses superuser power at once, because superuser status is read from the database on every request. Tests: `tests/auth/test_demotion_signs_out.py`.
- First superuser of an empty system: `scripts/grant_superuser.py EMAIL` (preview; `--apply` makes the change) refuses while an active superuser exists, needs an active, email-verified account, and writes one audit row with no actor. Tests: `tests/auth/test_grant_superuser_script.py`.
