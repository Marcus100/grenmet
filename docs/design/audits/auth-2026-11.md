# Design audit: Barrels sign-in and account security, the `auth` app (2026-11)

**Status:** Phase 1 audit, read only. Nothing was changed in the app; every fix below is a proposal for the owner.  
**Owner:** Barrels Grenada engineering (design mastery programme, issue #1453, section 8)  
**Last updated:** 2026-11-15

## Scope and method

Surfaces audited, all in `apps/web/auth`:

- the front door: sign-in (`/`), sign-up (`/signup`), sign in with an emailed code (`/code`), forgot password, and the "Join an app" and staff two-step hand-off screens (`/continue`);
- the signed-in account pages that live in this app: Profile, Password, Security (two-step verification, recovery codes, sign-in methods), Sessions, Apps, Organisations and Access;
- the superuser invitation page (`/superuser-invite`, ADR-0059), and the not-found page.

Not covered here: the rewards, tickets and organisation rewards screens (they have their own owner notes), and the `account` app, which is audited in [account-2026-11.md](account-2026-11.md).

The rule for judging: a defect is a gap against this app's own written design rules or a rule from a design skill, never a difference from another app. One thing is different from the earlier audits: **`auth` has no lane spec** (there is no `docs/design/auth.md`). Its only written rules are the lines in [`docs/design-system.md`](../../design-system.md) that place it in the "GMS institutional" typography lane and call it a "brand cleanup lane" (align radii, shadows and semantic colours), plus the owner's rule that the Barrels platform screens (sign-in, account, admin) share one clean look. Where this audit points at a gap with no written rule behind it, it says so; finding 3 asks for a lane spec.

Method:

1. Read the instructions (`AGENTS.md` at the root and in `apps/web/auth`), the design system and design workflow notes, the account lane spec (as the nearest Barrels platform pattern) and the section "Reviewing or polishing UI: check these before reporting a gap" in `docs/agents/extended-rules.md`.
2. Checked where styles live before reporting anything. The shared layer `packages/ui/src/styles/app-feel.css` is imported by `src/app/globals.css`, so the tap flash, `touch-action: manipulation`, scroll containment in dialogs and reduced motion are already handled and are not reported. A Toaster is mounted in `src/app/providers.tsx`, so `toast()` calls work. Form fields share one set of classes in `src/components/form-styles.ts`. The page stylesheet carries a bare rule `a { color: inherit; }` outside any cascade layer; that detail matters for finding 1.
3. Read every component and page listed above and applied the rules of these skills: web-design-guidelines (pinned rules), fixing-accessibility, refactoring-ui, mobile-native, emil-design-eng and break-ui (worst-case data argued from the code, and seen for real on the Sessions page). There is almost no motion here (colour changes, a dialog fade, a pulse on the QR placeholder), so the motion review found nothing to report.
4. Looked at the running staging app (`auth.staging.barrels.gd`) with a scripted browser at 390 pixels (phone) and 1280 pixels (desktop), light and dark: sign-in, sign-up, the emailed-code page, forgot password, the not-found page, and, signed in with the staging test account, Profile, Password, Security, Sessions, Apps, Organisations and Access. Measurements were taken from the live pages (text and background colour, size of every link and button, horizontal overflow). Screenshots were viewed during the audit and are not committed. Nothing was submitted: no sign-up, no code request, no password change.
5. Compared the security flows with three saved reference flows, for ideas only: [Customer.io two-factor setup](https://mobbin.com/flows/7fece37b-b393-4aa2-b261-fc6931c2a35e), [Railway two-factor setup](https://mobbin.com/flows/b9d19e77-5cb5-482e-9cec-2920a3f9ccd2) (its Security overview with Authenticator, Recovery codes, Passkeys and Sessions rows is the pattern finding 5 uses) and [Xero authenticator setup](https://mobbin.com/flows/f6c97bc9-ef5d-49a7-a87c-65177ad11e85).

How to read a finding:

- **Rule or reference** is the written rule, skill rule or reference behaviour behind it.
- **Size:** S is under half a day, M is about a day, L is several days or needs a decision first.
- **INVISIBLE** means people would not see a difference in normal use (accessibility, focus, keyboard, hidden hit areas, behaviour on failure). These can merge on green checks. **VISIBLE** means layout, colour or wording changes, so the owner reviews before and after screenshots first.

## What is already strong

- **Forms are careful.** Every field has a visible label tied to its input, the email-code form turns off spell-check and capitals and sets the email keyboard, password fields have a show/hide button with its pressed state announced, the new-password field shows a strength meter in words, errors appear in a box with `role="alert"`, and typed values survive a refusal (the code form passes the form data back; the password stays in state for the authenticator step).
- **Hydration is guarded.** Page-level forms that submit through script wait for `useHydrated()` before the button works, so a password or email can never end up in the address bar.
- **The code field is good.** Six separate boxes with the one-time-code autofill hint, a recovery-code alternative one tap away, and the box size is 44 pixels.
- **Security wording is plain.** Each row says what it does and shows the state as a word ("Off", "Verified", "Set", "Not connected"); recovery codes are shown once with a warning, and the dialog refuses to close until "I've saved my codes" is pressed.
- **The step-up flow explains itself.** Staff who need two-step verification are told why, in words, on the Security page and on the hand-off screen.
- **Sensitive invitation page is thoughtful.** The superuser invitation token travels in the address fragment, is removed from the address bar, focus moves to the error and to each new step heading, and a new code can be requested from the code step.
- **Layout holds on a phone.** No horizontal page scroll on any of the 13 pages visited at 390 pixels (or at 1280), the two-pane desktop layout collapses to one column, and there is a main landmark and one first-level heading on every page except the not-found page.
- **Dark mode works.** Checked on sign-in, sign-up, Security and the not-found page: text contrast is 7.5 to 1 or better for secondary text and 15.7 to 1 for body text, and the main blue button keeps 5.2 to 1 in both modes (white on `#0b63ee`).
- **Errors report quietly.** Failed loads show a sentence and are reported without personal data.

## Findings

### Blocking

#### 1. A page-level rule makes two buttons unreadable

- **Where:** `src/app/globals.css` (`a { color: inherit; }`, outside any layer). Tailwind's colour classes live in a lower layer, so this plain rule beats them on every link. Two screens use a link dressed as a button:
  - the not-found page (`src/app/not-found.tsx`, "Go to sign in"): measured on staging, the label is `rgb(17, 24, 39)` on navy, contrast 1.04 to 1 in light mode and 2.13 to 1 in dark mode (the standard asks for 4.5). The button looks like an empty dark bar;
  - the last step of the superuser invitation (`src/app/superuser-invite/invite-form.tsx`, "Set up your authenticator", a link with the white-on-blue button classes). This screen is on `dev` only and returned "Page not found" on staging, so it was read from code; the same rule applies and the label will be dark on blue. The link also has `w-full` but is not a block element, so it will not stretch like the other buttons.
- **Rule or reference:** fixing-accessibility, contrast and states ("ensure sufficient contrast for text and icons"); web-design-guidelines, Hover & Interactive States.
- **Why it matters:** the not-found page is where a person lands after a broken link and its only way out cannot be read. On the invitation page it is the one thing a new administrator must press to continue.
- **Suggested fix:** delete the bare `a { color: inherit; }` rule or move it into the base layer so utility classes win, and make the invitation link a block element. Size S. VISIBLE (a label becomes readable).

### Should fix

#### 2. The front door wears the Met Office identity and lists other organisations' apps

- **Where:** every page in the app. On a phone every screen starts with the Grenada Meteorological Service logo. On a desktop the left panel shows the full Met Office logo, "Hello again" and a list of seven apps: GAA Admin, Airport website, Weather, Docs, Barrels admin ("Staff console (superusers only)"), Signal and Events. `src/app/globals.css` says so in a comment: "this surface is Grenada Meteorological Service facing", and remaps the shared tokens onto the Met Office palette (navy `#0b132b`, not the Barrels navy `#15006b`).
- **Rule or reference:** the owner's rule that the Barrels platform screens share one clean look and one set of patterns; the account lane spec ("Do not use the GMS palette ... a Barrels product must not inherit the Grenada Meteorological Service brand"); `docs/design-system.md` still lists `auth` in the Met Office typography lane, so the written rules disagree. The bookings audit raised the same point from the other side (finding 10 in [bookings-2026-11.md](bookings-2026-11.md)).
- **Why it matters:** `auth` is the sign-in for every Barrels product, including the Barrels Bookings Studio for a salon owner and the account app for everyone. A person signing in to run a salon sees a weather service's logo and the names of other clients' internal tools (and, signed out, the existence of a staff console). The directory also omits Barrels Bookings and the account app, so it lists some products and not the ones the person may be here for.
- **Suggested fix:** decide the lane first (Barrels platform look, with the Met Office identity only when the person arrives from a Met Office app); show the requested app's name and a neutral Barrels panel on the sign-in screens; show the app directory only after sign-in. Needs an owner decision; the tokens already exist (the account app uses them). Size L. VISIBLE.

#### 3. There is no lane spec, and old internal names show

- **Where:** no `docs/design/auth.md`. Visible leftovers: the browser tab reads "Grenmet Auth" on the sign-in, sign-up, forgot-password and not-found pages and "Security — Grenmet Auth" on Security (`src/app/layout.tsx`, `src/app/security/page.tsx`), the page description says "for Grenmet apps", the recovery-codes download is named `grenmet-recovery-codes.txt` (`recovery-codes.tsx`), and the sign-in text reads "Use your work email, or continue with Google", which is wrong for customers and salon owners.
- **Rule or reference:** `docs/agents/extended-rules.md` ("Design rules learned in review go into the lane spec"); web-design-guidelines, Content & Copy (second person, specific, consistent); account lane spec for the pattern a spec should have.
- **Why it matters:** without a spec every finding in this document is a judgement call, and the next change cannot be checked. A tab named after an old project name tells people they are in the wrong place.
- **Suggested fix:** write `docs/design/auth.md` after finding 2 is decided (tokens, layout, states, copy rules), then change the titles, description and download name to "Barrels" and use a neutral line such as "Use your email, or continue with Google". Size M for the spec, S for the names. The spec is INVISIBLE; the names and the line are VISIBLE.

#### 4. Setting up two-step verification takes three dialogs and a wait, and skipping leaves no way back in

- **Where:** `src/app/security/two-step-settings.tsx`. Press "Set up", scan, enter a code, "Turn on". A second dialog then says "Wait for your app to show a new code", asks for the account password (where there is one) and a fresh six-digit code, and only then creates the recovery codes. A third dialog shows them. "Skip for now" is an equal-sized button on the second dialog and leaves the account with an authenticator and no recovery codes. The Security page then reads "None yet", with no warning colour.
- **Rule or reference:** the three reference flows. Customer.io shows the recovery codes before the final "Next" and enables on that step; Railway shows them in one dialog with a warning and "I've backed up my codes"; Xero shows a four-step progress line (Intro, Choose an app, Set up app, Add a backup) and offers "I don't have a code" and "Need help authenticating?" on the code step. In none of them is a person asked to wait for a second code.
- **Why it matters:** a staff member who must enable two-step verification to reach the admin tools can get stuck waiting for a code, give up at "Skip for now", and later lose a phone with no recovery path. The wait is the step most likely to be abandoned.
- **Suggested fix:** return the recovery codes in the same response that turns two-step verification on, so setup is two screens (scan and confirm, then save the codes); until the API changes, show a visible step line and, for staff accounts, make "Skip for now" a plain text link with a sentence about what happens. Size L for the API change, S for the step line and the skip link. VISIBLE.

#### 5. The Security page's layout works against its meaning

- **Where:** `src/app/security/page.tsx`, `src/components/account-layout.tsx`.
  - The guidance paragraph under "Two-step verification" sits directly on the divider line with no space (seen on both widths).
  - Each row shows its state badge below the action button, so on a phone the order is name, description, "Set up", then "Off". The state is the first thing a person wants to read.
  - "Password" is both a tab and a row on Security, and the page has no row for sessions or passkeys, so the overview that Railway shows (Authenticator, Recovery codes, Passkeys, Sessions on one page) is spread over four tabs.
  - The section headings are 11 pixel capitals in a monospace face.
- **Rule or reference:** refactoring-ui (group related things, put state next to the label); web-design-guidelines, Typography; Railway security overview.
- **Why it matters:** the page is the place where people check that their account is safe, and the state of each protection should read at a glance.
- **Suggested fix:** add vertical padding to the guidance paragraph, move the badge beside the row title, drop the Password tab in favour of the row and add a "Sessions" row that links to the list; raise the heading size to 12 pixels or more. Size M. VISIBLE.

#### 6. The emailed-code step is a dead end if the code does not arrive

- **Where:** `src/components/EmailCodeForm.tsx` (used by `/code` and `/signup`). After "Email me a code" the page says "If the address can sign in, we've sent it a 6-digit code. It expires in 10 minutes." There is no "Send a new code", no "Use a different email address" and no hint to check the spam folder; the only exit is "Sign in with a password instead" (people who signed up without a password have none). The submit button then reads "Sign in" even on the sign-up page. The superuser invitation page, by contrast, has "Email me a new code".
- **Rule or reference:** fixing-accessibility (error messages include the next step); web-design-guidelines, Content & Copy ("Specific button labels", errors include a fix); Xero's code step ("I don't have a code").
- **Why it matters:** this is the main way people create and enter an account (the passwordless decision), and a wrong email address or a lost message cannot be recovered without starting the whole page again.
- **Suggested fix:** add "Send a new code" (with a short wait before it is active), "Use a different email" and one line about spam; label the button "Create account" on the sign-up page. Size M. VISIBLE.

#### 7. Text fields are 14 pixels, so phones zoom the page on focus, and many tap targets are under 44 pixels

- **Where:** measured at 390 pixels on staging. The shared field class (`inputClass` in `src/components/form-styles.ts`) sets `text-body`, which is 14 pixels (the email field measured 14 pixels, 47 tall); the one-time code boxes are 16. Safari on an iPhone zooms the page in when a field under 16 pixels gets focus, and it does not zoom back out by itself. Inline links: "Forgot password?" 110 by 20, "Create an account" 113 by 18, "Sign in" on sign-up 42 by 18, the support email 131 by 19, "Sign in with a password instead" 245 by 38. Theme buttons 28 by 28. Outline buttons such as Set up, Change, Connect, Join, Leave, Sign out are about 32 tall; the account tabs are about 32 tall; the not-found button is 32 tall and the "Join" and "Not now" buttons are 40 tall. The main buttons (Sign in, Email me a code, Continue with Google) and the input fields are 44 or more.
- **Rule or reference:** mobile-native (inputs that zoom the page; touch targets); the account and bookings lane specs set 44 pixels as the Barrels platform target (`auth` has none of its own).
- **Why it matters:** the page jumping in on the first tap in the email field is the first thing a phone user sees on the sign-in screen; and the sign-in links are the way out of a failed attempt, which a thumb misses at 18 pixels.
- **Suggested fix:** set field text to 16 pixels on phones (`text-base md:text-sm`, as the shared `Input` does); keep the look and enlarge the hit area with padding or a pseudo-element on the inline links; give the outline buttons a 44 pixel minimum on phones. Size S. The field size is VISIBLE (slightly larger text); the links are INVISIBLE (hit area only); the taller buttons are VISIBLE.

#### 8. Nine tabs, a header that jumps, and a panel that scrolls away

- **Where:** `src/components/account-tabs.tsx`, `src/components/auth-shell.tsx`.
  - There are nine tabs (Profile, Password, Security, Sessions, Apps, Organisations, Tickets, Rewards, Access). On a phone only five show; the rest are cut off at the edge with no fade or arrow, so Tickets, Rewards and Access can look as if they do not exist.
  - The content is centred vertically, so the title sits at 70 pixels on Password but 190 pixels on Organisations. The page seems to move as the person changes tabs.
  - The left panel is not sticky. On the Sessions page (about 7,900 pixels tall on desktop) "Your account" and the app list sit thousands of pixels below the top, out of sight.
  - "Sign out of all apps" sits beside every page title. When the description is long it wraps into five lines ("Sign / out / of / all / apps" on Organisations at 390 pixels).
- **Rule or reference:** web-design-guidelines, Content Handling (flex children need room); refactoring-ui, hierarchy (a page title should not compete with a sign-out button); mobile-native.
- **Why it matters:** people cannot find the tabs they cannot see, and a layout that moves between tabs feels unreliable.
- **Suggested fix:** group the tabs into fewer places (Profile, Security with Password and Sessions, Apps and organisations, Access), add an edge fade to the scroller, align the content to the top, make the brand panel `sticky` with full height, and move "Sign out of all apps" into a menu or the foot of the page. Size M. VISIBLE.

#### 9. The Sessions page does not cope with many sessions

- **Where:** `src/app/sessions/sessions-list.tsx`. The staging test account shows about 70 rows on one page with no paging or grouping. Each row says "Chrome on Linux" and a technical app name ("cap", "gaa-admin") with an address and a relative time; every Sign out button is named "Sign out Chrome on Linux", so a screen reader hears dozens of identical buttons. A normal staff member collects one session per app per browser, so this is a long list soon.
- **Rule or reference:** break-ui (huge counts); fixing-accessibility, accessible names; Railway's sessions table (device, last active, first used, one menu per row).
- **Why it matters:** people open Sessions to find the one they do not recognise.
- **Suggested fix:** group by browser and device ("This device, 6 apps"), show app names in words, add the app and time to each button's accessible name, and page at 20. Size M. VISIBLE.

#### 10. Sign-out and leave actions happen at once

- **Where:** "Sign out of all apps" (every account page), "Sign out everywhere" and "Sign out other sessions" (Sessions), and "Leave" (Apps; the row text says "Leaving ends your sessions in this app"). Each is a plain form or button with no confirmation and no undo. "Sign out of all apps" and "Sign out everywhere" do exactly the same thing under two names (`signOutAction` and `signOutEverywhereAction` in `src/app/actions.ts` both call `endSession({ allSessions: true })`).
- **Rule or reference:** web-design-guidelines, Navigation & State ("Destructive actions need confirmation modal or undo window").
- **Why it matters:** the first one sits next to the page title, easy to hit by accident, and ends sessions in every app the person is working in.
- **Suggested fix:** one name, one place, and a confirm dialog (the two-step dialogs show how). Size S. VISIBLE.

#### 11. The staff step-up screens bury the one action

- **Where:** `src/app/continue/page.tsx`, cases "mfa-enrol" and "mfa-sign-in". The page explains in a paragraph that privileged tools need an authenticator, then offers "Open account security" or "Sign in again" as a small underlined text link (14 pixels, no button). The same pattern, `text-foreground text-sm underline`, is used for "Go to your account" on the notice screens; the "You don't have access to Barrels admin" screen (seen on staging, reached by a non-superuser) ends in that small link and nothing else.
- **Rule or reference:** refactoring-ui, hierarchy (one clear primary action); web-design-guidelines, Content & Copy (specific labels).
- **Why it matters:** this is the screen a new administrator sees when a required step blocks them, and the link looks like body text.
- **Suggested fix:** use the shared primary button for the next step on these screens. Size S. VISIBLE.

#### 12. The "Join" screen reads in a circle, and the app has two main button colours

- **Where:** `src/app/continue/page.tsx`. For the account app the text reads "Join Barrels account? You'll use your Barrels account to sign in to Barrels account. You only need to do this once." The "Join" button is navy and 40 pixels tall; every other main button in the app (Sign in, Email me a code, Change password, Turn on) is a brighter blue (`--auth-accent`, `#0b63ee`) and 44 or more; the not-found button is navy too. This screen is also the first thing every new person meets in the account app on staging (known, issue #1335).
- **Rule or reference:** refactoring-ui, hierarchy and consistency (one primary colour); web-design-guidelines, Content & Copy.
- **Why it matters:** two primary colours in one product tells people nothing, and the circular sentence gives no reason to press the button.
- **Suggested fix:** one primary button class; for the account app skip the prompt (#1335), and for others write what joining does ("Use Barrels Events with your Barrels account"). Size S for the class, M for the copy. VISIBLE.

### Nice to have

#### 13. Sign-in offers three routes of equal weight

- **Where:** `src/components/SignInForm.tsx`. "Continue with Google" and "Email me a sign-in code" are two outlined buttons of the same size above an "or" divider, then the email and password form with the one filled button. The email-code button looks like a social provider button but is a different kind of choice. The owner's decision is passwordless first, so the order may be wanted: it is a question, not a defect.

#### 15. Small setup details

Size S. INVISIBLE for the announcement and error, VISIBLE for the copy button.

#### 16. The not-found page has no shell

#### 17. The invitation flow counts its steps two ways

- The invitation page says "Step 1 of 3" on two screens in a row (send the code, enter the code) and then "Step 2 of 3: set up your authenticator", and the Security setup it leads to is headed "Step 1 of 2" and "Step 2 of 2". Make it one count. Size S. VISIBLE. (Code only: see "What could not be checked".)

#### 18. The theme switch is on every screen

## Documents that no longer match the app

These are small drifts noticed while auditing. Nothing was edited.

- `docs/design-system.md` places `auth` in the "GMS institutional" lane and calls it a "brand cleanup lane"; `src/app/globals.css` says it is "Grenada Meteorological Service facing"; the owner's rule is that Barrels platform screens share one look. These three need to agree (finding 2).
- The rewards and organisation screens are described at length in `apps/web/auth/AGENTS.md` but no design rule covers them.
- `apps/web/auth/AGENTS.md` lists the account tabs as organisations, tickets and rewards only; the app also has Password, Security, Sessions, Apps and Access tabs.

## What could not be checked

- **A real phone.** Sticky hover, the on-screen keyboard and the browser bar were argued from the stylesheets and tested only in an emulated phone viewport.
- **The Security setup dialogs.** Opening "Set up" writes a pending secret on the account and, for staff accounts, sends an email, so the dialogs were read from code and compared with the references; they were not opened on staging.
- **The emailed-code step, the two-step sign-in step and the recovery-code sign-in.** Reaching them needs a real email or a code from a phone, so they were audited from code only.
- **The superuser invitation page.** It returned "Page not found" on staging (it is on `dev` only), so it was read from code.
- **Rewards, tickets and the organisation rewards screens.** Out of scope for this audit.
- **Screen readers and the full keyboard route.** Reasoned from the markup, not run with a screen reader.
- **Production.** Only staging was visited.
- **The test account is not typical.** It has many sessions and a long role list, which made the Sessions and Access pages look heavier than an ordinary account would; the findings about them describe what happens at volume.
