# Design audit: Barrels admin, the staff console (2026-11)

**Status:** Phase 1 audit, read only. Nothing was changed in the app; every fix below is a proposal for the owner.  
**Owner:** Barrels Grenada engineering (design mastery programme, issue #1453, section 8)  
**Last updated:** 2026-11-15

## Scope and method

Surfaces audited, all in `apps/web/admin`: the console shell (header, navigation, sign-out, main area), the Overview page, the new **Superusers** page (invite a superuser, pending invitations, revoke), the status cards, the organisation table, the moderation decision forms (as a comparison point), the "Barrels staff only" refusal page, the sign-in hand-off page and the not-found page. The invoices, payments, receivables, flags, customers, organisation detail and API key screens were sampled for patterns (buttons, disclosures, notices, target sizes) but not read line by line.

The rule for judging: a defect is a gap against this app's own lane spec ([`docs/design/admin.md`](../admin.md)) or a rule from a design skill, never a difference from another app. The admin console is for Barrels staff and is dense on purpose; the rules for a customer page (large type, one task per screen) do not apply.

**This audit is mostly from code.** Staging admin needs a Barrels superuser, the staging test account is not one, and the brief said not to create accounts or change data. What was seen on staging: the sign-in hand-off page (`/signin?sign_in=expired`) at 390 and 1280 pixels, and the "You don't have access to Barrels admin" refusal that the sign-in host shows a non-superuser. Everything else was read from code and, for one layout question (the header navigation on a phone), checked by rebuilding the same markup and measuring it in a browser.

Method:

1. Read the instructions (`AGENTS.md` at the root and in `apps/web/admin`), the lane spec, the design system and design workflow notes and the section "Reviewing or polishing UI: check these before reporting a gap" in `docs/agents/extended-rules.md`.
2. Checked where styles live before reporting anything. `src/app/globals.css` imports `app-feel.css` (tap flash, `touch-action`, reduced motion, scroll containment in menus) and the shared token layer with no local colours, exactly as the spec says. The shared `Table` wraps itself in `overflow-x-auto`, so wide tables scroll inside their own box on a phone. Nothing in this audit repeats a gap those files already cover.
3. Read the layout, the Overview and Superusers pages and their components, then applied the rules of these skills: web-design-guidelines (pinned rules), fixing-accessibility, refactoring-ui (through the lane spec), mobile-native, emil-design-eng and break-ui (long emails and reasons argued from the code and the limits in the form). The console has no motion, so the animation skills had nothing to review.
4. Compared the Superusers invitation form with the moderation decision forms in the same app (they are the best pattern in the console) and with the saved reference flows where they apply, for ideas only: [Railway two-factor setup](https://mobbin.com/flows/b9d19e77-5cb5-482e-9cec-2920a3f9ccd2) for a security screen of rows with one action each; the other two ([Customer.io](https://mobbin.com/flows/7fece37b-b393-4aa2-b261-fc6931c2a35e), [Xero](https://mobbin.com/flows/f6c97bc9-ef5d-49a7-a87c-65177ad11e85)) are about the sign-in app's setup dialogs, not this app.

How to read a finding:

- **Rule or reference** is the lane spec line, skill rule or reference behaviour behind it.
- **Size:** S is under half a day, M is about a day, L is several days or needs a decision first.
- **INVISIBLE** means staff would not see a difference in normal use (accessibility, focus, keyboard, hidden hit areas, behaviour on failure). These can merge on green checks. **VISIBLE** means layout, colour or wording changes, so the owner reviews before and after screenshots first.

## What is already strong

- **It keeps to the spec's tokens.** The stylesheet defines no colour of its own; surfaces use `bg-card`, `bg-background`, `text-muted-foreground`, `border` and the shared `Badge`, `Card` and `Table`, so any future re-skin comes for free. Noto Sans is loaded in the root layout.
- **Status is written out.** The status cards say OK, Problem or Unknown beside the badge, an unknown value is never shown as green, and the organisation table writes "Active" or "Suspended" and "Verified" or "Not verified".
- **Failure and loading are handled in words.** Sections stream behind `Suspense` with a loading line, an empty line and an error line; a refused (403) pending-invitation list explains what to do and is not reported as a fault; any other failure says "could not be loaded", never an empty list.
- **The Superusers form is careful.** Labels tied to inputs, spell-check off on the email, a live character count for the reason ("12 of 500 characters") tied to the field with `aria-describedby`, the rule for the reason written before the field, typed values kept on a refusal and cleared on success, "Sending…" while the request runs, dates formatted with `Intl.DateTimeFormat` in Grenada time, and a confirmed revoke that says it "cannot be undone".
- **Destructive steps confirm.** Revoke, reject and suspend sit behind a native disclosure with the reason field or an explicit confirm button, as the lane spec asks, and the result comes back as a written notice.
- **The refusal page matches the spec.** "Barrels staff only" has no navigation, says why, names the signed-in email and has a sign-out button. Staff and non-staff are told apart on the server.
- **The moderation forms are the best pattern.** Their disclosure rows and fields are 44 pixels tall (`min-h-11`) and an error takes focus (`ref.current?.focus()`). Finding 3 asks for the same on the Superusers page.
- **Stays quiet.** No animation, no analytics, no decoration, as the spec says.

## Findings

### Blocking

None found. Nothing stops a staff member from reading the console or inviting a superuser; the issues below are about orientation, consistency and form feedback. (The sign-in hand-off page and the not-found page are readable.)

### Should fix

#### 1. The navigation has no "you are here" and may not fit a phone

- **Where:** `src/app/(console)/layout.tsx`. Eight links (Overview, Organisations, Invoices, Receivables, Payments, Flags, Superusers, Moderation) sit in one row with no marker for the current page: there is no `aria-current` and no visual state, so the only change between pages is the heading. The nav is a plain flex row with no wrapping or scrolling. Rebuilding the same header markup and loading it at 390 pixels showed the nav row 646 pixels wide, so the page became 662 pixels wide and scrolled sideways by about 270 pixels (this was the rebuilt markup, not the real page; the real header uses the same classes). The links are 20 pixels tall and the "Sign out" button is about 28 tall.
- **Rule or reference:** lane spec, Layout ("usable at phone width"); fixing-accessibility, semantics (mark the current item); mobile-native (touch targets). The moderation page already uses `aria-current` for its tabs.
- **Why it matters:** with eight sections a person needs to see which one they are in, and on a phone a row that is wider than the screen forces the whole page to scroll sideways.
- **Suggested fix:** mark the current link (`aria-current="page"` plus an underline or bar), let the row scroll or wrap on narrow screens with an edge fade, and give the links and the sign-out button a 44 pixel hit area. Size S to M. The attribute is INVISIBLE; the visual state and the wrapping are VISIBLE.

#### 2. Buttons are hand-written instead of the shared Button

- **Where:** the console files. Only three places use the shared `Button`; the rest write their own classes. The same outlined button (`rounded-md border px-3 py-1.5 text-sm`) is copied in six places, the sign-out button has its own variant (`px-2.5 py-1`), and the Superusers "Send invitation" button is near-black (`bg-foreground text-background`), a primary button that is not the Barrels navy the lane spec names. Seven different looks result across the console (moderation uses the shared Button).
- **Rule or reference:** lane spec ("Components come from `@barrelsgd/ui/components/ui/<name>` (badge, button, card, table, skip-link)"); refactoring-ui, consistency; `docs/design-system.md` (shared primitives carry the focus, press and disabled states).
- **Why it matters:** the shared Button already gives a 44 pixel option, a focus ring and a disabled style; each copy has to be fixed on its own, and a primary action should look the same on every page.
- **Suggested fix:** replace the copies with `Button` (variants `default`, `outline`, `destructive`) in one pass; the inputs and text areas can follow with the shared `Input`. Size M. VISIBLE (some buttons change colour and size).

#### 3. The Superusers page does not give the feedback the moderation pages do

- **Where:** `src/components/superuser-invitation-panels.tsx`, `pending-superuser-invitations.tsx`, `src/app/(console)/superusers/page.tsx`.
  - A refusal appears as a red paragraph above the form (`role="alert"`), but focus stays on the button; the moderation form moves focus to the message. Fields never get `aria-invalid`, and the message does not say which field is wrong.
  - A success or a revoke notice is a plain paragraph with `role="status"` at the top of the page, with no border or colour, easy to miss on a long page.
  - "Revoke" is a bare disclosure summary in body text, about 20 pixels tall, with nothing to show that it is a button or that it is destructive until it opens.
  - The preconditions (an authenticator and a two-step sign-in) are in the second sentence of a three-sentence paragraph, and a superuser who has neither learns it only by sending the form and getting a refusal.
- **Rule or reference:** fixing-accessibility, forms and errors (errors linked to fields, invalid fields marked, critical errors announced); web-design-guidelines, Forms ("focus first error on submit"); lane spec, Actions ("results come back as a written notice").
- **Why it matters:** this page grants the highest access in the system and should be the clearest form in the console.
- **Suggested fix:** copy the moderation pattern (focus the message, 44 pixel summary, destructive wording on Revoke), add a bordered notice style shared with the other pages, and show a short "You need two-step sign-in to invite" notice with a link to Security when the current session has none. Size M. Focus and field marking are INVISIBLE; the notice and the Revoke look are VISIBLE.

#### 4. The Overview still says a finished feature is "not built yet"

- **Where:** `src/app/(console)/page.tsx`. The dashed note reads "Verification and app entitlements. Not built yet. Reviewing organisation verification and switching apps on or off per organisation arrive in the next slice (C2)." Verification, entitlements, suspension, members and history are built (`AGENTS.md`, "Organisation management (C2)").
- **Rule or reference:** lane spec, Placeholders ("work that is not built is a dashed-border note saying it arrives in a later slice"); the note is now false.
- **Why it matters:** a staff member reading it will think the feature is missing, and the Overview is the page everyone lands on.
- **Suggested fix:** replace the note with links to the Organisations list ("Verify an organisation or switch its apps on or off") or remove it. Size S. VISIBLE.

#### 5. Small targets throughout the console

- **Where:** `src/app/(console)/layout.tsx` and the shared outline buttons. The nav links are 20 pixels tall, "Sign out" about 28, the outlined buttons about 32, and 8 of the 12 disclosure summaries in the console are not given a minimum height (the moderation ones are 44).
- **Rule or reference:** mobile-native (touch targets); lane spec, Layout ("usable at phone width"). The console is also used on a tablet or a phone by staff on the move.
- **Why it matters:** the actions here are consequential and a missed tap on "Confirm revoke" or "Suspend" next to another control is not a good place for a thumb.
- Text fields in the console forms (for example the Superusers email and reason) use `text-sm`, which is 14 pixels; a phone browser zooms in when a field under 16 pixels gets focus.
- **Suggested fix:** make 44 pixels the minimum for every control that changes data and use 16 pixel field text on phones; the look can stay (padding only). Size S. INVISIBLE for the links and summaries, VISIBLE for the taller buttons and the field text.

### Nice to have

#### 6. Times have no zone

- The invitation expiry reads "Expires 16 Nov 2026, 14:30" with no zone name, though it is formatted in Grenada time (`pending-superuser-invitations.tsx`). Staff in another zone, or reading an email, may misread it. Add "(Grenada time)" or use `timeZoneName: "short"`. Size S. VISIBLE.

#### 7. A very long reason or email

- The pending list shows the invitation's email and the full reason text in muted grey with no clamp (`pending-superuser-invitations.tsx`); a 500 character reason is allowed. The row's flex container wraps, but a long email without spaces has no `break-all` or `min-w-0` and could push the Revoke disclosure off the row (break-ui). Add `break-words` and `min-w-0` to the text column. Size S. INVISIBLE (only in the worst case).

#### 8. Wide tables have no scroll hint

- The shared `Table` scrolls inside its own box on a phone, which is right, but nothing shows that more columns are off screen (the organisation table has five columns). Add an edge fade or a "scroll for more" line on narrow screens. Size S. VISIBLE.

#### 9. The hand-off and refusal pages

- The "Sign-in did not finish" page (seen on staging) and the "Barrels staff only" page are plain text on white with no Barrels name or mark; an outlined button (34 pixels tall for "Try again" on staging, smaller for "Sign out of this console") is the only action. They are correct and match the spec's "plain" refusal, so this is only a note: add the product name above the heading and use the shared Button. Size S. VISIBLE.
- A signed-in person who is not a superuser never reaches the "Barrels staff only" page from a normal sign-in: the hand-off stops on the sign-in host with "You don't have access to Barrels admin. Ask an administrator to give your account access, then try again." (seen on staging), shown in the Met Office-branded shell with a small underlined "Go to your account" link. That screen is part of the sign-in app (finding 2 in [auth-2026-11.md](auth-2026-11.md)). Size S for the link. VISIBLE.

## Documents that no longer match the app

These are small drifts noticed while auditing. Nothing was edited.

- `docs/design/admin.md` says the header holds "product name, Overview, Organisations, signed-in email, Sign out"; the header now also has Invoices, Receivables, Payments, Flags, Superusers and Moderation.
- `docs/design-system.md` lists the lane specs in its overview without `admin` (and `barrels`, `commit`, `events`), although the files exist; the bookings and Babydoll audits noted the same.
- `docs/design/admin.md` still lists organisation verification and suspension as the actions that sit behind a disclosure; invoice void, flag delete, API key revoke, moderation decisions and the superuser invitation revoke follow the same rule and could be named.

## What could not be checked

- **The signed-in console on staging.** No superuser account was available and none was created, so every console page was audited from code. Spacing, real column widths, how the header looks at 390 and 1280 pixels, and the loaded state of the Overview and Superusers pages were not seen live.
- **The header navigation on a phone** was checked by rebuilding the markup, not by looking at the real header.
- **The invoices, payments, receivables, flags, customers, organisation detail, API key and site screens** were sampled for patterns, not audited one by one, and their forms (the invoice editor in particular) deserve their own pass.
- **Superuser invitation acceptance.** That page is in the sign-in app and is covered by [auth-2026-11.md](auth-2026-11.md).
- **Screen readers and the full keyboard route.** Reasoned from the markup, not run with a screen reader.
- **A real phone and tablet.** Argued from the code and an emulated viewport only.
- **Production.** Not visited; the admin host is on staging and production behind staff sign-in.
