# Design audit: Barrels HR (2026-11)

**Status:** Phase 1 audit, read only. Nothing was changed in the app; every fix below is a proposal for the owner. Nothing was seen in a browser: this audit is from the code alone (see "What could not be checked").  
**Owner:** Barrels Grenada engineering (design mastery programme, issue #1453)  
**Last updated:** 2026-11-23

## Scope and method

Surfaces audited, all in `apps/web/hr` (planned host `hr.barrels.gd`, the organisation in the path, ADR-0043):

- on `dev`: the organisation picker (`/`), one organisation's home (`/<organisation>`), the staff list for HR administrators (`/<organisation>/staff`), a person's own record and leave balances (`/<organisation>/me`), the sign-in hand-off, and the error and not-found pages;
- not merged yet: the read-only staff record (`/<organisation>/staff/<person>`) from pull request 1760 (branch `feat/hr-app-s3`), read with `git show`. It is the only open HR pull request.

The app is a first scaffold. It has no lane spec (`docs/design/hr.md` does not exist), no staging host and no dev script. So the rule for judging is: a defect is a gap against a rule from a design skill, the shared Barrels look the app says it follows (`docs/design/account.md`), or one of the owner's standing HR rules (organisation-scoped and driven by each organisation's configuration; organisation HR administrators onboard staff; HR has its own status colours and a Returned state; empty sections are never hidden; phone and laptop both matter).

Method:

1. Read the instructions (`AGENTS.md` at the root and in `apps/web/hr`), ADR-0043, `docs/hr/end-to-end-alignment.md`, `docs/design-system.md`, the lane specs for account and bookings, and the section "Reviewing or polishing UI: check these before reporting a gap" in `docs/agents/extended-rules.md`.
2. Checked where styles live before reporting anything. The app's stylesheet (`src/app/globals.css`) is eight lines: it imports Tailwind, the shared touch layer `packages/ui/src/styles/app-feel.css` and the shared tokens `packages/ui/src/styles/globals.css`. The touch layer already switches off the tap flash, sets `touch-action: manipulation` on controls and cancels animation for people who ask for less motion, so none of that is reported. Because the tap flash is off, each tappable control needs its own pressed state; that gap is in finding 11. Tailwind's `hover:` only applies on devices that can hover, so sticky hover on phones is not a problem here. Inter is loaded in `layout.tsx` and the shared `--brand-font-sans` falls back to it, so the typeface is correct.
3. Read every page, component and formatting helper, the two API schemas behind them (`HrMeEmploymentPublic` in `apps/api/fastapi/src/hr/schemas.py`, `StaffSetup` in `src/baseline/schemas.py`) and the staff query (`list_staff` in `src/baseline/service.py`), then applied these skills: ui-polish-pass (the states table below), web-design-guidelines, fixing-accessibility, mobile-native, emil-design-eng, break-ui (worst-case names, emails and list sizes, argued from the code) and the repository's refactoring-ui. There is no motion in the app, so the motion rules found nothing.
4. Judged two journeys: a staff member sees their own record and leave balance; an organisation HR administrator finds a staff member and reads their record.
5. Looked up reference flows on Mobbin for ideas (see "Inspiration").

How to read a finding:

- **Rule or reference** is the skill rule, owner rule or reference behaviour behind it.
- **Size:** S is under half a day, M is about a day, L is several days or needs a decision or an API change first.
- **INVISIBLE** means staff would not see a difference in normal use (accessibility, focus, keyboard, behaviour with extreme data). These can merge on green checks. **VISIBLE** means layout, colour or wording changes, so the owner reviews before and after screenshots first.

## Proposed design rules (what `docs/design/hr.md` should say)

This is a proposal for the missing lane spec. It adds no new tokens.

**Look.** The Barrels platform look, the same as `account` and `bookings`: white paper, near-black ink (`#111827`), grey helper text (`#6b7280`), Barrels navy (`#15006b`) for the one main action on a screen, Inter, 8 pixel corners, light mode only for now. Never the GMS `--gm-*` palette and never a client's brand: HR is a Barrels product used by many organisations. The organisation's name is the context label on every screen; Barrels HR is the small product label.

**Tokens.** Only the shared semantic classes from `packages/ui/src/styles/globals.css` (`bg-background`, `text-foreground`, `text-muted-foreground`, `border-border`, `bg-primary`, `ring-ring`) and `@barrelsgd/ui` primitives. Grey helper text is for help, never for an error or for the fact a person came to read.

**Status colours (HR's own, always a word with the colour).** One table, used by every HR screen, so the same word never has two colours:

| Kind | Word | Badge |
| --- | --- | --- |
| Person or employment | Active | green (`solid-success`) |
| | Pending (waiting on the organisation) | amber (`solid-warning`) |
| | Inactive | grey (`solid-light`) |
| | Ended (the API's "terminated") | grey outline (`outline`) |
| Request (leave and forms) | Draft, Submitted | outline |
| | Approved | navy (`default`) |
| | Returned (the author must act; show the reason under it) | amber (`solid-warning`) |
| | Rejected (final) | red (`destructive`) |
| | Cancelled | grey (`secondary`) |
| Readiness of a staff set-up | "Needs attention: …" naming what is missing | amber, only when something is missing |

The request rows are the ones already in use in `apps/web/gaa-admin/src/components/hr/request-status.tsx`; they move here unchanged. Returned and Rejected must never look alike.

**Navigation.** Every signed-in screen has one header: the product label, the organisation name (a switcher only when the person has more than one), the signed-in person's name and Sign out. Under it, one navigation row for the organisation, built from that organisation's configuration and the person's access: My record, Leave, then Staff and Setup for HR administrators. A top row that scrolls sideways on phones, a left column on laptops. A person with one organisation goes straight to it. A staff member lands on their own record; an administrator lands on the staff list. A section the person may not use stays visible with one line saying who it is for; empty sections stay visible with a sentence saying what will appear there.

**Density.** Two modes. Staff self-service (my record, leave) is phone first: one column up to `max-w-3xl`, 16 pixel body text, 16 pixel side gutters, 44 pixel targets, the balance as the largest thing on the page. Administrator lists are laptop first: a table at 14 pixels with name, department, position, status and "needs attention", a search box, filters and a count; on phones each person collapses to a two-line row (name and status; position and department). A record is a set of titled cards of label and value pairs, labels in a fixed left column on laptops and stacked on phones, every field shown with "Not set" when empty.

**Words.** Labels and values are sentence case. Dates read "3 March 2026". Leave types, grades and departments use the organisation's own configured names, never a name derived from a code. No screen names a client organisation or another product in fixed text; where work is still done elsewhere, the organisation's configuration supplies the name and the link.

**States.** Every screen defines loading (a polite status line or skeleton), empty (what will appear and who adds it), one, many, failed (what happened and a "Try again" button), no access (who to ask), and each role.

## What is already strong

- **Access is honest and safe.** The organisation in the address is checked against the person's own list on every page (`src/lib/organisation-access.ts`); a missing and a forbidden organisation read the same; a failed read never looks like "no access" or like an empty list. Expected refusals are not reported as errors, and no names or emails go to error reporting.
- **Every state has words.** No blank screens: no access, no record, no balances, could not load and administrators-only each have their own sentence, and "No HR access yet" says who to ask and offers Sign out.
- **Empty fields are shown, not hidden.** The staff record prints "Not set" for each missing fact, which matches the owner's rule.
- **Status is always a word.** Badges carry "Active", "Pending", "Inactive"; an unknown status reads "Status not recognised" instead of vanishing.
- **Structure is sound.** One first-level heading per page, sections tied to their headings, real definition lists for facts, a skip link, `lang="en"`, staff pages kept out of search engines.
- **Phone basics are in place.** Text links and rows are 44 pixels tall or more, the staff facts stack on phones, emails can wrap, numbers use tabular figures, and plurals are right ("1 staff record", "1 day").
- **Dates cannot shift.** Record dates are formatted in words in one fixed zone (`src/lib/my-record-format.ts`), so a start date never shows a day early.
- **The staff record degrades in parts.** When grades cannot be read, only the grade row says so and the rest of the record stays.

## Findings

### Blocking

#### 1. There is no way to sign out, and nothing shows who is signed in

- **Where:** every signed-in screen. The only Sign out button in the app is inside the "No HR access yet" state (`src/components/no-access.tsx` lines 25 to 29). The page frame (`src/components/organisation-page.tsx` lines 8 to 14) and the picker (`src/app/page.tsx` lines 36 to 49) have no header, no name and no sign-out.
- **Rule or reference:** the account lane spec, Layout: the header carries the name and a "Sign out of this app" button. Deel and Workable keep the person and the organisation in the header on every screen.
- **Why it matters:** these pages show employment facts, leave and other people's staff records. At an airport or a salon, HR is opened on shared desktops. A person who has access cannot leave the app, and the next person at the desk cannot tell whose record is open.
- **Suggested fix:** one shared header on every signed-in page: "Barrels HR", the organisation name, the signed-in name and Sign out (the form already exists in `no-access.tsx`). Size M. VISIBLE.

#### 2. An HR administrator cannot find a person

- **Where:** the staff list (`src/components/staff-list.tsx`; `src/app/[orgSlug]/staff/page.tsx` lines 135 to 144). There is no search, no sort, no filter and no grouping, and the page shows people in whatever order the API sends them. The API query has no ordering and no paging (`apps/api/fastapi/src/baseline/service.py`, `list_staff`, the `select` near lines 236 to 251), so the order is not even promised to stay the same between visits. Each person takes about eight lines on a phone, so 150 staff is well over a hundred screens of scrolling.
- **Rule or reference:** break-ui, "Huge": an unpaginated list must be tried at its realistic upper bound. Workable's people directory has a search box, status and department filters, a sort and a "showing 3 employees" count above the list.
- **Why it matters:** "find a staff member and read their record" is the administrator's whole journey, and it fails at the first step for any organisation larger than a few dozen people.
- **Suggested fix:** sort by name, add a search box over name, email and employee number and a status filter, keep the count. A filter on the page is size S to M; ordering and paging in the API is a separate, small contract change. VISIBLE.

### Should fix

#### 3. Every organisation is told its HR work is "in the GAA staff portal"

- **Where:** `src/app/[orgSlug]/page.tsx` lines 101 to 104, `src/app/[orgSlug]/staff/page.tsx` lines 97 to 100, and the staff record in pull request 1760 (`[userId]/page.tsx` lines 242 to 245).
- **Rule or reference:** the owner's rule that HR is organisation-scoped and driven by configuration.
- **Why it matters:** the sentence is fixed text. A salon's staff would be sent to another client's internal tool, by name, with no link. Even for GAA staff the sentence gives no way to get there.
- **Suggested fix:** take the name and address of "where HR work is done for now" from the organisation's configuration and show it as a link; with none set, say "Ask your HR administrator". Size S for the wording, M with the configuration field. VISIBLE.

#### 4. A staff member needs three screens to see their record, and is offered a dead end on the way

- **Where:** the picker always shows, even with one organisation (`src/app/page.tsx`, the comment at lines 13 to 17); the organisation home is three headings with one link each (`src/app/[orgSlug]/page.tsx` lines 75 to 106); "View the staff list" comes first and is shown to people whose access reads "Own record only" (line 73), who then land on "The staff list is for HR administrators".
- **Rule or reference:** refactoring-ui, hierarchy: lead with what this person came for. Gusto and Remote open on the person's own time off; Deel puts balances and requests on the first screen.
- **Why it matters:** the most common visit (a staff member checking leave on a phone) is the longest path, and the first link they are offered refuses them.
- **Suggested fix:** with one organisation, go straight to it. Put the person's own summary (status, position, leave balances) on the organisation home, first. Keep the Staff entry visible to everyone, but for people without administrator access show it as a plain line ("Staff list: for HR administrators") instead of a link that refuses. Size M. VISIBLE.

#### 5. The same status word has two colours, and there are two status vocabularies

- **Where:** "Inactive" is grey in the staff list (`src/components/staff-list.tsx` line 17; `staff-status.tsx` line 16 in pull request 1760) and amber on My record (`src/lib/my-record-format.ts` line 15). The staff list uses active, pending and inactive; My record uses Active, Inactive and Terminated.
- **Rule or reference:** the owner's rule that HR has its own status colours; refactoring-ui: colour must mean one thing.
- **Why it matters:** an administrator comparing a person's record with their own will read amber as "something needs doing" in one place and nothing in the other.
- **Suggested fix:** one status table for the whole app (the one proposed above), in one file, used by both screens. Size S. VISIBLE.

#### 6. Links do not look like links

- **Where:** "All organisations" (`src/components/organisation-page.tsx` line 21), "View the staff list" and "View my employment and leave balances" (`src/app/[orgSlug]/page.tsx` lines 81 and 92), the organisation name on the staff page (`staff/page.tsx` line 83), each person's name in the list and "Back to the staff list" (pull request 1760). All are ink-coloured medium-weight text that underlines only on hover.
- **Rule or reference:** web-design-guidelines and fixing-accessibility: a link must be told apart from text without hover and without relying on colour alone. Phones never hover.
- **Why it matters:** on a phone nothing says these words can be tapped; in the staff list the names look like bold labels.
- **Suggested fix:** underline text links always (or give list rows a chevron and make the whole row the target, as the organisation picker already does). Size S. VISIBLE.

#### 7. Staff rows say five things about everyone and stress nothing

- **Where:** `src/components/staff-list.tsx` lines 52 to 77 (lines 34 to 59 in pull request 1760): "Account: enabled", "Email: verified", "Staff access: approved", "HR details: ready", "Employee number: …" on every row, in the same grey-and-ink weight.
- **Rule or reference:** refactoring-ui: de-emphasise the competition. QuickBooks and Workable rows carry the name, role, department and one status.
- **Why it matters:** the list exists so an administrator can see who still needs onboarding work. "approval needed" and "incomplete" look exactly like "approved" and "ready", so the people who need attention are found only by reading every row.
- **Suggested fix:** each row shows the name, the status badge and one line: "Ready", or "Needs attention: email not verified, HR details incomplete" in the amber tone. The five facts stay, in full, on the person's record. Size M. VISIBLE.

#### 8. The staff record leaves out what an administrator opens it for

- **Where:** pull request 1760, `src/app/[orgSlug]/staff/[userId]/page.tsx` lines 173 to 247. The record has no department, no position or job title and no leave balances; the heading is the name alone, with the status badge further down under "Account and access". The pull request says the department and balances need API reads that do not exist yet (`StaffSetup` has a department identifier but no name, and no position).
- **Rule or reference:** Deel's and Workable's profile headers put name, job title, department and status together, with time off one tab away; Remote's manager view shows status beside the name.
- **Why it matters:** "who is this, where do they work, are they active, how much leave do they have" are the first four questions, and the record answers one of them.
- **Suggested fix:** a header of name, position, department and status badge; add the department name and position to the staff read; add an organisation-scoped leave balance read; show a "Leave" card that says "Leave balances are not available here yet" until then (shown, not hidden). Size L (needs API work). VISIBLE.

#### 9. Two different layouts for the same kind of fact

- **Where:** My record stacks the label over the value on phones and sets them side by side on laptops with no fixed label width (`src/app/[orgSlug]/me/page.tsx` lines 118 to 125). The staff list and staff record run them together as "Label: value" (`staff-list.tsx` lines 25 to 32; `staff-status.tsx` lines 30 to 36 in pull request 1760). In both, values start at a different place on every line.
- **Rule or reference:** refactoring-ui, alignment and hierarchy for label and value pairs. QuickBooks' employee record uses small grey labels over ink values in an even grid.
- **Why it matters:** a ten-row record with ragged values is slow to scan, and the two screens look like different apps.
- **Suggested fix:** one fact component for the whole app: labels in a fixed column (about 12rem) on laptops, stacked on phones, values in medium weight. Size S. VISIBLE.

#### 10. Leave balances are one bare number per type

- **Where:** `src/app/[orgSlug]/me/page.tsx` lines 163 to 189. Each row is a type and "12 days". There is no entitlement, taken or waiting figure, no year or "as at" date, no next step (requesting leave is not built), and the type's name is made from its code (`codeLabel(balance.leave_type)`, line 180) instead of the organisation's own name for it. The API sends only the type code and the balance.
- **Rule or reference:** the owner's configuration rule. Remote's time-off screen shows the available figure large, then Taken, Approved, Requested and Available to book; Gusto shows the balance, requested and available per policy.
- **Why it matters:** a balance without "of how many, as of when" is the number people most often dispute with HR.
- **Suggested fix:** show the balance as the largest text on the page, with entitlement, taken and waiting beneath it and the date it was worked out; use the configured leave type name; add "Request leave" when that slice is built, and until then say where to ask. Size M to L (needs API fields). VISIBLE.

#### 11. Nothing happens on screen between a tap and the next page

- **Where:** there is no `loading.tsx` anywhere in `src/app`. Every page is rendered on the server on each visit and makes two or three reads in a row (the staff record reads organisations, then staff, then grades). The text links and the picker rows have no pressed state (`organisation-list.tsx` line 20 has hover and focus only), and the shared touch layer has switched the browser's tap flash off.
- **Rule or reference:** `docs/agents/extended-rules.md`: because the tap highlight is off, every tappable control needs its own pressed state. emil-design-eng: the interface must confirm it heard the press. The bookings lane: loading is a polite status line.
- **Why it matters:** on a phone on a slow connection a tap looks ignored for a second or two, and people tap again.
- **Suggested fix:** a `loading.tsx` for the organisation pages with a `role="status"` line or a skeleton of the page frame, and an `active:` background on rows and links. Size S. VISIBLE (briefly).

#### 12. A failed load is a grey sentence that tells people to refresh

- **Where:** seven places, for example `src/app/page.tsx` lines 25 to 28, `[orgSlug]/page.tsx` lines 37 to 41, `staff/page.tsx` lines 119 to 124, `me/page.tsx` lines 111 to 115. Each is `text-muted-foreground` with "Refresh the page to try again."
- **Rule or reference:** the bookings lane, States: a short sentence with the next step. refactoring-ui: grey is for the least important text on the page. The app's own `error.tsx` already has a "Try again" button.
- **Why it matters:** the one message that needs action is styled as the least important text, and on a phone "refresh" is a gesture many people do not know.
- **Suggested fix:** ink-coloured sentence with a "Try again" link to the same address, in one shared component so the seven places match. Size S. VISIBLE.

#### 13. Very long names and addresses are not guarded

- **Where:** the person's name in the list (`staff-list.tsx` line 46; a link with `inline-flex` at line 24 in pull request 1760), the name as the page heading (`[userId]/page.tsx` line 108), the organisation name as a heading (`[orgSlug]/page.tsx` line 69) and in the picker (`organisation-list.tsx` line 23). None has a wrap guard. Emails use `break-all` (`staff-list.tsx` line 49), which breaks every long word mid-letter even when it would fit on the next line.
- **Rule or reference:** break-ui failure table: `overflow-wrap: anywhere` for unbreakable strings; `min-width: 0` on the text that should yield so the badge keeps its place.
- **Why it matters:** an unbroken 60-character name or a long organisation name pushes the page sideways on a 375 pixel phone.
- **Suggested fix:** `wrap-anywhere` on names, headings and emails; `min-w-0` on the name beside the badge. Size S. INVISIBLE.

#### 14. The error, not-found and sign-in pages are missing landmarks and do not match

- **Where:** `src/app/error.tsx` line 20 is a `div` with no `main` and no `main-content` target, so the skip link goes nowhere; `src/app/not-found.tsx` line 6 has the target on a `div`. `src/app/global-error.tsx` is unstyled, has a second-level heading and no first-level one. The retry links on the sign-in pages are hand-styled bordered boxes (`src/app/signin/page.tsx` lines 45 to 50, `src/components/sign-in-hand-off.tsx` lines 25 to 30) while the other pages use the shared Button, which is 32 pixels tall by default (`error.tsx` line 30, `not-found.tsx` line 11, `no-access.tsx` line 26).
- **Rule or reference:** fixing-accessibility, semantics; the account lane: targets are 44 pixels or more.
- **Suggested fix:** a `main` landmark with the skip target on all of them, the shared Button everywhere at a 44 pixel size, and a first-level heading on the last-resort page. Size S. The landmarks and target size are INVISIBLE; the matching look is VISIBLE.

### Nice to have

#### 15. Browser tab titles do not name the organisation

- `src/app/[orgSlug]/page.tsx` sets the title to the fixed word "Organisation", and the staff and record pages to "Staff" and "My record". A person with two organisations open in two tabs cannot tell them apart. Use the organisation's name ("Staff | Grenada Airports Authority | Barrels HR"); keep people's names out of titles. Size S. INVISIBLE.

#### 16. Wording and number details

- Values are lower case in the staff list ("enabled", "verification pending", "not set", `staff-list.tsx` lines 55 to 75) but sentence case elsewhere ("Not set", `my-record-format.ts` line 59).
- A balance of `12.50` is shown as "12.50 days" (`my-record-format.ts` line 37 keeps the string as sent); show "12.5 days".
- "Service details source", "Staff number" beside "Employee number", and "set (not on this staff list)" (pull request 1760) are system words. Say what each is, or give the two numbers distinct plain names.
- My record shows "End date" only when one is set (`me/page.tsx` lines 155 to 160) while the staff record shows every field with "Not set". Pick one rule; the owner's rule favours showing it.
- Rule: web-design-guidelines, content and copy. Size S in total. VISIBLE.

#### 17. Headings that repeat themselves

- The staff page has the heading "Staff" and then "Staff list" directly under it (`staff/page.tsx` lines 89 and 92 to 94). The organisation home gives each single link its own heading. Once the navigation row exists (proposed rules), these fold away. Size S. VISIBLE.

#### 18. The staff record is a dead end

- The supervisor's name is plain text, not a link to their record; the email is not a mail link; there is no way to step to the next person without going back to the list (pull request 1760, `[userId]/page.tsx` lines 180 to 236). Size S. VISIBLE.

#### 19. Phone details

- `layout.tsx` has no viewport export with a theme colour, so the phone's browser bar does not match the page; the body and the sign-in screens use `min-h-screen`, which is taller than the visible area on phones (mobile-native: use the dynamic viewport height); the page gutter is 24 pixels where the lane's phone gutter is 16. Size S. INVISIBLE apart from the gutter.

#### 20. Keyboard focus is uneven

- The picker rows draw the shared focus ring (`organisation-list.tsx` line 20); every other text link falls back to the browser's default outline. The `main` elements have no `tabIndex={-1}`, which the shared skip link's own note asks for (`packages/ui/src/components/ui/skip-link.tsx`). Size S. INVISIBLE.

## Inspiration

Reference flows from Mobbin, for ideas only. Each line says what to borrow and what to leave.

**My record and leave balance**

- [Remote: Requesting a time off (iPhone)](https://mobbin.com/flows/75b95f3c-0b4b-4ef5-8ae9-004157a85079): the first screen is one large "days available" figure with Taken, Approved, Requested and Available to book beneath it, then upcoming time off. Borrow the breakdown and the order. Leave the floating round button; use a labelled "Request leave" button.
- [Gusto: Policies and balances (iPhone)](https://mobbin.com/flows/210579bf-f1c0-4059-9c6d-5e0e6d07d8aa): each leave type is a row that opens to current balance, requested, available and a dated history of changes. Borrow the dated history: it answers "why is my balance this number". Leave the coloured header block.
- [Deel: Time off (web)](https://mobbin.com/flows/edcd69be-5998-4670-9fd7-35a307cb5702): balances, requests and public holidays sit in a left column beside a month calendar, and the empty request list says "No time off requested yet" instead of hiding. Borrow the three always-visible cards. Leave the calendar until the roster moves into this app.

**Requesting leave**

- [Deel: Requesting time off (web)](https://mobbin.com/flows/c17759fc-bb9d-48cf-9e8b-56e30b6cc6b8): a side panel with type, from and to, and a running "Your request: 2 days" total; afterwards the request shows in place with a "Waiting for approval" badge. Borrow the running total and the in-place status. Leave the side panel on phones: use a full page there.
- [Gusto: Request time off (iPhone)](https://mobbin.com/flows/dcd0311c-2878-45da-964b-13e92587f080): the form asks plain questions ("What kind of leave is this?", "When will you be away?") and shows the available balance inside the form. Borrow the questions as labels. Leave the hours field unless an organisation's leave is counted in hours.

**Administrator: staff list and staff record**

- [Workable: Employee profile (web)](https://mobbin.com/flows/727da974-5836-4df2-a05e-0c37d76b9bc0): the directory has search, status and department filters, a sort and a count; the record header carries name, job title, department and email, with tabs for Information, Files and Time off. Borrow the directory controls and the header. Leave the decorative banner and the letter grouping.
- [Remote: Employee profile (iPhone)](https://mobbin.com/flows/c60c7f26-c7d0-47ef-993c-571daf6304e4): on a phone the record is a header, a status badge, any waiting request with Approve and Decline, then labelled details. - [Aboard: People (web)](https://mobbin.com/flows/e920fb54-27f5-48c0-8b48-ce21a1fd5c9e): a searchable list on the left and the record on the right, so an administrator can step through people without going back. Borrow the list-beside-record layout on laptops. Leave the cover image and birthday tiles.

**Onboarding a new staff member**

## What could not be checked

- **Anything in a browser.** The app has no staging host and no dev script, and this audit was told not to start one. Nothing was seen rendered: no phone or laptop width, no screenshots, no real spacing, wrapping or colour. Every layout finding is argued from class names and should be confirmed on screen before it is fixed.
- **A real phone**, for the same reason: tap feel, the browser bar and safe areas.
- **Screen readers and the keyboard route:** reasoned from the markup only.
- **Contrast:** worked out from token values (ink, grey and navy on white pass; white on the green badge is 4.81 and passes at 12 pixels), not measured on screen.
- **Real data:** how many staff an organisation has, how long real names, job titles and grade names are, and which leave types exist were not looked up. The worst cases are argued from the schemas (for example, no length limit was found on a person's name in `StaffSetup`).
- **Sign-in:** the hand-off to the Barrels sign-in app was read only as far as this app's two screens; the sign-in app has its own audit ([auth-2026-11.md](auth-2026-11.md)).
- **The staff record after merge:** pull request 1760 was read at its current head and may change before it lands.
- **Screens that do not exist yet:** requesting leave, approvals, roster, timesheets, documents, setup and onboarding are still in `apps/web/gaa-admin`. They are covered here only by the proposed rules and the references, not by findings.
