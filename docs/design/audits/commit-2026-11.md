# Design audit: Commit, the Barrels engineering blog (2026-11)

**Status:** Phase 1 audit, read only. Nothing was changed in the app; every fix below is a proposal for the owner.  
**Owner:** Barrels Grenada engineering (design mastery programme, issue #1453)  
**Last updated:** 2026-11-23

## Scope and method

Surfaces audited, all in `apps/web/commit` (commit.barrels.gd, a static Next.js export on Cloudflare Pages): the single page that lists every post, the post layout and typography, the theme toggle, the feed, and the not-found page.

The rule for judging: a gap against the lane spec ([`docs/design/commit.md`](../commit.md)) or a design skill rule. The questions asked: is a release post comfortable to read on a phone and on a laptop, and can someone find, link to and share one release?

Method:

1. Read the root and app `AGENTS.md`, the lane spec and the section "Reviewing or polishing UI: check these before reporting a gap". Skipped what is in issue 1688 or fixed by pull request 1732, which already enlarged the tap area of the date link, the icon links and the post header on Commit.
2. Checked where styles live. `src/styles/tailwind.css` imports the shared `app-feel.css`, so tap flash, `touch-action` on controls and the reduced-motion override for CSS animation are already in place; the star twinkle is CSS, so it is covered. Post text uses `src/styles/typography.css`.
3. Read the layout, intro, post article, theme toggle, star field, feed code, the lane spec and the post files, then applied web-design-guidelines, fixing-accessibility, refactoring-ui, mobile-native, emil-design-eng, break-ui (long titles, long code lines, 14 posts) and the motion skills (review-animations, find-animation-opportunities).
4. Looked at the live production site (read only) with a scripted browser at 390 pixels (touch emulation) and 1280 pixels, in light and dark colour preference, on the home page and a missing page. At 390 pixels the page is about 34,800 pixels tall.
5. Compared with two saved reference screens (see Inspiration).

How to read a finding: **Size** S is under half a day, M about a day, L several days or needs a decision. **INVISIBLE** means readers would not see a difference in normal use; **VISIBLE** means layout, colour or wording changes, so the owner reviews it first.

## What is already strong

- **The look is distinctive and calm.** Dark sidebar with a sky glow and a still-until-needed star field, a light or dark reading column with a theme toggle (lane spec).
- **Reading width and type are good.** The post column is capped at about 36 rem (`max-w-xl`), with generous spacing, and code blocks scroll sideways inside their own box instead of widening the page (`overflow-x: auto` on `pre`).
- **Motion is restrained.** Only the star twinkle moves, in CSS, and it stops for people who ask for reduced motion (lane spec and `app-feel.css`).
- **Release badge and date on every post**, with the anchor name equal to the file name, so addresses are stable (`/#v1-6-0`).
- **A real feed.** RSS is advertised in the page head and linked from the intro; each item has a title with the release number and a summary.
- **Static and light.** No forms, no analytics, no scripts beyond the theme toggle, and no horizontal scroll at 390 pixels.

## Findings

### Blocking

#### 1. The list is missing the most recent releases, which breaks the "one post per release" promise

- **Where:** `apps/web/commit/content/posts/`. The newest post is `v1-6-0.mdx` (21 November); there is no post for 1.5.0 (the notes file exists locally but was never turned into a post) and none for the live 1.7.0. The posts present are 1.0.0 to 1.0.8, 1.1.0, 1.2.0, 1.3.0, 1.4.0 and 1.6.0.
- **What happens:** the owner's rule is one post per release and release notes ship with every release. A reader of commit.barrels.gd sees a gap at 1.5.0 and a platform that looks one version behind.
- **Rule or reference:** owner rule (Commit is one post per release).
- **Suggested fix:** write the missing posts from the existing release notes, in the app's own voice, owner edited. Content work, not design. Size M. VISIBLE.

### Should fix

#### 2. There is no way to find or jump to a release: the page is one 34,800 pixel scroll

- **Where:** `src/app/page.tsx` renders every post in full; `src/components/intro.tsx` has only three links (Documentation, Releases, RSS).
- **What happens:** at 390 pixels the sidebar sits above the posts and scrolls away; after the first post a reader has no list of releases, no "jump to 1.2.0" and no search. On a laptop the sidebar is fixed but holds no list either. Today there are 14 posts; each release will add more.
- **Rule or reference:** web-design-guidelines (long pages need landmarks); Productboard and n8n (see Inspiration) both keep a list of releases beside the content. Fixing-accessibility: provide a way to bypass blocks of repeated content.
- **Suggested fix:** keep the single page (it is the template's design and one post per release stays), but add a "Releases" list to the intro: version number and date, each linking to its anchor, a closed disclosure on a phone and always open in the desktop sidebar. Also show only the newest few posts in full if page weight grows. Size M. VISIBLE.

#### 3. Every release shares one address and one share preview

- **Where:** `src/app/layout.tsx` metadata (one title, one description, `openGraph` with only a site name); posts have no page of their own, so the feed and shares point at `/#v1-6-0`.
- **What happens:** a link to "release 1.6.0" in WhatsApp or Slack unfurls as the generic site card, no image, no release name (fragments never reach the server). The date link in a post is the only "copy the address" affordance and it is not labelled as a link to that release.
- **Rule or reference:** web-design-guidelines, Metadata (shareable pages); the owner's per-release address need.
- **Suggested fix:** two options for the owner. (a) Keep one page and add a share image and a better site description (S, VISIBLE only in shares). (b) Generate one small static page per release (`/v1-6-0/`) that shows the same post with its own title, description and share image and links back to the list; the anchor address keeps working with a redirect or a script. (b) keeps "one post per release" and makes each release linkable; it needs an owner decision because `AGENTS.md` for the app says the file name is the anchor and the feed link. Size M for (a), L for (b).

#### 4. Post headers are quiet but the title link and the date link are indistinguishable from text

- **Where:** `src/components/post-article.tsx`. The title is an `<a href="#slug">` styled by `.typography` without an underline or a pointer cue; the date is a second link to the same address, hidden at large widths and repeated in the sidebar position.
- **Rule or reference:** refactoring-ui (links should look like links); web-design-guidelines.
- **Why it matters:** a reader cannot tell the title is the way to copy a stable address. Two links to the same place also give screen reader users a duplicate.
- **Suggested fix:** show a small "#" or link icon on hover and focus beside the title, and give the date link a visually hidden "link to this release" suffix or a single link only. Size S. VISIBLE for the cue, INVISIBLE for the screen reader fix.

#### 5. Light-mode reading on a phone starts in the dark sidebar and long scrolls give no sense of place

- **Where:** `site-layout.tsx` (sidebar glow is always dark), `theme-toggle.tsx` (fixed at the top right, fill white on mobile).
- **What happens:** on a phone the first screen is the dark intro even for a light reader, then the page turns white, which is a hard flip; the theme toggle sits over the intro and scrolls away, so a reader deep in a post cannot change theme. In dark mode, the 14 posts are one unbroken dark column with a thin date rail.
- **Suggested fix:** keep the design, but make the toggle fixed with 44 pixel padding (it already has `-m-2.5 p-2.5`) and a pressed state, and add a small "Back to top" or release list button that appears after the intro. Size S to M. VISIBLE.

#### 6. The theme toggle has no visible state

- **Where:** `src/components/theme-toggle.tsx`. A half-filled circle icon at 50% opacity; the name says "Switch to dark theme" but nothing says which theme is active and there is no pressed state (the shared `app-feel.css` turns off the tap flash, so a tap gives no feedback until the theme changes).
- **Rule or reference:** emil-design-eng (every pressable thing needs a pressed state); fixing-accessibility (state is conveyed).
- **Suggested fix:** add an `:active` scale or full-opacity state and a focus ring with a clear contrast on both the dark sidebar and the white page. Size S. VISIBLE (small).

### Nice to have

#### 7. Not-found and loading cases

The not-found page is dark only, ignoring the reader's theme and offering one link ("Go back home"). It could link to the newest release and the feed. Size S. VISIBLE.

#### 8. Release text structure

Release posts are long lists (the 1.6.0 post has Events, Bookings and other sections as bold bullet lists). A one-sentence "At a glance" with the biggest change, then the sections, would help a skimming reader; this is content structure the owner edits. Size S. VISIBLE.

#### 9. The feed could carry more

The RSS item has the summary only; adding the full text helps feed readers (`src/lib/feed.ts`). Size S. INVISIBLE.

#### 10. Long unbroken words

Post titles and table cells are free text; `overflow-wrap: anywhere` is not set on `.typography` headings and table cells, so a very long identifier (a route path in a title) could push the column wider than the phone. No current post breaks it (break-ui, argued from the stylesheet). Size S. INVISIBLE.

## Inspiration

Ideas only; nothing here is to be copied.

- [Productboard, Releases list](https://mobbin.com/screens/5d055c4b-a5cf-4113-9246-bb879a4004a6): releases grouped under a plain heading with a collapsible tree and a date column. Borrow the idea of a compact release index with dates for the sidebar. Do not borrow the dense table, which is for managing releases, not reading them.
- [n8n, summary of changes](https://mobbin.com/screens/b8ca5b32-8de2-4e44-903e-f7d1428ada72): a short numbered "what was wrong and what I changed" summary above the detail. Borrow the pattern of a short numbered summary at the top of each release post (finding 8). Do not borrow the chat framing.

(Mobbin's saved screens did not include a classic changelog page, so these are the nearest matches.)

## What could not be checked

- **A real phone.** Tap flash, the toggle feel and the browser bar were argued from the stylesheets and seen only in an emulated phone viewport.
- **Measured tap targets.** A scripted measurement was queued behind other agents' work on the shared heavy-job slot and stopped, so sizes come from the code (the date link is `min-h-11`, the logo link `min-h-11`, the toggle about 44 pixels with its margin trick).
- **Reading contrast.** Body and code colours in `typography.css` were judged by eye and from the Tailwind grey and sky scales; no contrast tool was run.
- **A screen reader and the full keyboard route.** Reasoned from the markup.
- **The RSS feed in a reader.** Read from code only.
- **A staging site.** None exists for Commit (production only), so only production was seen.
