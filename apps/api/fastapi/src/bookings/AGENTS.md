# bookings domain — agent context

**Owner:** Barrels platform (Barrels Bookings; [ADR-0024](../../../../../docs/adr/0024-bookings-domain.md); plan: B-series in `docs/exec-plans/barrels-foundations-plan.md`). A shared capability for every app and client site, not a GAA/GMS module. Pilot tenant: Babydoll Beauty Bar.

**Clean-room rule:** the model follows Easy!Appointments' concepts (services, providers, weekly working plans, exceptions). It is GPL-3: never copy its code, schema files or text.

**Frontend-agnostic (owner rule):** this is an HTTP/JSON API for any client (web, mobile, kiosk, bot). Times are naive UTC in the database and `Z` UTC on the wire, with the profile's IANA `timezone` for display; money is minor units plus `currency`. No HTML, no framework assumptions, no hard-coded site URLs: links to a business's own pages come from profile settings (`manage_url_template` with `{token}`). Public endpoints are keyed by `public_slug`, never by origin.

- **Tables** (`bookings` schema, main database, migration `bookings20261019`, `bookings` in `TRACKED_SCHEMAS` (`src/model_registry.py`)): `profile` (one per organisation), `service`, `provider`, `provider_service`, `working_hours`, `availability_exception`, `customer`, `booking`, `booking_event`. Every row is scoped by `organisation_id` (directly or through its provider/booking).
- **No double-booking:** `booking.blocked_from/blocked_until` store the range a booking holds (buffers included); the `booking_no_overlap` exclusion constraint (`btree_gist`, active statuses `pending_payment|pending|confirmed`) rejects overlaps per provider. `service.is_overlap_violation(error)` recognises it (and Postgres' `40P01` deadlock, which is how two racing inserts for one provider can end): map it to 409 or try the next provider.
- **Availability** (`availability.py`) is pure and tested without a database: weekly periods (gaps are breaks), `extra_hours` adds, `time_off` removes, slots on the step grid from local midnight, the service must fit one window, blocked ranges must not overlap, lead time and horizon apply. `service.available_slots` loads rows and calls it; keep business rules in the pure module.
- **Organisation routes** (`/bookings/org/*`, the business's staff; a client site may call its UI "studio") use `OrgContext`: `OrgMember` reads, `OrgAdmin` writes. Another organisation's ids answer 404. **Public routes** (`/bookings/public/{slug}`, `/availability`) need no sign-in, are rate limited, and answer the same 404 for unknown and disabled profiles; availability spans at most 14 days.
- Schema and enum names are prefixed `Booking*` so OpenAPI never renames a clashing name (Events already owns `ProfilePublic`).
- Routers commit; services flush.

- Organisation routes (`/bookings/org/*`) require the `bookings` entitlement (`require_org_app`, PF1); the B4 tenant seed must grant it. Tests use `make_org(..., apps=("bookings",))`.

## App session on organisation routes (ADR-0016 amendment)
- The bookings app's own session (an access token with `app = "bookings"`) is accepted on every `/bookings/org/*` route: four aliases in `router.py` (`BookingsOrgMember`, `BookingsOrgAdmin`, `BookingsOrgRead`, `BookingsOrgWrite`) and two in `settings.py` (`_Read`, `_Write`), all with `session_app="bookings"`. The caller must hold `app.bookings.access` and an active membership in the header organisation (`X-Barrels-Organisation`); role, suspension and the `bookings` entitlement checks are unchanged, other apps' tokens are 401, and an API key (`bk_`) still works on the `org_or_key` routes.
- `GET /bookings/me/organisations` (zone `me`, `list_my_organisations`, response `BookingMyOrganisation`: `id`, `name`, `slug`, `role`) feeds the studio organisation picker. It takes an account or the bookings app session (via `resolve_org_caller`, no organisation header, no API key), lists the caller's active memberships in active organisations entitled to `bookings`. Another user's organisations never appear.
- New organisation routes in this domain must use the same aliases (or `session_app="bookings"` on a new one); do not add a second way to accept app tokens.

## B3: public create, manage, cancel, reschedule (built on PF2, ADR-0026)
Logic is in `public.py` (service.py keeps studio config and availability); routes are in `router.py`.
- `POST /bookings/public/{slug}/bookings`: needs an `Idempotency-Key` header (400 without), runs through `idempotency.run_idempotent` (scope `bookings.create`; same key and body replays with `Idempotency-Replayed: true`, same key with another body is 409; the hash leaves out `turnstile_token` and `website`). Order: profile and `bookings` entitlement (404 for unknown, disabled or unentitled) then Turnstile (`public.turnstile_policy`: the organisation's public site named like the slug, else its only site, else the global setting) then the honeypot `website` (a filled one gets a decoy 201 and nothing is stored) then the idempotent handler. The handler re-runs `service.available_slots` inside the transaction, picks the first free provider (or the named one), inserts inside a savepoint and treats `is_overlap_violation` as "try the next provider, else 409". Status is `pending` when `profile.requires_confirmation`, else `confirmed`. Customers are upserted by `hash_email`.
- **Manage token:** `secrets.token_urlsafe(32)`; only its SHA-256 is in `booking.manage_token_hash`. The plaintext is in the 201 body and therefore in the idempotency row for 24 hours (purged by retention), and in the creation email's outbox payload until the row is done. Never log or persist it elsewhere. Retention clears `manage_token_hash` 90 days after the booking ends.
- **Signed manage links (owner decision 21 Nov 2026):** every later mail carries a link minted when the mail is built (`manage_link.py`, see the section below). The booking stores nothing for it.
- Manage routes `/bookings/public/bookings/{token}` (`GET`), `/cancel`, `/reschedule`, `/ics`: unknown, expired, tampered, cleared and unentitled tokens answer one 404. `public.load_by_token` treats a token with a dot as a signed link, any other as the legacy token (its hash). Reschedule mails and the `booking.rescheduled` webhook are keyed to the move's own `BookingEvent` id (`record_event` returns it), so moving 10:00 to 11:00 and back notifies every time. Cancel and reschedule honour `profile.cancel_cutoff_hours` (409 inside it); a repeated cancel is a no-op; reschedule keeps provider, service, status and token, re-validates availability with `exclude_booking_id`, and writes a `BookingEvent` with equal from/to status. The slug `bookings` is reserved.
- **Status machine:** `transitions.py` table; `public.transition` is the only place that changes status and it writes a `BookingEvent`. Studio actions (B5) must use it.
- **Emails:** `emails.py` (pure) builds an `EmailCard` (`src/email_layout.py`, house style in `docs/email-design.md`); `public.py` queues `to_props(card)` as template `card` with `notifications.outbox_handlers.enqueue_email` (topic `email.send`, dedupe keys `booking-<kind>:<id>`), rendered at delivery. `reminders.enqueue_due_reminders` (job `enqueue_booking_reminders`, hourly at :07) queues `booking-reminder:<id>` once per booking for confirmed and `pending` bookings starting within 24 hours; a pending booking's mail says the business has not confirmed it yet. Every mail goes through `public.build_mail`. **Manage links:** create (legacy token), confirmed, deposit paid, reminder and both reschedules carry one; cancellation mails (customer, studio, decline) carry none, though a cancelled booking still opens read-only.
- **ICS:** `ics.py` is a pure RFC 5545 writer (CRLF, 75-octet folding, escaping, UTC, `STATUS`, `SEQUENCE` = history length - 1).
- Deposits (`pending_payment`) are wired: see B6 below.

## Wiring (PF3, PF5, PF8)
- **API keys:** the `/bookings/org/*` GET routes (`BookingsOrgRead`) accept a member or an API key with `bookings.read` (`organisations.api_key_auth.org_or_key`); the B5 studio action routes use `org_or_key("bookings", "bookings.write", MembershipRole.ADMIN)` (`BookingsOrgWrite`) and pass `actor_id` (None for a key) to `public.transition`.
- **Contacts (party/role, ADR-0028, migration `bookingspartyrole20261021`):** `bookings.customer` keeps only booking facts (`id`, `organisation_id`, `created_at`, `last_booked_at`) plus a required `contact_id` -> `org.contact.id` (no `SET NULL`). Name, email, phone and marketing consent exist only on the contact; views, mail and reminders join `Contact` (`Managed.contact`, `public.display_name`; an erased contact has no email so nothing is sent). Public create calls `contacts.service.upsert_contact(source="bookings", consents={marketing: marketing_consent})` for every organisation (no entitlement check at booking time; granting `bookings` also grants `contacts` via `entitlements.BUNDLED_WITH`, so the organisation gets the whole contact book: read for members; create, edit name/phone, record consent, merge and erase for admins and owners), then `public.customer_for_contact` finds or creates the role (unique `(organisation_id, contact_id)`, insert-on-conflict so concurrent first bookings share one row; a contact merge folds two customers into one and moves the bookings). A returning contact keeps its curated name. A contact merge re-points customers through `contacts.references` (this table is registered in `models.py`); erasure blanks the contact in place and bookings keep working. Existing unlinked customers were deleted by the migration (nothing was live).
- **Rewards:** `public.transition` to `completed` calls `rewards.service.emit_qualifying_action` (`bookings.completed`, source id = booking id) when the customer's contact is live and has a `user_id`; otherwise nothing is queued. Tests: `tests/bookings/test_wiring.py`, `test_wiring_migration.py`.
- **Account link (ADR-0058 slice 1):** `public.create_booking` passes the optional signed-in `payer` into `_create_booking`, which calls `contacts.service.link_verified_account` right after the contact upsert. The contact gets `user_id` only when the payer's email is verified (`is_email_verified`, not admin activation) and equals the booking email (normalised). Name and phone never link; a contact already linked to any account is left alone. Guest bookings are unchanged. Completion then earns through the rewards outbox above.
- **Prefill for a signed-in booker:** `GET /bookings/me/businesses/{slug}/choices` (`get_my_choices`, `StudioCaller`, `BookingMyChoices`: `phone`, `recent`) reads only bookings whose contact in that business is linked to the caller. `recent` is the latest booking per service (DISTINCT ON), at most three, newest first, with the last provider; only `pending`, `confirmed` and `completed` count (`SUGGESTED_STATUSES`). `phone` is the most recently booked linked contact's number, else `user.phone_e164`. Unknown or disabled slug is the public 404. Tests: `tests/bookings/test_my_choices.py`.
- **Account invitation:** the received, confirmed and reminder mails end with an invitation to create an account or sign in (`BookingEmail.account_invite_url`, set by `public.build_mail` only while the contact has no `user_id`, from `account_signup_url(slug)`: auth `/signup?returnTo=<BOOKINGS_APP_URL>/signin?returnTo=/<slug>`; `AUTH_FRONTEND_URL` must name the web apps' `AUTH_APP_URL`, checked in the test). The manage page shows the same step from `BookingPublicDetail.account_invite_url` (null once linked). Booking never needs an account. Do not promise automatic linking: a guest booking is not linked when made and there is no claim flow; once the person has an account with the same verified email and books with the business again while signed in, the contact links and `GET /bookings/me/bookings` lists the earlier guest bookings too (`tests/bookings/test_account_invite.py`). Cancellations and moves carry no invitation.
- **My bookings (ADR-0058 slice 1):** `GET /bookings/me/bookings` (zone `me`, `list_my_bookings`, `OwnAccountAnyUser`; customers awaiting approval allowed, no privileged-MFA gate; full account token or the account app's session (`OWN_ACCOUNT_APPS`), other apps' tokens 401) lists bookings whose customer's contact is linked to the caller. Owner decision (14 Nov 2026): a guest booking made with an already-linked person's email also appears there; accepted, not a defect. Filter, count and page in SQL: `upcoming` true is soonest first (`starts_at`, `id` ascending), otherwise newest first; `cancelled` true or false filters it. Rows add a signed `manage_url`. Tests: `tests/bookings/test_account_link.py`.

## B5: studio actions (`studio.py`)
- Routes (org zone): `GET /bookings/org/bookings/{id}` (customer name/phone/email, `BookingEvent` history, deposit intent id and captured/refunded amounts), `GET /bookings/org/agenda` (`from_date`..`to_date` local days inclusive, at most 62, else 422; optional `provider_id`, repeated `status`; `limit` <= 500 and `offset` page in SQL, grouped by local day in Python), `POST .../confirm|decline|cancel|no-show|complete`. Reads accept `bookings.read`, writes `bookings.write` or an admin member. Another organisation's id is 404; an illegal move is 409 (`BookingConflictError`).
- Every move is `public.transition` (`actor_user_id` None for a key). Confirm only from `pending` (a `pending_payment` booking answers 409 "waiting for its deposit"); decline only from `pending` and needs a `reason`; cancel needs a `reason`. Decline and cancel emit `booking.cancelled` and queue one customer email (`booking-declined:<id>`, `booking-cancelled-by-studio:<id>`; `emails.customer_declined`, `customer_cancelled_by_studio`). Confirm queues `booking-confirmed:<id>` (`emails.customer_confirmed`) and emits no webhook. Completion keeps the rewards action inside `transition`.
- **Staff reschedule** (`studio.reschedule`, `POST /bookings/org/bookings/{id}/reschedule`, `BookingStudioReschedule`: `starts_at`, `BookingsOrgWrite`): moves a `pending` or `confirmed` booking (409 for any other status) to a new start with the same provider and service; no body field for provider or notify, the customer is always emailed (`booking-rescheduled-by-studio:<booking id>:<history row id>`, `emails.customer_rescheduled_by_studio`, with a signed manage link and no invitation; a pending booking's mail also says the business has not confirmed it yet). The mail key and the webhook event id (`booking.rescheduled:<booking id>:<history row id>`) use the move's own `BookingEvent` id (`public.record_event` returns it), so moving 10:00 to 11:00 and back to 10:00 notifies three times; keys built from the new start time would swallow the third (the customer's own reschedule still keys on the start time). Like staff create it skips the availability engine (hours, lead time and horizon do not apply); the new time must be in the future and on a whole minute, no seconds (422) and `booking_no_overlap` still answers 409 on a clash. The same time again is a no-op (no event, no mail). Status, manage token and deposit stay. Writes a `BookingEvent` with equal from/to status (note "Rescheduled from ... by the business", `actor_user_id` None for a key) and a `booking.rescheduled` webhook. The move itself is `public.move_booking`, shared with the customer's reschedule. Tests: `tests/bookings/test_staff_reschedule.py`.
- `public.build_mail`, `queue_customer_email`, `queue_studio_email`, `emit_webhook`, `load_by_id` are the shared helpers (public, not underscore, so `studio.py` and `deposits.py` can use them).

- **Staff create** (`studio.create_booking`, `POST /bookings/org/bookings`, scope `bookings.studio-create`, `Idempotency-Key` required): phone, walk-in and re-entered appointments. Source `studio`, status `confirmed`, no deposit. It does not call the availability engine, so lead time, horizon and weekly hours do not apply; the provider must be active, belong to the organisation and offer the service, and `booking_no_overlap` still gives 409. The contact is reused by email hash; without an email each entry is a new contact with no address (`contacts.service.create_without_email`). The customer is emailed (`booking-confirmation:<id>`, with the legacy manage link) only when `send_confirmation` is true. History note "Entered by the business", `actor_user_id` None for a key. Staff never record marketing consent (`consents=None`). Tests: `tests/bookings/test_studio_create.py`.

## B6: deposits (`deposit_payments.py`, `deposits.py`, `outbox_handlers.py`, `config.py`)
- At create, `deposit_payments.effective_deposit` copies `service.deposit_minor` into `booking.deposit_minor` only when the organisation holds the `payments` entitlement (else no deposit, one INFO log, the booking still succeeds). A deposit booking starts `pending_payment` (the exclusion constraint holds the slot) and no email is queued yet. `start_deposit` calls `payments.service.create_intent` with `source_type="bookings.deposit"`, `source_id=<booking id>`, key `bookings.deposit:<booking id>`, `actor=None` (created_by NULL). Provider: `stripe` when `PAYMENTS_STRIPE_SECRET_KEY` is an `sk_test_` key (a Stripe failure falls back), else `manual` (`checkout_url` null; the studio records the payment through `POST /payments/org/intents/{id}/manual-payments`). The receipt carries `payment_required` and `checkout_url`.
- Payment received: payments enqueues outbox topic `bookings.deposit_paid` in the charge transaction; `outbox_handlers.deposit_paid` -> `deposits.confirm_paid` moves `pending_payment` to `confirmed` (or `pending` when `requires_confirmation`), queues `booking-confirmation:<id>` (with a signed manage link) and `booking-studio-created:<id>`. A replay finds the booking moved and does nothing. A payment that lands after the hold expired (booking already cancelled) is refunded in full.
- Expiry: ARQ job `expire_unpaid_bookings` (every 5 minutes, `deposits.expire_unpaid`) cancels `pending_payment` bookings older than `BOOKINGS_DEPOSIT_HOLD_MINUTES` (default 30), cancels the open intent and emits `booking.cancelled`; a booking whose payment just succeeded is skipped.
- Refund policy (`settle_cancellation`): cancelling an unpaid deposit booking cancels its intent. Cancelling a paid booking refunds the deposit when it starts at least `cancel_cutoff_hours` away, keeps it inside the cutoff (history note "Deposit kept"); studio cancel can override with `refund_deposit`, decline always refunds, customer cancel is always before the cutoff so it refunds. A failed refund never undoes the cancel (note "Deposit refund failed; refund it by hand").
- No migration: the intent is found by `(source_type, source_id)`.
- **Manual deposit (`studio.record_manual_deposit`):** `POST /bookings/org/bookings/{id}/manual-deposit` (`BookingManualDepositCreate`: method cash|bank_transfer|cheque, reference) records a deposit taken outside Stripe through `payments.service.record_manual_payment`, so the ledger, the `bookings.deposit_paid` topic and `deposit_captured_minor` follow from one charge (a `pending_payment` booking is confirmed by the handler). Owner/admin session only (`BookingsOrgAdmin`, no API key), `payments` entitlement, required `Idempotency-Key` (scope `bookings.manual-deposit`). The booking row is locked; the intent is resolved by the booking's own key (`deposit_payments.intent_key`) and must carry source `bookings.deposit` and this booking's id, match the deposit amount and currency and be a manual intent (an open Stripe intent is 409 until it expires). 409 for no deposit, a closed booking, an already-paid deposit, or an intent that failed or was cancelled (the customer needs to book again). Writes audit action `manual_deposit` (the reference is sensitive) and a `BookingEvent` note. Tests: `test_manual_deposit.py`.

## Take payment at booking (Stripe test mode, #1372, owner decision 15 Nov 2026)
- Profile column `payment_at_booking` (migration `bookingpayment20261115`, `BookingPaymentMode`): `deposit` (default; each service's own deposit, the B6 behaviour, so nothing changes for existing profiles) or `full_price`. A PUT that leaves it out keeps the stored value (`service.KEPT_UNLESS_NAMED`, like the contact options).
- `deposit_payments.amount_due` is the one rule: `full_price` charges `service.price_minor` only while `stripe_available()` (a `PAYMENTS_STRIPE_SECRET_KEY` that starts `sk_test_`) and the organisation holds `payments`; otherwise the service deposit rule applies (`effective_deposit`). With no Stripe keys nothing changes for anyone. The amount is stored in `booking.deposit_minor` (it means "paid at booking"), so the hold, expiry sweeper, emailed-code step, refund policy and studio screens all apply unchanged. A free service (price 0) is never charged.
- The storefront gives each service `due_at_booking_minor` (`deposit_payments.due_by_service`, one entitlement query); the booking flow asks for the emailed code when it is above 0. `GET /bookings/org/settings` adds `card_payments_available`.
- Checkout line: `deposit_payments.checkout_title` ("Payment: <service>, <business>" or "Deposit: ..."). Stripe returns the customer to `<BOOKINGS_APP_URL>/checkout/return?booking=<id>&result=paid|cancelled` (a `payments.return_urls` builder registered for `bookings.deposit`, built from settings and the booking id only; no manage token or personal data goes to Stripe). The bookings app's return page reads the manage path that the tab saved before leaving (sessionStorage) and goes on to the manage page.
- `BookingPublicDetail.payment` (`BookingPaymentSummary`, `deposit_payments.payment_summary`, null when nothing was due): `due` (slot held; `checkout_url` from the intent while it is an open Stripe checkout, so the customer can return to pay), `paid` (with any partial refund), `refunded`, `unpaid` (closed without payment). Every manage route answers with it (`public.full_detail`).
- Confirmation still comes only from the signed webhook (`checkout.session.completed` -> ledger charge -> outbox `bookings.deposit_paid` -> `deposits.confirm_paid`), idempotent by the ledger key and the outbox dedupe key.
- Not built yet: setting the Stripe Checkout `expires_at` to the hold; per-business merchant accounts (Connect, ADR-0027); live mode. Tests: `tests/bookings/test_payment_at_booking.py`.

## Signed manage links (`manage_link.py`, owner decision 21 Nov 2026)
- **Why:** only the token's hash is stored, so later mails cannot repeat it; storing it encrypted would keep the key beside the data. A signed link is minted on demand with nothing stored: `v1.<booking id hex>.<expires, Unix seconds>.<tag>`, where the tag is the first 16 bytes of HMAC-SHA256 over `manage|v1|<id>|<expires>` (URL-safe base64, no padding; about 70 characters).
- **Key:** HKDF-SHA256 (RFC 5869) of `SECRET_KEY` with the info string `bookings-manage-link-v1`. Worker and API share `SECRET_KEY` (deploy compose), so a link minted by the reminder job verifies in the API. Rotating `SECRET_KEY` ends outstanding signed links (legacy tokens are unaffected). A new key version gets a new info string, and the old one keeps verifying until retired. Local development: `SECRET_KEY` is random per process unless set, so set it to test links minted by the worker.
- **Lifetime and revocation:** a link expires at the booking's end plus 7 days (`GRACE`; shortened from 30 for privacy, 21 Nov 2026). A link minted before a move keeps the old end, and the mail after a move carries a new one. Clearing `manage_token_hash` (retention, 90 days after the end) revokes signed links too, because the route also needs the hash to be present. A cancelled or completed booking still opens read-only (status shown; cancel answers the usual no-op or 409), as with the legacy token.
- **Routing:** a token with a dot is verified and then loaded by its booking id; any other token is the legacy hash lookup. Both share the entitlement check and the single 404.
- **Logging:** a link appears only in outbox payloads and HTML, never in a log line (`test_no_manage_link_or_token_reaches_the_logs`). Do not add logging of mail bodies.
- **Tests:** `tests/bookings/test_manage_link.py` (pure) and `test_manage_links.py` (mail links, 404s, revocation, read-only, invitation, logs).
