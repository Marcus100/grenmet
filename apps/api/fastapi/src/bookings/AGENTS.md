# bookings domain — agent context

**Owner:** Barrels platform (Barrels Bookings; [ADR-0024](../../../../../docs/adr/0024-bookings-domain.md); plan: B-series in `docs/exec-plans/barrels-foundations-plan.md`). A shared capability for every app and client site, not a GAA/GMS module. Pilot tenant: Babydoll Beauty Bar.

**Clean-room rule:** the model follows Easy!Appointments' concepts (services, providers, weekly working plans, exceptions). It is GPL-3: never copy its code, schema files or text.

**Frontend-agnostic (owner rule):** this is an HTTP/JSON API for any client (web, mobile, kiosk, bot). Times are naive UTC in the database and `Z` UTC on the wire, with the profile's IANA `timezone` for display; money is minor units plus `currency`. No HTML, no framework assumptions, no hard-coded site URLs: links to a business's own pages come from profile settings (`manage_url_template` with `{token}`). Public endpoints are keyed by `public_slug`, never by origin.

- **Tables** (`bookings` schema, main database, migration `bookings20261019`, `bookings` in `_TRACKED_SCHEMAS`): `profile` (one per organisation), `service`, `provider`, `provider_service`, `working_hours`, `availability_exception`, `customer`, `booking`, `booking_event`. Every row is scoped by `organisation_id` (directly or through its provider/booking).
- **No double-booking:** `booking.blocked_from/blocked_until` store the range a booking holds (buffers included); the `booking_no_overlap` exclusion constraint (`btree_gist`, active statuses `pending_payment|pending|confirmed`) rejects overlaps per provider. `service.is_overlap_violation(error)` recognises it (and Postgres' `40P01` deadlock, which is how two racing inserts for one provider can end): map it to 409 or try the next provider.
- **Availability** (`availability.py`) is pure and tested without a database: weekly periods (gaps are breaks), `extra_hours` adds, `time_off` removes, slots on the step grid from local midnight, the service must fit one window, blocked ranges must not overlap, lead time and horizon apply. `service.available_slots` loads rows and calls it; keep business rules in the pure module.
- **Organisation routes** (`/bookings/org/*`, the business's staff; a client site may call its UI "studio") use `OrgContext`: `OrgMember` reads, `OrgAdmin` writes. Another organisation's ids answer 404. **Public routes** (`/bookings/public/{slug}`, `/availability`) need no sign-in, are rate limited, and answer the same 404 for unknown and disabled profiles; availability spans at most 14 days.
- Schema and enum names are prefixed `Booking*` so OpenAPI never renames a clashing name (Events already owns `ProfilePublic`).
- Routers commit; service functions flush.

- Organisation routes (`/bookings/org/*`) require the `bookings` entitlement (`require_org_app`, PF1); the B4 tenant seed must grant it. Tests use `make_org(..., apps=("bookings",))`.

## App session on organisation routes (ADR-0016 amendment)
- The bookings app's own session (an access token with `app = "bookings"`) is accepted on every `/bookings/org/*` route: four aliases in `router.py` (`BookingsOrgMember`, `BookingsOrgAdmin`, `BookingsOrgRead`, `BookingsOrgWrite`) and two in `settings.py` (`_Read`, `_Write`), all with `session_app="bookings"`. The caller must hold `app.bookings.access` and an active membership in the header organisation (`X-Barrels-Organisation`); role, suspension and the `bookings` entitlement checks are unchanged, other apps' tokens are 401, and an API key (`bk_`) still works on the `org_or_key` routes.
- `GET /bookings/me/organisations` (zone `me`, `list_my_organisations`, response `BookingMyOrganisation`: `id`, `name`, `slug`, `role`) feeds the studio organisation picker. It takes an account or the bookings app session (via `resolve_org_caller`, no organisation header, no API key), lists the caller's active memberships in active organisations entitled to `bookings`. Another user's organisations never appear.
- New organisation routes in this domain must use the same aliases (or `session_app="bookings"` on a new one); do not add a second way to accept app tokens.

## B3: public create, manage, cancel, reschedule (built on PF2, ADR-0026)
Logic is in `public.py` (service.py keeps studio config and availability); routes are in `router.py`.
- `POST /bookings/public/{slug}/bookings`: needs an `Idempotency-Key` header (400 without), runs through `idempotency.run_idempotent` (scope `bookings.create`; same key and body replays with `Idempotency-Replayed: true`, same key with another body is 409; the hash leaves out `turnstile_token` and `website`). Order: profile and `bookings` entitlement (404 for unknown, disabled or unentitled) then Turnstile (`public.turnstile_policy`: the organisation's public site named like the slug, else its only site, else the global setting) then the honeypot `website` (a filled one gets a decoy 201 and nothing is stored) then the idempotent handler. The handler re-runs `service.available_slots` inside the transaction, picks the first free provider (or the named one), inserts inside a savepoint and treats `is_overlap_violation` as "try the next provider, else 409". Status is `pending` when `profile.requires_confirmation`, else `confirmed`. Customers are upserted by `hash_email`.
- **Manage token:** `secrets.token_urlsafe(32)`; only its SHA-256 is in `booking.manage_token_hash`. The plaintext is in the 201 body and therefore in the idempotency row for 24 hours (purged by retention), and in the confirmation email's outbox payload until the row is done. Never log or persist it elsewhere. Retention clears `manage_token_hash` 90 days after the booking ends.
- Manage routes `/bookings/public/bookings/{token}` (`GET`), `/cancel`, `/reschedule`, `/ics`: unknown, cleared and unentitled tokens answer one 404. Cancel and reschedule both honour `profile.cancel_cutoff_hours` (409 inside it); a repeated cancel is a no-op; reschedule keeps provider, service, status and token, re-validates availability with `exclude_booking_id` (the booking's own range does not block itself) and writes a `BookingEvent` with equal from/to status. The slug `bookings` is reserved so it cannot shadow the manage path.
- **Status machine:** `transitions.py` table; `public.transition` is the only place that changes status and it writes a `BookingEvent`. Studio actions (B5) must use it.
- **Emails:** `emails.py` (pure) builds subject and HTML; `public.py` queues them with `notifications.outbox_handlers.enqueue_email` (topic `email.send`, dedupe keys `booking-confirmation|studio-created|cancelled|studio-cancelled|rescheduled:<id>`...). `reminders.enqueue_due_reminders` (job `enqueue_booking_reminders`, hourly at :07) queues `booking-reminder:<id>` for confirmed bookings starting within 24 hours; it has no manage link (the token is only a hash).
- **ICS:** `ics.py` is a pure RFC 5545 writer (CRLF, 75-octet folding, escaping, UTC, `STATUS`, `SEQUENCE` = history length - 1).
- Deposits (`pending_payment`) are wired: see B6 below.

## Wiring (PF3, PF5, PF8)
- **API keys:** the `/bookings/org/*` GET routes (`BookingsOrgRead`) accept a member or an API key with `bookings.read` (`organisations.api_key_auth.org_or_key`); the B5 studio action routes use `org_or_key("bookings", "bookings.write", MembershipRole.ADMIN)` (`BookingsOrgWrite`) and pass `actor_id` (None for a key) to `public.transition`.
- **Contacts (party/role, ADR-0028, migration `bookingspartyrole20261021`):** `bookings.customer` keeps only booking facts (`id`, `organisation_id`, `created_at`, `last_booked_at`) plus a required `contact_id` -> `org.contact.id` (no `SET NULL`). Name, email, phone and marketing consent exist only on the contact; views, mail and reminders join `Contact` (`Managed.contact`, `public.display_name`; an erased contact has no email so nothing is sent). Public create calls `contacts.service.upsert_contact(source="bookings", consents={marketing: marketing_consent})` for every organisation (no entitlement check at booking time; granting `bookings` also grants `contacts` via `entitlements.BUNDLED_WITH`, so the organisation gets the whole contact book: read for members; create, edit name/phone, record consent, merge and erase for admins and owners), then `public.customer_for_contact` finds or creates the role (unique `(organisation_id, contact_id)`, insert-on-conflict so concurrent first bookings share one row; a contact merge folds two customers into one and moves the bookings). A returning contact keeps its curated name. A contact merge re-points customers through `contacts.references` (this table is registered in `models.py`); erasure blanks the contact in place and bookings keep working. Existing unlinked customers were deleted by the migration (nothing was live).
- **Rewards:** `public.transition` to `completed` calls `rewards.service.emit_qualifying_action` (`bookings.completed`, source id = booking id) when the customer's contact is live and has a `user_id`; otherwise nothing is queued. Tests: `tests/bookings/test_wiring.py`, `test_wiring_migration.py`.

## B5: studio actions (`studio.py`)
- Routes (org zone): `GET /bookings/org/bookings/{id}` (customer name/phone/email, `BookingEvent` history, deposit intent id and captured/refunded amounts), `GET /bookings/org/agenda` (`from_date`..`to_date` local days inclusive, at most 62, else 422; optional `provider_id`, repeated `status`; `limit` <= 500 and `offset` page in SQL, grouped by local day in Python), `POST .../confirm|decline|cancel|no-show|complete`. Reads accept `bookings.read`, writes `bookings.write` or an admin member. Another organisation's id is 404; an illegal move is 409 (`BookingConflictError`).
- Every move is `public.transition` (`actor_user_id` None for a key). Confirm only from `pending` (a `pending_payment` booking answers 409 "waiting for its deposit"); decline only from `pending` and needs a `reason`; cancel needs a `reason`. Decline and cancel emit `booking.cancelled` and queue one customer email (`booking-declined:<id>`, `booking-cancelled-by-studio:<id>`; `emails.customer_declined`, `customer_cancelled_by_studio`). Confirm queues `booking-confirmed:<id>` (`emails.customer_confirmed`) and emits no webhook. Completion keeps the rewards action inside `transition`.
- `public.build_mail`, `queue_customer_email`, `queue_studio_email`, `emit_webhook`, `load_by_id` are the shared helpers (public, not underscore, so `studio.py` and `deposits.py` can use them).

- **Staff create** (`studio.create_booking`, `POST /bookings/org/bookings`, scope `bookings.studio-create`, `Idempotency-Key` required): phone, walk-in and re-entered appointments. Source `studio`, status `confirmed`, no deposit. It does not call the availability engine, so lead time, horizon and weekly hours do not apply; the provider must be active, belong to the organisation and offer the service, and `booking_no_overlap` still gives 409. The contact is reused by email hash; without an email each entry is a new contact with no address (`contacts.service.create_without_email`). The customer is emailed (`booking-confirmation:<id>`, with a manage link) only when `send_confirmation` is true. History note "Entered by the business", `actor_user_id` None for a key. Staff never record marketing consent (`consents=None`). Tests: `tests/bookings/test_studio_create.py`.

## B6: deposits (`deposit_payments.py`, `deposits.py`, `outbox_handlers.py`, `config.py`)
- At create, `deposit_payments.effective_deposit` copies `service.deposit_minor` into `booking.deposit_minor` only when the organisation holds the `payments` entitlement (else no deposit, one INFO log, the booking still succeeds). A deposit booking starts `pending_payment` (the exclusion constraint holds the slot) and no email is queued yet. `start_deposit` calls `payments.service.create_intent` with `source_type="bookings.deposit"`, `source_id=<booking id>`, key `bookings.deposit:<booking id>`, `actor=None` (created_by NULL). Provider: `stripe` when `PAYMENTS_STRIPE_SECRET_KEY` is an `sk_test_` key (a Stripe failure falls back), else `manual` (`checkout_url` null; the studio records the payment through `POST /payments/org/intents/{id}/manual-payments`). The receipt carries `payment_required` and `checkout_url`.
- Payment received: payments enqueues outbox topic `bookings.deposit_paid` in the charge transaction; `outbox_handlers.deposit_paid` -> `deposits.confirm_paid` moves `pending_payment` to `confirmed` (or `pending` when `requires_confirmation`), queues `booking-confirmation:<id>` and `booking-studio-created:<id>` (no manage link: the token exists only as a hash). A replay finds the booking moved and does nothing. A payment that lands after the hold expired (booking already cancelled) is refunded in full.
- Expiry: ARQ job `expire_unpaid_bookings` (every 5 minutes, `deposits.expire_unpaid`) cancels `pending_payment` bookings older than `BOOKINGS_DEPOSIT_HOLD_MINUTES` (default 30), cancels the open intent and emits `booking.cancelled`; a booking whose payment just succeeded is skipped.
- Refund policy (`settle_cancellation`): cancelling an unpaid deposit booking cancels its intent. Cancelling a paid booking refunds the deposit when it starts at least `cancel_cutoff_hours` away, keeps it inside the cutoff (history note "Deposit kept"); studio cancel can override with `refund_deposit`, decline always refunds, customer cancel is always before the cutoff so it refunds. A failed refund never undoes the cancel (note "Deposit refund failed; refund it by hand").
- No migration: the intent is found by `(source_type, source_id)`.

## B4: Babydoll tenant seed
`seed.py::seed_babydoll(session)` creates (create-only, advisory-locked, safe to repeat, never overwrites studio edits) the `babydoll` client organisation, `bookings` + `contacts` entitlements, the profile `babydoll-beauty-bar` (enabled, `America/Grenada`, 24 h lead, 60-day horizon, `requires_confirmation`, manage link `<BABYDOLL_SITE_URL>/booking/{token}`), the 14 bookable services from `apps/web/babydoll/src/data/site.ts` (prices x100 minor XCD; durations are assumptions the site does not publish), provider "Jeriann" with the published hours (Mon-Fri 09:30-17:30, Sat 09:00-17:30) and public site `babydoll` (no contact, no subscriptions, Turnstile inherit). It never runs at startup. Run on demand from `apps/api/fastapi`: `python -m src.bookings.seed [--dry-run]` (`--dry-run` rolls back). `BOOKINGS_BABYDOLL_SITE_URL` lives in `config.py`. Tests: `tests/bookings/test_seed_babydoll.py`.

## A1.2: settings screen (`settings.py`)
`GET /bookings/org/settings` returns profile (nullable), services, providers (with `service_ids` and `working_hours`, two queries) and `deposits_available` (payments entitlement) in one call. `PUT /bookings/org/services/order` and `/providers/order` set `sort_order` to list position (all ids must be the organisation's, else 404). Services are deactivated, never deleted (bookings reference them). Its router is registered separately in `main.py`; tests: `tests/bookings/test_settings.py`.

## Tests
`tests/bookings/test_availability.py` (pure engine, no database), `tests/bookings/test_ics.py` (ICS format, status table), `tests/bookings/test_bookings_api.py` (studio CRUD, member read-only, cross-organisation denial, slug uniqueness, validation, the exclusion constraint, public storefront and availability, disabled/unknown 404, range limit), `tests/bookings/test_public_bookings.py` (create, replay, 409 reuse, concurrent duplicates, overlap race, honeypot, Turnstile, entitlement 404, cancel cutoff, reschedule, ICS, outbox emails, reminders, token never stored), `tests/bookings/test_studio.py` (studio actions, API keys, agenda), `tests/bookings/test_deposits.py` (deposits, paid handler, sweeper, refunds), `tests/worker/test_platform_jobs.py` (job registration, retention of tokens).

- **Turnstile and replays:** the public create route verifies Turnstile *inside* the idempotent handler (`create_once` in `router.py`). Tokens are single-use, so a client retrying after a lost response replays its stored receipt with the same `Idempotency-Key` and body without a second token; a new key must pass the check, and a failed check is not stored and releases the key. Tests: `test_a_replay_does_not_need_a_second_turnstile_token`, `test_a_failed_turnstile_check_releases_the_key`.
