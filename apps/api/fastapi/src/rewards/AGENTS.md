# rewards domain — agent context

**Owner:** Barrels platform (Barrels ID rewards, U1-U4; plan: `docs/exec-plans/barrels-foundations-plan.md`). Not a GAA/GMS module.

**Guardrails (amended by ADR-0030; do not weaken further without an owner decision):** opt-in action-ranked leaderboards, community challenges, check-in streaks and capped or non-redeemable stamp gifting are approved (PF10, behind flags; gifting stays off in production until an accountant and legal sign-off). The rest still holds: no cash withdrawal, person-to-person transfer, purchase of stamps or points, or anything that acts as stored value. No leaderboards, random prizes or rewards for opening the app. Stamps come only from a real-world source (an Events admission), a customer's own redemption, or an audited adjustment.

- Organisation routes (`/rewards/programs`, `/rewards/redemptions/confirm`) require the `rewards` entitlement (`require_org_app`, PF1). Migration `orgsites20261020` granted it to every organisation that had a programme; tests use `make_org(..., apps=("rewards",))`.
- Tables in the `rewards` schema of the main database (migration `rewards20261018`, `rewards` is in `_TRACKED_SCHEMAS`): `program` (organisation-funded stamp card: `stamps_required`, `reward_description`, `qualifying_source_type`, optional lifetime `max_redemptions_per_account`), `entry` (the ledger), `review_flag`.
- **Ledger (`entry`) is append-only.** A trigger rejects DELETE and any UPDATE that touches a column other than `status`, `settled_at`, `settled_by_user_id`, and never reopens a `reversed` entry. `amount` is signed (earn/credit +, redeem/debit -); balances are always SUMs in SQL (`service.cards`, `_available`), never stored. `balance` = confirmed + reversed entries (a reversal nets the original out); `pending` = unconfirmed earns (not spendable); `available` = balance minus stamps held by an open (pending) redemption. Test cleanup (`tests/conftest.py`) disables the trigger inside its own transaction.
- **Uniqueness:** `transaction_ref` is unique (`earn:<program>:<source_type>:<source_id>`, `reverse:<entry>`, `redeem:<uuid>`, `adjust:<uuid>`), plus a partial unique index per `(program, source_type, source_id)` for earns, so a repeated check-in or replayed sync credits nothing. A reversed source cannot be credited again.
- **Reversal:** `service.reverse_for_source(session, source_type, source_id)` appends a negating `reverse` entry per earn and marks the original `reversed`; idempotent; service functions flush, the caller commits.
- **Redemption:** the customer holds a card's stamps behind an 8-character one-time code (`POST /rewards/me/redemptions`, pending debit); staff of the funding organisation confirm it (`POST /rewards/redemptions/confirm`, `OrgContext`, other organisations' codes answer 404); the customer may cancel an open one. Limits: full card required, one open redemption per card, optional lifetime cap, paused programmes refuse. Per account+programme work is serialised with `pg_advisory_xact_lock`.
- **Velocity flag:** more than `REWARDS_VELOCITY_MAX_EARNS` (10) earns in `REWARDS_VELOCITY_WINDOW_MINUTES` (60) opens one `review_flag` per account (entries are kept). Reviewed through `/rewards/admin/flags`.
- **Adjustments:** `POST /rewards/admin/adjustments` needs `rewards.manage` (superusers pass); reason required; cannot take a card below zero. Every ledger/programme/flag write is audited by the flush listener (`audit.py`): ledger and flags under the `rewards_account` subject (readable with `rewards.manage`), programmes under `rewards_program` (also that organisation's admins/owners).
- **Badges (U4, `badges.py`):** `GET /rewards/me/badges` derives verified organiser (active membership in an organisation with `verified_at`), verified attendee (an admission on one of the person's tickets) and verified purchaser (a confirmed order with `total_minor > 0`) on every read. No table, no write path; when Events has no database the Events badges report `available=false`. The public organiser badge is the existing `verified` on Events organisers.
- **Account page (U1):** `GET /rewards/me/tickets` returns the account's Events tickets (read-only reuse of `events.service.my_tickets`; empty without an Events database), because the account token cannot call the app-scoped `/events/me/tickets`. Web: `apps/web/auth` Tickets and Rewards tabs.

## Earn sources, gamification and organisation views (PF8, PF9, PF11 API)

- **Earn sources (`sources.py`):** the catalogue of qualifying source types (`events.admission`, `bookings.completed`, `billing.invoice_paid`, `payments.succeeded`, `rewards.venue_check_in`). `ProgramCreate.qualifying_source_type` (default `events.admission`) must be in it (422 otherwise). `service.record_qualifying_action(session, source_type, source_id, organisation_id, user_id)` is the one entry point: it rejects unknown sources, credits every active programme of the organisation with that source through `earn_for_source` (idempotent per programme and source, velocity flag applies) and returns the new entries. `events_link.sync_admissions` calls it. No outbox yet: a later integration wires an outbox handler to this function; other products call it in their own transaction.
- **Gamification tables (migration `rewardsgame20261020`, `models_gamification.py`):** `venue` (organisation, name, `secret_encrypted` Fernet via `ORG_SECRET_ENCRYPTION_KEYS`; creating or scanning without keys is 503; the secret is never returned or audited), `trail` (organisation or NULL = platform, kind parish/festival/custom, optional window, status draft/active/archived), `trail_stop` (position, label, venue, `required_check_in` needs a venue), `check_in` (`UNIQUE (user_id, venue_id, local_date)`, `local_date` in Grenada time), `achievement_definition` (globally unique `key`, rule `attended_n_events {n}` / `visited_all_stops_of_trail {trail_id}` / `streak_days {days}`) and `achievement_award` (unique per user and definition). Not audited yet.
- **Venue QR (`qr.py`, pure):** token `v1.<venue_id>.<window>.<hmac>`, 60-second windows, HMAC-SHA256 truncated to 32 hex characters, constant-time compare, +-1 window tolerance. The display screen polls `GET /rewards/org/venues/{id}/qr-token` (org admin). Every failure (malformed, unknown or inactive venue, bad MAC, expired) is one 400, so the API is not an oracle.
- **Check-in (`gamification.check_in`, `POST /rewards/me/check-ins`):** a real-world scan only, never an app-open event. One per person, venue and Grenada day (409). It records the visit, calls `record_qualifying_action(rewards.venue_check_in, source_id=check_in.id)`, then evaluates achievements (platform ones plus the venue organisation's). Trail progress, the passport and the streak are derived from `check_in` rows on every read (`GET /rewards/me/passport|streak|achievements`); streaks use gaps-and-islands SQL and a day is not lost until it has passed. `attended_n_events` counts non-reversed `events.admission` earns and is evaluated at check-in (and by whatever calls `evaluate_achievements` later).
- **Organisation zone:** `GET|POST /rewards/org/venues`, `GET|POST /rewards/org/trails`, `PATCH /rewards/org/trails/{id}`, `POST /rewards/org/trails/{id}/stops`, `GET|POST /rewards/org/achievements`, `POST /rewards/org/programs/{id}/pause|resume`, `GET /rewards/org/entries` and `/rewards/org/redemptions` (no account identity). Reads need a member, writes an admin, all need the `rewards` entitlement (`RewardsOrgMember`/`RewardsOrgAdmin` live in `dependencies.py`).
- **Sample content:** `seed.seed_parish_explorer(session, organisation_id)` (idempotent; six parish venues, a trail and a completion achievement). Call it from a script or admin task; it is not run at startup or in a migration.
- **Still banned (tests assert what they can):** cash withdrawal, buying points or stamps, random prizes, rewards for opening the app, spend-ranked boards. The social layer is below.

## Social layer (PF10, `social.py`, `router_social.py`, `models_social.py`, migration `rewardssocial20261020`)

- **Everything is dark by default.** Each route needs its feature flag (`rewards-leaderboards`, `rewards-challenges`, `rewards-gifting`; unknown flag = off, 404 when off, evaluated for the user and the scope's organisation). Gifting additionally needs `REWARDS_GIFTING_ENABLED` (default false), which `social.gifting_hard_enabled()` refuses when `ENVIRONMENT=production` whatever the flag says (ADR-0030: accountant and legal sign-off first). Withdrawing a leaderboard opt-in is never flagged.
- **Leaderboards (`leaderboard_opt_in`):** nobody is read unless an active row exists (`withdrawn_at IS NULL`); withdrawal is immediate and idempotent; re-opting reuses the row. Scopes: `organisation` and `trail`. Metrics are action counts only (`venue_check_ins`, `trail_stops`, `events_attended`: distinct check-ins and non-reversed `events.admission` earns); `social._score_query` never reads an amount, price or balance (a test greps its source). Names are hidden by default: the alias or "Anonymous explorer"; `show_name` shows first name and last initial. A board needs `REWARDS_LEADERBOARD_MIN_COHORT` (10) opted-in people, else an empty board with a reason; max 50 rows plus the caller's own rank (people with score 0 are ranked but not listed). `GET /rewards/org/leaderboard` is the organisation's own board, aliases only.
- **Challenges (`challenge`, `challenge_progress`):** organisation-owned; `reward_description` is text and creates no ledger value. The total is computed from check-ins or ledger earns inside the window on every read; `challenge_progress` holds only the completion marker (first time the target is met, never reopened). Member view is aggregate only (no identity fields). Org create/pause/resume need `RewardsOrgAdmin`.
- **Gifting (`gift`):** `kind` is only `passport_stamp`: a souvenir copy of a venue stamp the sender earned (a `check_in`), found by recipient email (recipient must have an active account). It is never an `rewards.entry` row, so redemption balances cannot change; gifts do not feed passports, streaks, achievements, challenges or boards. The sender keeps their own stamp. No chains: only the sender's own check-ins can be gifted and a partial unique index allows one live gift per check-in. Caps (settings): 3 per sender per Grenada day and 10 per recipient for life, both counting reversed gifts; the sender may reverse within 24 hours (`reversed_at`); rows are never deleted. Per-sender work is serialised with an advisory lock.
- **Tests:** `tests/rewards/test_social.py` (flags off, production hard-off, privacy and withdrawal, cohort guard, spend does not rank, aggregate-only challenges, caps, no chains, ledger untouched, cross-organisation isolation) and `test_social_migration.py`.

## Integration with Events (no Events code is edited)

`events_link.py` reads the Events database read-only. The worker job `sync_event_rewards` (every 5 minutes) calls `sync_admissions`: it credits one stamp entry per admission whose organiser (via `organisers.organisation_id`) funds an active `events.admission` programme, and reverses entries whose ticket is no longer `valid` or whose order is no longer `confirmed` (cancelled/refunded). Events can also be exact and immediate: in the same main-database transaction as a refund or cancellation call `rewards.service.reverse_for_source("events.admission", str(admission_id))`, and after an admission call `rewards.service.earn_for_source(session, account_id=ticket.user_id, organisation_id=organiser.organisation_id, source_type="events.admission", source_id=str(admission.id))`. Both are idempotent, so the sync and direct calls coexist. E3-E5 should keep `orders.status` / `tickets.status` honest (`confirmed`/`valid` only while the sale stands); the sync keys off those.

## Tests
`tests/rewards/test_gamification.py` (+ `test_gamification_migration.py`): sources catalogue, idempotent replay, QR validity/expiry/tamper, Grenada-midnight check-in boundary, streaks, trail progress, achievement idempotency, isolation and entitlement, organisation ledger views, seed. `tests/rewards/test_rewards.py`: ledger invariants (append-only trigger, idempotent earn, reversal, uniqueness), pending/confirmed, velocity flag, redemption flow and cross-organisation denial, caps, programme roles, `rewards.manage` permission and audit, adjustments, flag review, Events sync and reversal, badge derivation and degradation, tickets bridge. `tests/rewards/conftest.py` reuses the Events disposable database fixture.
