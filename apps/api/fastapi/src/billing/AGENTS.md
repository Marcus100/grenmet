# billing domain — agent context

**Owner:** Barrels platform/product capability. Stripe groundwork is kept isolated until an approved product consumes it; invoicing (P1-P3) is live in the control plane.

## Stripe groundwork (unchanged)
- Stripe-backed subscriptions. `gateway.py` defines the `StripeGateway` protocol and `StripeSdkGateway` adapter; services depend on the protocol so tests can substitute it.
- Webhooks must verify Stripe signatures (`InvalidStripeWebhookError`). No card rail is wired for invoices; adding another payment provider is an Ask-First change and a portfolio decision.

## Invoicing (P1-P3, `billing` schema in the main database)
- Barrels invoices its own service-line clients. A customer is a platform organisation (`billing.customer.organisation_id`, unique). Routes (`invoice_router.py`, under `/api/v1/billing`) need superuser or `billing.manage` (`BillingManager`); the web console is `apps/web/admin`.
- **Money:** integer minor units (XCD cents), `Decimal` arithmetic in `calc.py`, rounded half-up per line (line subtotal, then line tax on that subtotal). Invoice totals are sums of rounded lines. The API takes `quantity` (3 dp) and `tax_rate` (2 dp) as floats and converts through `Decimal(str(x))`; never compute totals in the client.
- **Numbering:** `billing.invoice_counter` has one row per issue year, locked `FOR UPDATE` in the issuing transaction, so numbers are gapless and unique (a rolled-back issue rolls the counter back). Format `<prefix>-YYYY-NNNN`. Drafts have no number.
- **Status machine:** `draft -> issued -> partially_paid -> paid`; `issued -> void` only while unpaid (reason required, explicit audit entry). Drafts are edited (PUT replaces the lines) or deleted; everything else is immutable. Payments (bank transfer, cash, cheque) lock the invoice row, reject amounts above the balance (422) and future dates, and move the status.
- **Issue:** assigns the number, sets issue and due date (net 30, `issue_date` optional), snapshots the legal entity name, renders the PDF with WeasyPrint (`pdf.py`, in a threadpool), stores it privately at `billing/invoices/<id>.pdf` when `STORAGE_*` is configured, and queues an `OutboundEmail` card (`emails.py` queues it, `email_cards.py` builds it). The outbox has no attachments, so the email holds a 7-day presigned link when a PDF is stored, else it offers another copy on request. `GET .../pdf` always re-renders on demand.
- **Receivables:** `GET /billing/receivables` buckets open invoices (current, 1-30, 31-60, 61-90, 90+ days past due) in SQL with date comparisons; `bucket_for` in `invoices.py` must stay consistent with the SQL CASE.
- **Reminders:** worker job `send_invoice_reminders` (11:00 UTC = 07:00 Grenada) calls `reminders.send_due_reminders`. Stages: 7 days before due, due date, 7 days overdue. A unique `(invoice_id, stage)` row is inserted (ON CONFLICT DO NOTHING) before the email is queued, so a repeat run sends nothing; a stage is still sendable for `INVOICE_REMINDER_GRACE_DAYS` after its trigger day.
- **Audit:** `audit.py` registers invoices, lines and payments under `billing_invoice` and customers under `billing_customer`; history is readable with `billing.manage`.
- **Settings** (`BILLING_INVOICE_*` in `config.py`, `docs/env.md`): legal entity name, default VAT 15%, number prefix and padding are **provisional** until the registration and tax advice are confirmed. Currency XCD and net 30 are owner decisions.
- Service functions `flush` and never `commit`; routers commit (reminders commit themselves, as the worker owns that transaction).

## App subscriptions (ADR-0065, slice 1)
- Barrels sells its own app plans through Stripe Billing (NZ account, Barrels' subscriptions only). **Live switch** `BILLING_STRIPE_LIVE_ENABLED` (default off). Off: every Stripe call goes through `_require_stripe_key` (`gateway.py`), which accepts only `sk_test_` and refuses anything else with 503 before any request. On: only `sk_live_` (a test key is refused; mixed states fail closed). The owner flips it after the steps in ADR-0065 "Going live".
- Tables in `billing`: `plan`, `plan_price` (minor units; `bookings-monthly` XCD 3000 seeded), `app_subscription` (one live row per organisation and app, partial unique index; `status` moves only through `app_subscription_transitions.py`), `stripe_event` (applied event ids; the primary key makes a replay a no-op), `customer.stripe_customer_id`.
- Routes (`router.py`, ADR-0025 zone `org`): `GET /billing/org/subscriptions`, `POST /billing/org/subscriptions/checkout`. Gated by `OrgAdmin` alone (admin and owner, superuser or not; 404 for an outsider's organisation, and a superuser gets no bypass). No route uses `billing.subscriptions.manage` any more; that key stays in `src/auth/permissions.py` for owner review. Do not gate these routes on a global key again.
- The webhook `POST /billing/webhooks/stripe` applies events through `app_subscriptions.apply_stripe_event`. `construct_webhook_event` (after the signature) refuses an event whose mode does not match the switch with 503 before anything is written: off refuses `livemode: true`; on accepts only `livemode: true`. Otherwise the event id is inserted inside a savepoint, then the event is applied. An event strictly older than `last_event_at` is ignored; a same-second event applies in delivery order, and the transition table refuses backward moves (a canceled row stays canceled). An event that names one of our rows (`app_subscription_id` metadata) whose row is not written yet returns 503 and rolls the savepoint back, so the id is not recorded and Stripe retries; an event more than two hours old (or with no `created` time) is recorded and ignored with 200 instead (`_RETRY_WINDOW`). A status the table refuses is logged and the webhook still answers 2xx. Subscription row lookups take `FOR UPDATE`.
- `checkout.session.completed` links the Stripe ids and does **not** move `last_event_at` (Stripe may send the subscription's earlier event after it). Status comes from the subscription events.
- Checkout inserts the pending row after the refusals and before the provider call, with a per-subscription idempotency key, and stores the session id (`checkout_session_id`). A repeat checkout while a pending row exists resumes it: an open Stripe session returns the same id and URL; an expired one cancels the row (`INCOMPLETE` to `CANCELED`) and a new row replaces it; a session Stripe reports `complete` is refused (409) until the webhook moves the row. Rows without a stored session id are refused (409). Settings: `BILLING_STRIPE_PRICES` (`plan_key:currency` -> price id).
- **Access (ADR-0065 amendment):** the two org routes use `BillingOrgAdmin` (`require_org_role_session(ADMIN, session_app="bookings")`): an account token or the bookings studio token, OrgAdmin role, no entitlement check (buying is what entitles). Any other app's token is 401.
- **Return URLs:** `checkout_return_urls(slug)` builds `<BOOKINGS_APP_URL>/studio/<slug>/plan?checkout=success|cancelled` from the caller's organisation, never from the request. Without a slug or a bookings address it falls back to `BILLING_CHECKOUT_SUCCESS_URL` / `_CANCEL_URL`.
- **Trials:** a `billing.app_subscription_trial` row (`organisation_id`, `plan_key`, `trial_days` 1-365) is the only source. No row, no trial, which is the default for every business. The Babydoll seed (`src/bookings/seed.py`, `TRIAL_DAYS = 30`) writes it through `grant_trial`, create-only. A grant is used once: once a Stripe subscription has started for that org and plan, a new checkout gets no trial. An abandoned checkout keeps it. The global `BILLING_APP_TRIAL_DAYS` setting is removed. A self sign-up grant (ADR-0066) also stores `trial_ends_at`: checkout passes the days left rounded up, and none once it has ended (`_trial_days`).
- Legacy `POST /billing/checkout-sessions` (invoicing-era, creates no row) is test-only in every mode and answers 503 while the switch is on. Kept, not removed, so the contract does not break; ADR-0065 says it must move before live.
- Not built: the entitlement link (an organisation's app access). Do not add it without the owner's go and a flag that is off by default.
