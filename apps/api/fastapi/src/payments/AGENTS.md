# payments domain — agent context

**Owner:** Barrels platform (PF4; ADR-0027; plan: `docs/exec-plans/barrels-foundations-plan.md`). Not a GAA/GMS module. Consumers (Events paid tiers, Bookings deposits, invoice payment) are wired by their own domains; this domain imports none of them.

## Hard rule: no live card rail
Stripe runs in **test mode only**. `providers/stripe.py` refuses (503) any `PAYMENTS_STRIPE_SECRET_KEY` that does not start with `sk_test_` before a request is made, refuses callbacks while `PAYMENTS_STRIPE_WEBHOOK_SECRET` is unset or not `whsec_...`, and is disabled while the key is unset. `tests/payments/test_providers.py` asserts a live key sends nothing. Going live needs the ADR-0027 gate (owner decision, accountant and legal sign-off, reconciliation exercise); do not weaken the guard without it.

## Model (schema `payments`, migration `payments20261020`)
- `intent`: amount (integer minor units) + 3-letter currency (default XCD), status `requires_payment/processing/succeeded/failed/cancelled`, `provider` (`manual`/`stripe`), `provider_ref` (Checkout Session), `provider_payment_ref` (Stripe PaymentIntent, set on capture), `source_type`/`source_id` (what is sold, e.g. `bookings.deposit`), `customer_email_hash` (SHA-256 only, the address is never stored or sent to Stripe), `metadata` JSONB (no personal data), `idempotency_key` unique per organisation.
- `attempt`: one try per online checkout. `refund`: amount, reason, status. `ledger_entry`: the money record.
- **`ledger_entry` is append-only.** A trigger rejects DELETE and any UPDATE (only `created_by_user_id` may be nulled when a user is removed). Signed `amount_minor`: charge +, refund/fee/payout -, adjustment either. Check constraints enforce the signs. Unique `(provider, provider_event_id)` is the callback idempotency key (manual charges use `manual:<intent>`, refunds `refund:<id>`, payouts `payout:<uuid>`). Balances are SUMs in SQL, never stored. Test cleanup (`tests/conftest.py`) disables the trigger inside its own transaction.

## Flows
- Funds sit on Barrels' merchant account; the ledger says what each organisation is owed. Payouts are manual `payout` entries created by a superuser and cannot exceed the balance (advisory lock per organisation).
- **Manual rail** (cash, bank, cheque): create an intent with `provider=manual`, then staff `POST .../manual-payments`; it succeeds immediately and writes the charge.
- **Stripe rail**: create returns a hosted Checkout URL (intent `processing`); the webhook `POST /payments/public/webhooks/stripe` maps `checkout.session.completed` (charge), `payment_intent.payment_failed` (failed attempt), `charge.refunded` and the refund events `refund.created`, `refund.updated` and `refund.failed`. **The live webhook endpoint must subscribe to `charge.refunded`, `refund.created`, `refund.updated` and `refund.failed`** (owner dashboard step, before any live key): without `refund.created|updated|failed` a refund the provider reports on its own never reaches the ledger, and without the charge list a dashboard refund is missed. A callback locks the intent row, checks the ledger key, and answers 2xx for anything already processed. A captured amount that differs from the intent is logged and not credited. Refund reconciliation (one rule for every refund report, `_reconcile_listed_refund`): each refund the provider reports is matched to our row by our refund id (the refund's `metadata.refund_id`; every core refund sends it) and then by the provider refund id (`provider_ref`). A refund we did not record (our call lost before commit, or a dashboard refund) is written once, under our id when it has one. A row moves to the provider's status: `pending` (also `requires_action`) is recorded as pending and counts against what can be refunded; `succeeded` settles it; `failed` or `canceled` marks it failed and writes an adjustment that reverses its ledger entry (`refund-failed:<id>`); a failed row the provider later reports succeeded is taken off the balance again (`refund-succeeded:<id>`). Settled money is never moved back by a later report. Listed amounts are capped at what was captured. Ledger keys: `refund:<row id>` for a refund we or the provider made (as `refund_intent` writes it). `charge.refunded` reconciles the refunds on its list the same way. **A charge's refunds are listed only when Stripe expands them, and webhook payloads are not expanded**, so a `charge.refunded` without a list is incomplete: its total is never used to infer a missing refund (a guess would write our lost refund under a random id and count it twice when the outbox retry arrives). The remainder from `amount_refunded` minus what is recorded is taken only from a complete list; a truncated list (`has_more`) is logged and not guessed from either. The refund events carry the refund itself and are reconciled the same way. A refund that fails after our call (`refund_intent` replays a failed row) raises `RefundFailedAtProvider` (a 409 conflict) instead of reporting success: Stripe replays the stored answer for the same idempotency key, so a retry cannot succeed. The Events outbox handler turns it into a terminal failure (`outbox.TerminalFailure`), so the row dead-letters at once with the dead-letter signal; the organiser refunds again with a new key (see `src/events/AGENTS.md`).

**Which payment a refund event is about:** the provider's `payment_intent` decides (`_locate_refunded_payment`); our metadata `intent_id` is only a fallback. When both name a payment and they differ, or our metadata payment has another provider payment, the event is refused and logged (`refund event names two payments; not applied`) and nothing is recorded.

**Out of order:** a late pending report never moves a settled refund back, and a pending report after a failure is ignored (logged at info). A failed refund the provider later reports succeeded is taken off the balance again (`refund-succeeded:<id>`) without re-checking the refundable amount; that case is rare and the cap applies only to new rows.

**Missing list log:** a `charge.refunded` without a refund list logs `charge.refunded without a refund list: the refund.created, refund.updated and refund.failed webhook subscription may be missing`; grep for it when refunds look missing in staging.
- **Refunds** lock the intent and refuse more than captured minus already refunded (pending + succeeded) with 422. A provider failure rolls back (502).
- Webhook signatures are verified in-house (HMAC-SHA256 over `t.payload`, `PAYMENTS_WEBHOOK_TOLERANCE_SECONDS` window, constant-time compare, any `v1` may match for rotated secrets). The adapter talks to `api.stripe.com` over httpx; tests swap `providers.stripe._transport` with `httpx.MockTransport` (see `tests/payments/conftest.py`). `fetch_status` exists on the protocol and adapter but no route calls it yet.

## Routes (`/api/v1/payments`, ADR-0025 zones)
- `org/*`: OrgAdmin with the `payments` entitlement (`require_org_app`): create/list/get intents, record manual payment, refund, balance. Other organisations' ids answer 404.
- `POST org/intents` refuses `source_type` values owned by another domain (`RESERVED_SOURCE_TYPES`: `bookings.deposit`, `events.order`, from `PAID_TOPICS`/`REFUND_TOPICS`) with 422 (`reject_reserved_source`); those domains create intents through the service. Bookings records a deposit taken by hand with `record_manual_payment` (see `src/bookings/AGENTS.md`). `refund_intent(refund_id=)` is replay-safe: an existing refund with that id on the intent is returned as is (a failed one is a 409, not a success), another intent's id is 409, and Stripe uses `refund-<id>` as its idempotency key (used by the Events refund outbox handler).
- `public/webhooks/{provider}`: signature-authenticated, hidden from OpenAPI (like the billing webhook).
- `admin/*`: superuser only: all intents, ledger, balances, payouts, reconciliation JSON and `reconciliation.csv` (Events settlement CSV style, formula-neutralised cells). Periods are Grenada days, both ends inclusive.

## Known gaps
No audit-log registration for payments tables yet (the ledger itself is the record). Stripe Connect is deferred (ADR-0027, option 3).

- **Hosts for return addresses:** a registered return URL whose host contains `%` or non-ASCII characters is refused outside the local environment (`_is_local_host`), as are loopback, unspecified, private and link-local addresses and localhost names. Non-ASCII domain names must be sent in their punycode form.
- **Truncated refund lists and the reconciliation job (#869):** a `charge.refunded` with more refunds than it carries (`has_more`) is logged and not reconciled from the webhook. The daily ARQ job `reconcile_provider_refunds` (04:40 UTC, `service.reconcile_recent_refunds`) closes the gap: for each captured Stripe payment created in the last `PAYMENTS_REFUND_RECONCILE_WINDOW_DAYS` (default 180, at most `PAYMENTS_REFUND_RECONCILE_BATCH`, default 200, per run, newest first) it lists every refund through `GET /v1/refunds?payment_intent=` following `has_more` (`StripeProvider.list_refunds`, at most `REFUND_MAX_PAGES` pages, else the listing is incomplete and totals are not compared) and reconciles each with `_reconcile_listed_refund`, the webhook rule, so a second run writes nothing. The Stripe call runs with no transaction open; the intent is locked only to apply the result, and each payment commits on its own. Afterwards the refunded totals are compared; a difference is logged at error (`refund reconciliation mismatch`, reaches Sentry), except a refund of ours younger than `REFUND_CHECK_GRACE` (1 hour) that the listing does not show yet. A Stripe error on one payment is logged and retried next run; Stripe off (unset or not a test key) skips the run. Tests: `tests/payments/test_refund_check.py`.
- **Rollout risk for rows written before this change:** refunds recorded by the old total-based path have `provider_ref` NULL, so a later provider report for the same refund (matched by provider id) will not find them and would record it again. Stripe is test-mode only today, so the risk is test data; before any live key, backfill `provider_ref` on those rows from the provider's refund list or check the ledger against the provider.

## Tests
`tests/payments/`: `test_payments.py` (manual flow, idempotent create, refund limits, cross-organisation denial, ledger trigger and signs, webhook replay/signature/mismatch/failure/refund, admin, payouts, reconciliation and CSV), `test_providers.py` (live-key refusal, signature valid/invalid/stale, Stripe client over a mock transport, manual provider), `test_refund_check.py` (refund listing pagination, the reconciliation job), `test_payments_migration.py`.

- **Payout idempotency:** `POST /payments/admin/payouts` requires a client-generated `request_id` (UUID). It becomes the ledger's `provider_event_id` (`payout:<request_id>`), so a double click or retry returns the original entry, and the same id with another organisation, amount or currency is a 409. The admin confirmation page renders one id per page view.
- **Webhooks:** a captured payment emits `payment.succeeded`, a refund emits `payment.refunded` (`_emit_payment_event`): ids, amounts, currency and the source reference only; the refund reason is free text and is never sent.


- **Service actor and consumer hooks (Bookings B6):** `create_intent` and `refund_intent` take `actor: User | None`; `None` means the system acts for an anonymous customer or a rule, and `created_by_user_id` is NULL (the org routes still pass the member). `find_by_source(organisation_id, source_type, source_id)` returns the newest intent with its captured and refunded totals; `cancel_open_intent(...)` locks it and cancels an unpaid one (returns False when it already succeeded). `_capture` enqueues an outbox topic from `PAID_TOPICS` (`bookings.deposit` -> `bookings.deposit_paid`, dedupe key = intent id) in the same transaction as the ledger charge; the consuming domain registers the handler, payments imports nothing of it. Add a source type by adding it to `PAID_TOPICS`. `PAID_TOPICS` now also maps `events.order` -> `events.order_paid` (Events paid tiers, N4b). `REFUND_TOPICS` (`events.order` -> `events.order_refunded`) enqueues a topic for every recorded refund (app refund or a provider-dashboard refund via `charge.refunded`), dedupe key = refund id, payload `intent_id`, `source_id`, `refund_id`; a source type without an entry is not told. Tests: `tests/payments/test_refund_topics.py`.
