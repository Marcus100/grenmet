# contacts domain — agent context

**Owner:** Barrels platform (ADR-0028, foundations slice PF3). An organisation's contact book: one record per person per organisation, with consent and erasure in one place. Not a GAA/GMS module.

- Tables (main database, `org` schema): `org.contact` (`con_<hex>` id, `organisation_id` cascade, `email_hash` unique per organisation, `email` only while needed to send, `name`, `phone`, optional `user_id` Barrels ID link with no foreign key, free-text `source`, `erased_at`) and `org.contact_consent` (bigint identity id, `contact_id`, `organisation_id`, `purpose` marketing/service/analytics, `granted`, `source`, `granted_at`, `revoked_at`, `recorded_at`).
- **Matching:** exact `hash_email` match within one organisation only (`find_by_email`, `upsert_contact`). Never match or merge on name, phone or user link. The one account link is `link_verified_account` (ADR-0058): a signed-in booking sets `user_id` only when the account's verified email equals the booking email (`normalise_email`, the same normalisation as the hash); it never relinks, and it never links on name or phone. `merge_contacts` is the only way to join two records; it is explicit, same-organisation, audited, moves the consent history, keeps the earlier `created_at`, fills blank name/phone/user link, and deletes the other record.
- **Variant hash (#1982):** `email_variant_hash` (coarser form: `+tag` stripped, dots stripped at gmail.com and googlemail.com) is read only by `is_known_address` (exact or variant, one organisation). It is never identity: no unique key, no use in `upsert_contact` or `merge_contacts`. Erasure clears it, so an erased contact matches on its exact `email_hash` tombstone alone.
- **Upsert** keeps existing name/phone and fills blanks; passed consents add a history row only when the decision changes. One exception for the name: `take_name_from_linked_account` renames a contact to the name typed on a booking made by the account it is linked to, so the contact book follows what the person last called themselves (#1688; what each booking *shows* is its own `booked_name`, #1951). It is never used for a guest, and never for an erased contact. An erased contact that returns is revived with only the data now supplied and no consent.
- **Consent history is append-only:** `set_consent` inserts, the current decision per purpose is the latest row (`current_consents`). Only merge re-parents rows. Consent cannot be set on an erased contact.
- **Erasure** (`erase_contact`): blanks email, name, phone and user link, sets `erased_at`, appends a revocation (source `erasure`) for every granted purpose, keeps the hash tombstone. Domains that reference a contact must respect `erased_at`. A domain that keeps a *copy* of personal data beside its role row registers an `erase` hook in `references.py` (`register(table, erase=...)`, an async `(session, contact_id)`), and `erase_contact` runs every hook inside the erasure's transaction, so the copies go with the original: hiding a copy at read time would leave the data stored. The copies today are `bookings.booking.booked_name` (the name typed on one booking, which the views prefer) and `bookings.booking.notes` (free text) and the note text of each `bookings.booking_event` (the staff timeline; the rows, kinds, times and reason codes stay) and `bookings.booking.cancel_reason` (the cancellation reason: staff's, or the customer's own when they cancel), all cleared by `_erase_booking_copies`. Mail is matched by the contact's address and the erasing organisation before it is blanked (`notifications.address_log.clear_contact_mail`): queued mail is deleted, sent rows are redacted (the record stays). Rows with NULL `outbound_email.organisation_id` (written before that column) are not attributable and are left alone: no retention purge reaches the delivery log today, so they persist until a retention decision. Erasure clears `events.orders` cash walk-in copies; online buyers not (#1986).
- **Services flush; routers commit.** Other domains call the service functions (consumers: `bookings.customer.contact_id` is required and holds the booking role of a contact; billing keeps one organisation-level billing email).
- **Routes** (`/contacts`): `/org/contacts` list (paginated, `q` name search or exact email, `include_erased`), upsert (`POST`), `/{contact_id}` get and `PATCH` (name, phone), `/consents` get and `POST`, `/merge`, `/erase`; `/admin/contacts` superuser read. All `/org` routes use `require_org_app("contacts")`: members read, admins and owners write. The `contacts` product is in `organisations.entitlements.PRODUCTS`. It is granted together with `bookings` (`entitlements.BUNDLED_WITH`, applied in `organisations.service.set_app_enabled`; migration `bookingsgrantscontacts20261021` covered existing organisations), so a booking organisation gets the whole contact book: members read; admins and owners can also create contacts (POST), edit name and phone (PATCH), record consent decisions (POST `/consents`, including marketing), merge and erase. Disabling `bookings` later leaves `contacts` on; the standalone contacts product is still sold separately. No public routes.
- **Audit:** `audit.py` tracks contacts (excluding email, hash, name, phone) and consent rows under the `platform_organisation` subject; merge and erase add explicit entries. Logs carry no personal data.
- **Registration** (ADR-0031 manifest): `register.py` names the router, the `org` schema, `models.py` and the audit register by import path; `src/domains.py` lists it in `DOMAINS`. `main.py`, `database.py` and `alembic/env.py` do not name this domain.
- Retention: `docs/security.md` (data retention table).
- **Party/role references (ADR-0028):** a domain table with a required `contact_id` registers itself in `references.py` (`register(table)`, done in its `models.py`), optionally with a `merge` hook (fold the rows itself) and an `erase` hook (clear its copies of personal data); `merge_contacts` re-points all registered rows to the kept contact before deleting the other. `create_without_email` makes a contact with no address (`email_hash` is NULL, never matched; used for walk-ins).

- **Account link (ADR-0058):** `link_verified_account` (signed-in booking only; locks the account row and re-reads its email and verification, then the contact row; erased contacts never link; #1384) and `unlink_account(user_id)` (clears every link of one account; called by auth on an email change and on account deletion, through the service, never the table). The link is never shown to businesses: `user_id` is excluded from the audit registry and from organisation responses (`contacts/router.py` `_view`); link and unlink write value-free `link_account` / `unlink_account` rows under the organisation's history, with no actor (`_system_actor`). Public bookings clear the audit actor so a signed-in payer's name never appears in the business's history.
- **Not backfilled:** existing contacts are not linked. Past guest bookings appear in the account's list only after the person books while signed in with a verified matching email, or through the claim flow (a later slice).
- **Known behaviour (owner decision, accepted):** a guest booking made with an email whose contact is already linked to an account appears in that account's list. A merge that folds a guest record into a linked one does the same.
