# events domain — agent context

**Owner:** Barrels product (Barrels Events, `apps/web/events`; PWA `apps/pwa/pwa-events` next). Not a GAA/GMS module.

- Tables live in the `events` schema of the **main database** (ADR-0003), migrated by the main Alembic chain (`alembic/versions/2026-10-21_events_schema.py`, hand-written SQL; models in `models.py` extend `src.orm.Base` via `EventsModel`). People are auth `user_id` UUIDs, organisations and payment intents are plain ids with no FK. Routes use the request's main session (`EventsSession` = the same cached `SessionDep` session), so a ticket, its payment and its points save in one transaction. There is no `EVENTS_DATABASE_URL` and no 503-while-unset behaviour.
- Auth is app-scoped (ADR-0016): member routes use `EventsMember` (`app_user("events")`), public reads use `EventsViewer` (optional). Staff tokens are refused here; Events tokens are refused on staff routes. Organiser routes need `events.organiser.manage` **and** `organiser_members` membership; moderation needs `events.moderate`.
- **Organiser to organisation bridge (F5, ADR-0022):** `organisers.organisation_id` (migration `events_0002`, unique, no cross-DB FK) holds the `org.organisation.id` backing the organiser. `require_organiser` passes with `events.organiser.manage` or an active admin/owner platform membership; `organiser_scope` lists those organisation ids and the service resolves the organiser (`?organiser=<slug>` picks one when several). Once an organiser is linked, platform membership is authoritative; the legacy `organiser_members` row only counts while `organisation_id` is NULL. `service.create_organiser` creates the platform organisation plus owner membership. Tests: `test_organiser_platform.py`.
- **Organiser requests:** `POST /events/manage/organiser` (any Events member, 5/hour) calls `service.request_organiser`: `create_organiser` with `verified=false` (pending), one pending request per member (409). Moderators list `GET /events/moderation/organisers`; verification is decided by an MFA superuser (`PATCH /events/moderation/organisers/{id}` `{verified}` or the admin moderation routes below). Verification (platform organisation `verified_at` when linked, else the legacy flag) gates publishing: only verified organisers can move a listing to `published` (403 `Only verified organisers can publish events…`); unverified organisers can save drafts. `scripts/seed_events_demo.py` (local, after `initial_data.py` in prestart) creates organisers through the service, owned by `--owner-email` (default first superuser). Tests: `test_organiser_request.py`, `test_seed_demo.py`.
- **Outbox (F6, `outbox.py`, `notifications.py`):** `outbox.enqueue` adds an `events.notify` row to the platform outbox (`src/outbox.py`, ADR-0026) in the caller's transaction (deduped by `(topic, dedupe_key)`). Kinds (`payload.kind`): `listing.published` (followers of the organiser, public listings only), `listing.cancelled`, `listing.postponed` (going + saved members + ticket holders), `organiser.approved` (active owners/admins of the backing platform organisation), `ticket.issued`. The platform `drain_outbox` job runs `outbox.deliver`: recipients resolved at drain time, `notifications.notify(dedupe_key=...)` so a repeat tells nobody twice; retries, back-off and dead-lettering belong to the platform outbox. Payloads hold ids and public labels only. Notification emails carry no deep link. Tests: `test_outbox.py`.
- **Activity log (F7, `events_0004`, `activity.py`):** append-only `activity` table (a trigger rejects UPDATE and DELETE). Every organiser and moderation mutation writes exactly one row in the change's transaction: `organiser.created` (in `create_organiser`), `organiser.verified`/`unverified` (only when the flag changes), `organiser.rejected`/`resubmitted` (moderation), `listing.created|updated|published|rescheduled|cancelled`, `report.actioned|dismissed`, `suggestion.approved|rejected`. Rows hold the actor's auth user id, the entity and a summary of changed field names plus short public before/after values (title, status, times); no names, emails or free text. `GET /events/manage/{listing_id}/activity` (organiser of that listing only, newest first) joins the actor's current profile name at read time; `/dash/events/[id]` renders it as the History panel. Tests: `test_activity.py`.
- **Orders and tickets (E1, `events_0005`, `tickets.py`, `service/ticketing.py`):** `orders`, `order_items`, `tickets` (+ `ticket_tiers.per_account_limit`, default 4). Free and registration tiers issue tickets at once; paid tiers are the N4b flow below. Inventory is the count of `valid` tickets per tier plus the stock held by unpaid orders (`service/holds.py`); `claim_tickets` locks the requested tier rows `FOR UPDATE` (id order) before checking allocation and the per-account limit, so sold never exceeds allocation. Cancelling sets `cancelled` and releases the seat; only before the event starts. Ticket `code` is random and opaque; the QR token `BT1.<code>.<hmac>` is signed with the app `SECRET_KEY` and holds no personal data. `_sync_tiers` updates tiers in place (`TierInput.id`) and refuses to remove or shrink tiers below issued tickets. Outbox kind `ticket.issued` notifies the buyer. Tests: `test_tickets.py`.
- **Door admission (E2, `events_0006`, `service/admission.py`):** `admissions` has a unique `ticket_id`, so a ticket is admitted once even when two devices scan together (the ticket row is locked `FOR UPDATE`). `POST /events/manage/{listing_id}/admissions` takes the QR token or a typed code (`tickets.code_from_scan`; tokens are signature-checked) and an optional client `idempotency_key`: the same key replays its own success (`repeat=true`), any other second scan is 409 `Already admitted at HH:MM by <name>` (Grenada time). Cancelled tickets and other events' tickets are refused; used tickets cannot be cancelled. Each admission writes a `ticket.admitted` activity row on the listing (ticket id, tier, method; no names). `GET /events/manage/{listing_id}/manifest` lists valid tickets with holder name, tier and admission time plus `issued/admitted/waiting/cancelled` counts. Same organiser gate as listing management (404 for another organiser's event). Tests: `test_admission.py`.
- **Outlet cash (E3, `events_0008`, `service/outlet.py`):** the organiser's own staff sell tickets for cash (`POST /events/manage/{listing_id}/outlet/sales`; screen data `GET .../outlet`; reprint `GET .../outlet/sales/{order_id}`). Who: the same people as door admission, i.e. active platform admin/owner (or legacy organiser member); plain `member` staff are deliberately excluded because they would handle cash. Outlet orders have `channel='outlet'`, `payment_method='cash_outlet'`, null `user_id` on the order and its tickets (buyer name/phone optional, stored on the order only), `collected_minor` that must equal the price total (409 otherwise) and an optional `idempotency_key` (replay returns the original sale, `repeat=true`). Inventory is shared with online claims: both lock tier rows `FOR UPDATE` in id order and count `valid` tickets, and both take a shared lock on the listing row; the per-account limit applies online only. A sale needs the caller's open `till_sessions` row (one per staff, listing and Grenada day: `POST .../outlet/till` with an opening float, `POST .../outlet/till/close` with the counted cash; expected = float + takings, difference = counted - expected). Activity: `till.opened`, `till.closed`, `ticket.sold_outlet` (ids and amounts only, no buyer details). Tests: `test_outlet.py`.
- **Settlement (E4, `service/settlement.py`):** `GET /events/manage/{listing_id}/settlement` (same gate as door/outlet), `GET .../settlement.csv` (download; text cells starting `= + - @` are prefixed with `'`) and `GET /events/manage/settlement` (one summary row per ticketed, non-draft event). Counts come from `tickets` joined to the order channel (`online`, `outlet_cash`) and `admissions`: `issued` (all), `claimed` (valid), `admitted`, `waiting` (valid, not admitted), `cancelled`, `refunded`, `value_minor` (face value of claimed). Cash comes from `till_sessions`: expected = float + takings - cash refunds; closed tills are compared with the count. Mismatches are listed in `discrepancies` (`till_short`, `till_over`, `till_open` once the event ended or was cancelled, `refund_without_till`, `online_ledger_mismatch`), never netted away. N4b adds `online_payments` (below) and the online channel's `collected_minor`/`refunded_minor`. Tests: `test_settlement.py`, `test_paid_orders.py`.
- **Cancel, postpone and refund (E5, `events_0009`, `service/cancellation.py`):** `POST /events/manage/{listing_id}/cancel` (`{confirm: true, refund}`; legacy `CancelEvent.refund` is `full|none|follow_policy` and defaults to `none`, while the org-zone `OrgEventCancel` and `OrgOrderCancel` default to `follow_policy`) takes the exclusive listing row lock (claims and outlet sales hold a shared one), sets the event `cancelled`, cancels every valid ticket (`ticketing.cancel_valid_tickets`; saving a listing as cancelled through `PUT` does the same), queues `listing.cancelled` and writes `listing.cancelled` activity with `tickets_cancelled`. Only a published event can be cancelled or postponed. `POST .../postpone` (`{starts_at, ends_at}`, new start in the future and different) keeps tickets valid, queues `listing.postponed` (dedupe by new start) and writes `listing.rescheduled`. The outbox audience for cancelled/postponed is going + saved members + ticket holders. `POST .../tickets/{ticket_id}/refund` (`{amount_minor, method: cash|bank, reference?}`) records a manual refund (`refunds`, one per ticket): outlet cash tickets only (an online-paid ticket is refunded through the payments core instead, see N4b), amount at most the paid unit price, bank needs a reference, a used ticket only when the event was cancelled, a holder-cancelled ticket never. The ticket becomes `refunded` (not admittable, seat released) and a cash refund links to the refunding staff member's open till (subtracted from its expected cash; with no open till settlement flags `refund_without_till`). Activity `ticket.refunded` holds ids, amount and method, never the reference. Tests: `test_cancellation.py`.
- **Paid tiers (N4b, `events_0010`, ADR-0027; test-mode Stripe or the manual rail only):** `orders` gains `payment_intent_id` (plain UUID of `payments.intent.id`, indexed, **no FK**: ADR-0003), `payment_expires_at`, `paid_at`, `refunded_minor`, and `payment_method` may be `online`. Order `status`: `confirmed` (free, outlet, paid) | `pending_payment` | `expired` | `refunded`. `claim_tickets(db, user, slug, body, idempotency_key=)` with a total above zero: requires the organiser's organisation to hold the `payments` entitlement (else 409 "...online payment isn't available for this event"), counts valid tickets **plus `pending_payment` order items** against the allocation and the per-account limit (tier rows locked `FOR UPDATE`, so overselling is impossible), creates the order `pending_payment` with `payment_expires_at = now + EVENTS_ORDER_HOLD_MINUTES` (default 30) and commits the order, then creates the intent through `order_payments.ensure_intent` (`source_type="events.order"`, `source_id=<order id>`, key `events.order:<order id>`, `actor=None`, metadata `order_id` + `listing_id`) and records its id on the order. Order first, then intent: a retry finds the intent by its key; an order that never got one is expired by the sweeper; if the money side fails the hold is released at once. `Idempotency-Key` (optional header, stored on the order, unique per listing and member) makes a replay return the same order (looked up under the tier locks, so concurrent twins converge; other items with the same key: 409). Postgres deadlock-victim = a lost race (409, `ticketing.is_deadlock`, same rule as bookings). The order response is additive: `status`, `payment_required`, `checkout_url`, `payment_expires_at`; `GET /events/me/orders/{id}` polls it.
- **Paid tiers, payment and refund reactions (`order_fulfilment.py`, `payment_handlers.py`):** payments enqueues `events.order_paid` (charge) and `events.order_refunded` (each refund) on the platform outbox; the handlers (imported by the worker `startup` and `drain_outbox`) run on the outbox session, so tickets, order status, queued receipt, refund and the outbox row's `done` status commit together; a crash replays the message and the order row lock plus its status make it idempotent. `fulfil_paid`: `pending_payment` and the event still on sale -> tickets created once (count guard), status `confirmed`, `collected_minor`/`paid_at` mirrored from the ledger, receipt email queued with `notifications.outbox_handlers.enqueue_email` (dedupe `events-order-paid:<order id>`, requeued on every replay, no `ticket.issued` notification for paid orders); `expired`, or the event cancelled/ended -> **full refund** via payments and no tickets; already `confirmed`/`refunded` -> no-op. A payments failure propagates so the outbox retries (5 attempts, then `dead`). `apply_refund`: mirrors the ledger onto the order; only a **full** refund moves valid tickets to `refunded` and the order to `refunded` (a partial refund keeps them). Known gap: a provider refund that fails after it was recorded (pending, then `refund.failed`) reverses the money and the order mirror, but tickets already moved to `refunded` by a full refund are **not restored** (and the rewards reversed for them are not re-credited); staff re-refund or re-issue by hand. A queued refund whose provider refund failed dead-letters at once (`outbox.TerminalFailure`, dead-letter signal); operator recovery: the organiser issues a new refund from the order desk (`POST .../orders/{id}/refunds` with a new `Idempotency-Key`, so a new refund id) for the amount still due, and the dead request is left as it is. Sweeper: ARQ job `expire_unpaid_event_orders` (every 5 minutes) -> `order_fulfilment.expire_unpaid`: due `pending_payment` orders `FOR UPDATE SKIP LOCKED`, `cancel_open_intent` (False = payment just succeeded, skipped), then `expired` in the same transaction as the cancelled intent. A holder cannot self-cancel an online-paid ticket (409; refund through payments). On an event cancel (`event_cancel.cancel_event_orders`, only for an organiser linked to an organisation) the online `confirmed` and `pending_payment` orders are locked and settled by the request's `refund` choice; for a `pending_payment` order `order_payments.stop_collecting` cancels the unpaid intent and the order becomes `expired` (counted in `orders_released`), and only a payment that just landed is refunded in full by the paid handler. Single orders are refunded through the org order desk below. Settlement `online_payments` compares the orders' `collected_minor`/`refunded_minor` with the payments ledger summed by `metadata.listing_id` (`order_payments.ledger_totals`). Rewards: `rewards_hook.credit_admission` runs in the admission transaction (only valid tickets exist for confirmed orders, so unpaid or expired orders never earn); `reverse_for_tickets` reverses stamps when the event is cancelled or a paid order is fully refunded. Tests: `test_paid_orders.py`, `tests/payments/test_refund_topics.py`, `tests/worker/test_event_order_jobs.py`.
- **Organiser org zone (ADR-0044 S2, `org_router.py`, `/events/org/*`):** acts for the organisation in `X-Barrels-Organisation`; each route is gated by `require_org_permission(key, session_app="events")` (membership role or live grant, `events` entitlement, account or Events app session). Keys per route: `GET events/{listing_id}/orders` and `GET orders/{order_id}` need `events.settlement.view`; `GET events/{listing_id}/attendees` `events.door.scan`; `POST orders/{order_id}/manual-payments` `events.tickets.sell`; `POST orders/{order_id}/refunds` and `.../cancel` `events.refunds.issue`; `POST events/{listing_id}/cancel` `events.listings.manage`. Another organisation's event or order is 404. Buyer emails show to owners and admins only, not to members holding a grant. Manual payment and refund require an `Idempotency-Key` (replay returns the first answer with `Idempotency-Replayed: true`). Refund choice is `full|none|follow_policy` (`order_refunds.py`): the manual rail settles inline, a provider rail queues the outbox topic `events.order_refund_requested` (`payment_handlers.order_refund_requested`; refund id derived from order and request key, so a retry never refunds twice). Lock order: listing, then order, then intent or tickets. A queued refund's outbox row is taken NOWAIT on a re-cancel (409 "being sent" while the outbox holds it); a re-armed dead refund keeps the amount fixed at request. The "refund already waiting on this order" check uses `outbox.pending_for_order` (partial index `outbox_pending_order_idx`, migration `outboxorder20261031`); an event cancel counts such an order in `orders_pending`, not in `refunds_failed`. Known gap: the outbox sends the provider refund inside the drain transaction, which holds the outbox row and the order lock for up to `PAYMENTS_REQUEST_TIMEOUT_SECONDS` (#517). Migration `eventsentitlement20261022` backfills the `events` entitlement for organisations behind organisers and `service.organiser_admin.ensure_events_entitlement` does it on `create_organiser` (a missing row only; a switched-off row stays off). `/events/manage/*` keeps the legacy organiser gate unchanged. Tests: `test_org_permissions.py`, `test_org_orders.py`, `test_org_orders_money.py`, `test_entitlement_backfill.py`, `test_organiser_entitlement.py`.
- **Organiser verification moderation (`moderation_router.py`, `service/organiser_verification.py`, over `organisations.service.admin_set_verified`):** staff routes under `/admin/moderation/organisers`: `GET` (queue by `status`, default `pending`, oldest first) and `GET /{organisation_id}` are open to moderators and superusers (`ModerationReader`); `POST .../approve` and `.../reject` (reason required) need an MFA superuser (`MfaAdminUser`). Approve queues outbox `organiser.approved`; reject queues `organiser.rejected` with the reason (notification `events.organiser_rejected`). `POST /events/manage/organiser/resubmit` (owner/admin of the organiser) puts a rejected organiser back to `pending` (409 otherwise). `GET /events/moderation/organisers` (pending only) stays for Events moderators; `PATCH /events/moderation/organisers/{id}` is MFA superuser only, goes through the same path and answers 409 for a rejected organiser. Activity actions `organiser.verified|unverified|rejected|resubmitted`. Tests: `test_moderation_admin.py`, `test_organiser_verification.py`.
- **Stored images (F8, `events_0007`):** `organisers.logo_file_id` and `listings.image_file_id` hold ids of completed `org.upload` rows (no cross-database FK). A changed id must pass `storage.uploads.file_is_usable` for the organiser's organisation and the purpose (`organiser-logo` / `listing-image`), else 409; unchanged ids are not re-checked, so legacy data stays valid. `ListingUpsert.image_file_id` sets the cover; `PUT /events/manage/organiser/logo` sets or clears the logo (activity `organiser.logo_changed`). Responses carry the ids (`ListingCard.image_file_id`, `OrganiserPublic.logo_file_id`); the web app renders them through its `/files/{id}` route. Tests: `test_stored_images.py`.
- `listings` is the event table (avoids clashing with "event" elsewhere). Only `status='published'` + `visibility='public'` appear in lists; unlisted published listings open by slug.
- Business rules live in the `service/` package, split by area and re-exported from `service/__init__.py` so `service.<name>` still works: `common` (constants, Grenada time windows), `people` (profiles, blocks, connections, `can_message`), `discover` (listings, organisers, groups), `messaging`, `network` (person pages, plans, network), `moderation`, `organiser_admin`. Imports only point one way: `common` ← `people` ← `discover` ← `organiser_admin`, `messaging` ← `people`, `network` ← `discover`/`messaging`/`people`. Do not add an import that closes a cycle (listings and groups are one module because they call each other).
- Safety rules live in `service/` (mainly `people.py` and `messaging.py`) and must hold for every client: DMs only between accepted connections or shared active group members (`can_message`, re-checked on every send); blocks hide both people from each other (profiles 404, going previews, members, messages) and drop any connection; `visibility='connections'` profiles expose only name/headline outside the network; join requests to `approval` groups stay `pending` with no chat access.
- Times are stored naive UTC; `when` windows (`tonight`/`weekend`/`week`/`month`) use Grenada calendar days (UTC−4, no DST).
- Tests: `tests/events/` on the main test database (`events_db` in `conftest.py` returns a session factory over the cleaned DB and overrides `deps.get_session`); helpers in `support.py` (`client_as` overrides `deps.get_session`, `deps.require_member`, `deps.optional_member`, `deps.require_organiser`). Organiser and moderator gates are tested for real with `client_with_real_roles` plus `roles.user_with_role` (main auth DB via `db_async`); never override them to test permissions. Files: `test_events_api.py` (listings, RSVP, safety rules), `test_when_window.py`, `test_network.py`, `test_groups.py`, `test_messaging.py`, `test_organiser_admin.py`, `test_moderation.py`. Auth flows: `tests/auth/test_app_scoped.py`.
- Related: ADR-0003, ADR-0016, `docs/products/barrels-events-v1-definition.md`.
- **Barrels staff operations (ADR-0050, Proposed; not built):** staff run organisers' events through global keys `events.ops.door|till|refunds|settlement|listings` in roles `events-staff-door|till|refunds|manager`, accepted only on org-zone routes via `require_org_permission_or_staff(org_key, staff_key, session_app="events")` (member path first; staff need the key through a role, never superuser-implied; unknown organisation or missing key 404; MFA for all but door). Every route ported from `/events/manage/*` gets its staff-key pair (`docs/exec-plans/events-legacy-manage-routes.md`). Activity gets `actor_capacity` (`member|staff`, shown to organisers as "Barrels staff"); staff reads of attendee/order lists log ids only; staff writes are rate-limited per user. Do not give staff a path to `events.team.manage`.
