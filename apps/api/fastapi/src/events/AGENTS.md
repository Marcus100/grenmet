# events domain — agent context

**Owner:** Barrels product (Barrels Events, `apps/web/events`; PWA `apps/pwa/pwa-events` next). Not a GAA/GMS module.

- Separate, self-contained database with its own Alembic history (`alembic.ini`, `migrations/`, revisions `events_NNNN`, version table `events_alembic_version`). People are auth `user_id` UUIDs; never a cross-database FK. Migrations are hand-written SQL and **additive**; models in `models.py` on `events_metadata` mirror them (never autogenerate).
- `EVENTS_DATABASE_URL` is optional when running the API alone; `/events` routes return 503 while unset. The deployed Events website requires its database, so core delivery validates `EVENTS_DB_PASSWORD` before provisioning/migration.
- Auth is app-scoped (ADR-0016): member routes use `EventsMember` (`app_user("events")`), public reads use `EventsViewer` (optional). Staff tokens are refused here; Events tokens are refused on staff routes. Organiser routes need `events.organiser.manage` **and** `organiser_members` membership; moderation needs `events.moderate`.
- **Organiser to organisation bridge (F5, ADR-0022):** `organisers.organisation_id` (migration `events_0002`, unique, no cross-DB FK) holds the `org.organisation.id` backing the organiser. `require_organiser` passes with `events.organiser.manage` or an active admin/owner platform membership; `organiser_scope` lists those organisation ids and the service resolves the organiser (`?organiser=<slug>` picks one when several). Once an organiser is linked, platform membership is authoritative; the legacy `organiser_members` row only counts while `organisation_id` is NULL. `service.create_organiser` creates the platform organisation plus owner membership. Backfill: `python -m src.events.backfill [--dry-run]` (idempotent; platform id is `org_<first 16 hex of organiser id>`; lowest user id becomes owner, others admin). Tests: `test_organiser_platform.py`.
- **Organiser requests:** `POST /events/manage/organiser` (any Events member, 5/hour) calls `service.request_organiser`: `create_organiser` with `verified=false` (pending), one pending request per member (409). Moderators list `GET /events/moderation/organisers` and verify with `PATCH /events/moderation/organisers/{id}` (`{verified}`). Verification (platform organisation `verified_at` when linked, else the legacy flag) gates publishing: only verified organisers can move a listing to `published` (403 `Only verified organisers can publish events…`); unverified organisers can save drafts. `scripts/seed_events_demo.py` (local, after `initial_data.py` in prestart) creates organisers through the service, owned by `--owner-email` (default first superuser). Tests: `test_organiser_request.py`, `test_seed_demo.py`.
- **Outbox (F6, `events_0003`, `outbox.py`, `notifications.py`):** `outbox.enqueue` adds a row to the caller's Events session (`ON CONFLICT (dedupe_key) DO NOTHING`), so it commits with the change. Kinds: `listing.published` (followers of the organiser, public listings only), `listing.cancelled`, `listing.postponed` (going + saved members; start time changed on a published listing), `organiser.approved` (active owners/admins of the backing platform organisation). The ARQ job `drain_events_outbox` (every 30 s) calls `outbox.drain`: one transaction per row, recipients resolved at drain time, `notifications.notify(dedupe_key=row.dedupe_key)` so a repeat tells nobody twice, failures back off 30 s doubling to 1 h and give up after 6 attempts (`failed_at`). Payloads hold ids and public labels only. Notification emails carry no deep link (the notifications base URL is the staff portal). Tests: `test_outbox.py`, `tests/worker/test_events_outbox_job.py`.
- **Activity log (F7, `events_0004`, `activity.py`):** append-only `activity` table (a trigger rejects UPDATE and DELETE). Every organiser and moderation mutation writes exactly one row in the change's transaction: `organiser.created` (in `create_organiser`), `organiser.verified`/`unverified` (only when the flag changes), `listing.created|updated|published|rescheduled|cancelled`, `report.actioned|dismissed`, `suggestion.approved|rejected`. Rows hold the actor's auth user id, the entity and a summary of changed field names plus short public before/after values (title, status, times); no names, emails or free text. `GET /events/manage/{listing_id}/activity` (organiser of that listing only, newest first) joins the actor's current profile name at read time; `/dash/events/[id]` renders it as the History panel. Tests: `test_activity.py`.
- **Orders and tickets (E1, `events_0005`, `tickets.py`, `service/ticketing.py`):** `orders`, `order_items`, `tickets` (+ `ticket_tiers.per_account_limit`, default 4). Free and registration tiers issue tickets at once; paid tiers are the N4b flow below. Inventory is the count of `valid` tickets per tier plus the stock held by unpaid orders (`service/holds.py`); `claim_tickets` locks the requested tier rows `FOR UPDATE` (id order) before checking allocation and the per-account limit, so sold never exceeds allocation. Cancelling sets `cancelled` and releases the seat; only before the event starts. Ticket `code` is random and opaque; the QR token `BT1.<code>.<hmac>` is signed with the app `SECRET_KEY` and holds no personal data. `_sync_tiers` updates tiers in place (`TierInput.id`) and refuses to remove or shrink tiers below issued tickets. Outbox kind `ticket.issued` notifies the buyer. Tests: `test_tickets.py`.
- **Door admission (E2, `events_0006`, `service/admission.py`):** `admissions` has a unique `ticket_id`, so a ticket is admitted once even when two devices scan together (the ticket row is locked `FOR UPDATE`). `POST /events/manage/{listing_id}/admissions` takes the QR token or a typed code (`tickets.code_from_scan`; tokens are signature-checked) and an optional client `idempotency_key`: the same key replays its own success (`repeat=true`), any other second scan is 409 `Already admitted at HH:MM by <name>` (Grenada time). Cancelled tickets and other events' tickets are refused; used tickets cannot be cancelled. Each admission writes a `ticket.admitted` activity row on the listing (ticket id, tier, method; no names). `GET /events/manage/{listing_id}/manifest` lists valid tickets with holder name, tier and admission time plus `issued/admitted/waiting/cancelled` counts. Same organiser gate as listing management (404 for another organiser's event). Tests: `test_admission.py`.
- **Outlet cash (E3, `events_0008`, `service/outlet.py`):** the organiser's own staff sell tickets for cash (`POST /events/manage/{listing_id}/outlet/sales`; screen data `GET .../outlet`; reprint `GET .../outlet/sales/{order_id}`). Who: the same people as door admission, i.e. active platform admin/owner (or legacy organiser member); plain `member` staff are deliberately excluded because they would handle cash. Outlet orders have `channel='outlet'`, `payment_method='cash_outlet'`, null `user_id` on the order and its tickets (buyer name/phone optional, stored on the order only), `collected_minor` that must equal the price total (409 otherwise) and an optional `idempotency_key` (replay returns the original sale, `repeat=true`). Inventory is shared with online claims: both lock tier rows `FOR UPDATE` in id order and count `valid` tickets, and both take a shared lock on the listing row; the per-account limit applies online only. A sale needs the caller's open `till_sessions` row (one per staff, listing and Grenada day: `POST .../outlet/till` with an opening float, `POST .../outlet/till/close` with the counted cash; expected = float + takings, difference = counted - expected). Activity: `till.opened`, `till.closed`, `ticket.sold_outlet` (ids and amounts only, no buyer details). Tests: `test_outlet.py`.
- **Settlement (E4, `service/settlement.py`):** `GET /events/manage/{listing_id}/settlement` (same gate as door/outlet), `GET .../settlement.csv` (download; text cells starting `= + - @` are prefixed with `'`) and `GET /events/manage/settlement` (one summary row per ticketed, non-draft event). Counts come from `tickets` joined to the order channel (`online`, `outlet_cash`) and `admissions`: `issued` (all), `claimed` (valid), `admitted`, `waiting` (valid, not admitted), `cancelled`, `refunded`, `value_minor` (face value of claimed). Cash comes from `till_sessions`: expected = float + takings - cash refunds; closed tills are compared with the count. Mismatches are listed in `discrepancies` (`till_short`, `till_over`, `till_open` once the event ended or was cancelled, `refund_without_till`, `online_ledger_mismatch`), never netted away. N4b adds `online_payments` (below) and the online channel's `collected_minor`/`refunded_minor`. Tests: `test_settlement.py`, `test_paid_orders.py`.
- **Cancel, postpone and refund (E5, `events_0009`, `service/cancellation.py`):** `POST /events/manage/{listing_id}/cancel` (`{confirm: true}`) takes the exclusive listing row lock (claims and outlet sales hold a shared one), sets the event `cancelled`, cancels every valid ticket (`ticketing.cancel_valid_tickets`; saving a listing as cancelled through `PUT` does the same), queues `listing.cancelled` and writes `listing.cancelled` activity with `tickets_cancelled`. Only a published event can be cancelled or postponed. `POST .../postpone` (`{starts_at, ends_at}`, new start in the future and different) keeps tickets valid, queues `listing.postponed` (dedupe by new start) and writes `listing.rescheduled`. The outbox audience for cancelled/postponed is going + saved members + ticket holders. `POST .../tickets/{ticket_id}/refund` (`{amount_minor, method: cash|bank, reference?}`) records a manual refund (`refunds`, one per ticket): outlet cash tickets only (an online-paid ticket is refunded through the payments core instead, see N4b), amount at most the paid unit price, bank needs a reference, a used ticket only when the event was cancelled, a holder-cancelled ticket never. The ticket becomes `refunded` (not admittable, seat released) and a cash refund links to the refunding staff member's open till (subtracted from its expected cash; with no open till settlement flags `refund_without_till`). Activity `ticket.refunded` holds ids, amount and method, never the reference. Tests: `test_cancellation.py`.
- **Paid tiers (N4b, `events_0010`, ADR-0027; test-mode Stripe or the manual rail only):** `orders` gains `payment_intent_id` (plain UUID of `payments.intent.id`, indexed, **no FK**: ADR-0003), `payment_expires_at`, `paid_at`, `refunded_minor`, and `payment_method` may be `online`. Order `status`: `confirmed` (free, outlet, paid) | `pending_payment` | `expired` | `refunded`. `claim_tickets(db, user, slug, body, main=, idempotency_key=)` with a total above zero: requires the organiser's organisation to hold the `payments` entitlement (else 409 "...online payment isn't available for this event"), counts valid tickets **plus `pending_payment` order items** against the allocation and the per-account limit (tier rows locked `FOR UPDATE`, so overselling is impossible), creates the order `pending_payment` with `payment_expires_at = now + EVENTS_ORDER_HOLD_MINUTES` (default 30) and commits Events, then creates the intent on the main database through `order_payments.ensure_intent` (`source_type="events.order"`, `source_id=<order id>`, key `events.order:<order id>`, `actor=None`, metadata `order_id` + `listing_id`) and records its id on the order. Not atomic by design: a retry finds the intent by its key; an order that never got one is expired by the sweeper; if the money side fails the hold is released at once. `Idempotency-Key` (optional header, stored on the order, unique per listing and member) makes a replay return the same order (looked up under the tier locks, so concurrent twins converge; other items with the same key: 409). Postgres deadlock-victim = a lost race (409, `ticketing.is_deadlock`, same rule as bookings). The order response is additive: `status`, `payment_required`, `checkout_url`, `payment_expires_at`; `GET /events/me/orders/{id}` polls it.
- **Paid tiers, payment and refund reactions (`order_fulfilment.py`, `payment_handlers.py`):** payments enqueues `events.order_paid` (charge) and `events.order_refunded` (each refund) on the platform outbox; the handlers (imported by the worker `startup` and `drain_outbox`) run on the main session and open their own Events session (`database.create_session`; tests monkeypatch it). No distributed transaction: main-database work first (refund, queued receipt, uncommitted), then the Events commit, then the outbox row commits; a crash replays the message and the order row lock plus its status make it idempotent. `fulfil_paid`: `pending_payment` and the event still on sale -> tickets created once (count guard), status `confirmed`, `collected_minor`/`paid_at` mirrored from the ledger, receipt email queued with `notifications.outbox_handlers.enqueue_email` (dedupe `events-order-paid:<order id>`, requeued on every replay, no `ticket.issued` notification for paid orders); `expired`, or the event cancelled/ended -> **full refund** via payments and no tickets; already `confirmed`/`refunded` -> no-op. A payments failure propagates so the outbox retries (5 attempts, then `dead`). `apply_refund`: mirrors the ledger onto the order; only a **full** refund moves valid tickets to `refunded` and the order to `refunded` (a partial refund keeps them). Sweeper: ARQ job `expire_unpaid_event_orders` (every 5 minutes) -> `order_fulfilment.expire_unpaid`: due `pending_payment` orders `FOR UPDATE SKIP LOCKED`, `cancel_open_intent` (False = payment just succeeded, skipped), main commit, then `expired`. A holder cannot self-cancel an online-paid ticket (409; refund through payments). Not built: automatic refunds when the organiser cancels the event, and cancelling pending orders then (a later payment is refunded by the handler). Settlement `online_payments` compares the orders' `collected_minor`/`refunded_minor` with the payments ledger summed by `metadata.listing_id` (`order_payments.ledger_totals`); the routes pass the main session. Rewards: `rewards.events_link` counts only `confirmed` orders, so unpaid or expired orders never earn. Tests: `test_paid_orders.py`, `test_paid_orders_migration.py`, `tests/payments/test_refund_topics.py`, `tests/worker/test_event_order_jobs.py`.
- **Stored images (F8, `events_0007`):** `organisers.logo_file_id` and `listings.image_file_id` hold ids of completed `org.upload` rows (no cross-database FK). A changed id must pass `storage.uploads.file_is_usable` for the organiser's organisation and the purpose (`organiser-logo` / `listing-image`), else 409; unchanged ids are not re-checked, so legacy data stays valid. `ListingUpsert.image_file_id` sets the cover; `PUT /events/manage/organiser/logo` sets or clears the logo (activity `organiser.logo_changed`). Responses carry the ids (`ListingCard.image_file_id`, `OrganiserPublic.logo_file_id`); the web app renders them through its `/files/{id}` route. Tests: `test_stored_images.py`.
- `listings` is the event table (avoids clashing with "event" elsewhere). Only `status='published'` + `visibility='public'` appear in lists; unlisted published listings open by slug.
- Business rules live in the `service/` package, split by area and re-exported from `service/__init__.py` so `service.<name>` still works: `common` (constants, Grenada time windows), `people` (profiles, blocks, connections, `can_message`), `discover` (listings, organisers, groups), `messaging`, `network` (person pages, plans, network), `moderation`, `organiser_admin`. Imports only point one way: `common` ← `people` ← `discover` ← `organiser_admin`, `messaging` ← `people`, `network` ← `discover`/`messaging`/`people`. Do not add an import that closes a cycle (listings and groups are one module because they call each other).
- Safety rules live in `service/` (mainly `people.py` and `messaging.py`) and must hold for every client: DMs only between accepted connections or shared active group members (`can_message`, re-checked on every send); blocks hide both people from each other (profiles 404, going previews, members, messages) and drop any connection; `visibility='connections'` profiles expose only name/headline outside the network; join requests to `approval` groups stay `pending` with no chat access.
- Times are stored naive UTC; `when` windows (`tonight`/`weekend`/`week`/`month`) use Grenada calendar days (UTC−4, no DST).
- Tests: `tests/events/` on a disposable migrated DB (`events_db` in `conftest.py`, via `fresh_weather_engine`); helpers in `support.py` (`client_as` overrides `deps.get_session`, `deps.require_member`, `deps.optional_member`, `deps.require_organiser`). Organiser and moderator gates are tested for real with `client_with_real_roles` plus `roles.user_with_role` (main auth DB via `db_async`); never override them to test permissions. Files: `test_events_api.py` (listings, RSVP, safety rules), `test_when_window.py`, `test_network.py`, `test_groups.py`, `test_messaging.py`, `test_organiser_admin.py`, `test_moderation.py`. Auth flows: `tests/auth/test_app_scoped.py`.
