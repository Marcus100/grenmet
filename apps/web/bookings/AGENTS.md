# Barrels Bookings (`@barrelsgd/web-bookings`) — agent context

Port **3015**, host `bookings.${BASE_DOMAIN}` (`bookings.barrels.gd` in production). Design lane: `docs/design/bookings.md` (read before UI work). Product decision: `docs/exec-plans/product-and-hardening-handoff.md` (A1). Backend and domain: `apps/api/fastapi/src/bookings/AGENTS.md` and ADR-0024.

## Status: public booking flow and staff studio live

State on 14 Nov 2026: the app is live on production (deployed before v1.0.8). Babydoll Beauty Bar, the pilot tenant, is seeded on staging, where a test booking made on the public page appeared as pending in the Studio agenda and was confirmed; it is **not** seeded on production yet, so `/babydoll-beauty-bar` answers "not found" there. Time off per provider is in v1.0.8. On `dev`, not released: prices show with the currency (`EC$210`, #1394). Go-live order: `docs/operations/babydoll-cutover.md`.

`/[slug]` is the public booking flow for any business: storefront (name, services with duration, price and deposit label, providers), then the shared `@barrelsgd/bookings-web` flow (service, time, details, confirm), then `/[slug]/booking/[token]` to view, reschedule or cancel (plus `/ics` for the calendar file). The staff studio (`/studio`) is sign-in-guarded and built (see Studio below).

The page asks `loadVisitor(slug)` (`src/lib/signed-in-visitor.ts`) who is signed in (`getSession`; a fault counts as a guest and is reported). A signed-in person gets their own name (`fullName`, never the email stand-in), email and phone prefilled and still editable, a "Booking as <name>. Not you? Sign out" line (POST to `/auth/logout`, which lands on auth's signed-out page, not back here), and "Book again" shortcuts from `GET /bookings/me/businesses/{slug}/choices` called with their own token; the full service list stays below. If that call fails the session's name and email still prefill. A guest gets a blank form, the invitation and a sign-in link (below). The booking itself is unchanged: a signed-in booking with a verified matching email links the contact to the account (ADR-0058). The proxy sets `Cache-Control: private, no-store` on every response to a request that carries the session cookie, so a page with a person's details is never stored. Nothing personal goes to Sentry or logs. There is no sign-in link on the public page: a customer's bookings-app session exists only after `/signin` (known gap).

For guests the page passes `accountInvite` to the booking flow; the confirmation then invites them to create an account or sign in. The link is the auth app's `/signup?returnTo=<this app>/signin?returnTo=/<slug>` (`src/lib/sign-in-links.ts`; this app's origin comes from the forwarded host, and auth refuses an origin that is not on its return-host allow-list, `AUTH_ALLOWED_RETURN_HOSTS`, which includes `https://bookings.${BASE_DOMAIN}` in the deploy compose), so a new account comes back signed in to the booking page. Guests also see a quiet "Sign in" link under the heading (`/signin?returnTo=/<slug>`). `AUTH_APP_URL` here and `AUTH_FRONTEND_URL` in the API (invitation emails) must name the same auth app; `tests/bookings/test_account_invite.py` checks the deploy compose file.

Host wiring mirrors `apps/web/babydoll`: `src/lib/booking-api.ts` (server-only, generated client, every call takes the slug), `src/lib/booking-errors.ts` (`failureFrom`), Server Actions in `src/app/[slug]/actions.ts` and `booking/[token]/actions.ts`, `src/components/booking-link.tsx` (router-aware manage link). The page binds the slug into each action (`loadSlots.bind(null, slug)`) so the package's action shapes stay unchanged; actions re-check the slug. The package carries class names only: `src/app/booking.css` is the host's side, built from the shared semantic tokens (light mode, no `--gm-*`). Turnstile site key is `NEXT_PUBLIC_TURNSTILE_SITE_KEY` (empty: no widget); the API enforces per-site policy and the honeypot. Unknown or switched-off slugs call `notFound()` (a real 404, so there is deliberately no `loading.tsx`). A `notFound()` thrown while a dynamic page renders makes Next 16 send an empty error document (`<html id="__next_error__">`) that only fills in with JavaScript, so `src/proxy.ts` answers a full page load of `/<slug>` first: a slug that cannot be a business, or one the API answers 404/422 for (`src/lib/storefront-exists.ts`, answers kept one minute), is rewritten to Next's `/_not-found`, rendered on the server with status 404. Client navigations (`RSC` header) and API failures fall through to the page. `/[slug]/booking/[token]` is handled the same way for a full page load: the proxy asks the API whether the token is known (`src/lib/booking-link-exists.ts`, nothing kept, the token is a secret) and answers an unknown one with status 404 on the same address (`rewrite` to itself), while the page itself words the dead link (`src/components/missing-booking.tsx`: names the business, says what to do next) instead of calling `notFound()`; a business with no booking page gets the plain not-found page. A valid manage page load therefore costs two API reads.

## Boundary

- `/` is public: what Barrels Bookings is.
- `/[slug]` is the public booking page for one business (any tenant). It shows the business name from the API, never a name typed into this app. A business with no services says online booking is not open.
- `/studio` is staff only, behind a Barrels sign-in. The agenda, booking detail, New booking, Record deposit and Settings live here.
- Backend logic stays in FastAPI (`/bookings/public/*`, `/bookings/org/*`). Route handlers may only validate, proxy or render. Never add database access or booking rules here.
- Server Components by default. Client Components only for interaction. React Query only for client-side mutations and polling; generated clients and types come from `@barrelsgd/api-client`.

## Auth (ADR-0016/0017)

- Registry key `bookings`, registered in `apps/api/fastapi/src/auth/apps.py` (API config `BOOKINGS_APP_URL`, `BOOKINGS_SSO_CLIENT_SECRET`). `src/lib/auth-config.ts` (`APP_NAME`) names it. Sign-in only completes where the API has both set.
- Flow: `/signin` -> `/auth/start` -> auth.barrels.gd -> `/auth/callback` (redeems the code with `BOOKINGS_SSO_CLIENT_SECRET`; without it the callback returns 503). Session cookie `bookings_session`, host-only. `src/proxy.ts` checks only that the cookie exists for `/studio`; `src/lib/session.ts` (`requireSession`) exchanges it on the server for an app-scoped access token (`app = "bookings"`).
- Studio calls to FastAPI: send that token as the bearer plus `X-Barrels-Organisation: <organisation id>`. The API accepts the bookings session on every `/bookings/org/*` route and on `GET /bookings/me/organisations`, which lists the caller's bookings organisations for the picker (ADR-0016 amendment; `apps/api/fastapi/src/bookings/AGENTS.md`). Membership, role and entitlement are decided by FastAPI each call; this app never decides access. The studio screens are listed under Studio below.
- Reserved paths: `studio`, `signin`, `auth` and `api` are app routes and win over `/[slug]`, so a business with one of those slugs would be unreachable. Avoid them when creating a profile. The API currently rejects only `bookings` (`RESERVED_SLUGS` in `src/bookings/schemas.py`); extending it is pending.
- Never read `process.env` outside `src/env.ts` (plus the Sentry and `next.config` exceptions).

## Studio (`/studio`)

- `/studio` is the organisation picker (`listMyOrganisations`; one business goes straight on). `/studio/[orgSlug]` itself redirects to `agenda`. Under `/studio/[orgSlug]/`: `agenda` (read, grouped by local day), `bookings/[id]` (detail, confirm/change time/decline/cancel/no-show/complete in `booking-actions.tsx`; "Change time" is offered for a pending request (even after its start time, to a future time) and for a confirmed booking that has not started (`availableActions`); it asks for a date and time on the business's clock, calls `POST .../reschedule` and says the customer is emailed; a clash answers "That time is not free"; owner/admin "Record deposit received" in `record-deposit.tsx`), `bookings/new` (staff New booking, business-timezone today) and `settings` (profile, services, providers, weekly hours, time off per provider: `components/studio/settings/time-off.tsx`, `lib/time-off.ts`; the API has no update, so an edit is a remove and an add). Time off makes one request per provider (there is no organisation-wide list endpoint); a failure blanks only that provider's section with an inline message, and the rest of Settings stays editable. A wall-clock time in a spring-forward gap resolves to one instant (`zonedToUtcIso` moves it an hour later), never two. The organisation id always comes from the person's own list, never the URL. Server actions sit beside each page (`actions.ts`) and call FastAPI through `src/lib/studio-api.ts`; refusals map through `src/lib/studio-errors.ts` and return `ActionState` (`studio-action-state.ts`). FastAPI decides role and entitlement each call; a 403 shows plain wording, not a retry.
- Money and create actions carry an `Idempotency-Key` made on mount, kept after a timeout or server fault and rotated after a refusal (`rotatesKey` in `studio-view.ts`).
- The Settings forms keep typed values with `keepTyped` (`components/studio/settings/settings-ui.tsx`). Forms that are driven by `useActionState` and whose success redirects or unmounts submit through `keepValuesOnSubmit` (`src/lib/keep-values.ts`) so a refusal keeps what was typed. A form with only an `onSubmit` handler disables its submit until `useHydrated()` (`src/lib/use-hydrated.ts`) is true (New booking does; the Settings forms do not yet, a known gap tracked in a follow-up issue). Rules: `docs/agents/extended-rules.md`, Form patterns.

## Env, errors and tests

- Typed env: `src/env.ts` (`docs/env.md`, section bookings). The Sentry DSN comes from the shared catalogue (`SENTRY_DSN_<APP>` in render-env).
- Unexpected errors throw to `error.tsx` / `global-error.tsx`. A caught error that shows a fallback calls `reportError(error, "<area>")` from `src/lib/report-error.ts`.
- Tests: `pnpm --filter @barrelsgd/web-bookings test` (jsdom, fixed values in `vitest.config.ts`).
- CSP is Report-Only through `packages/ui` `APP_SOURCES.bookings` (Turnstile allowed for the booking form).

## Deployment

Compose service `web-bookings` with its own Traefik router and certificate (`bookings.${BASE_DOMAIN}`), release scope in `scripts/ci/release-scope.mjs`, service-catalogue entry in `packages/ui/src/lib/service-catalogue.json`, monitor in `scripts/monitoring/betterstack.json` (paused, deferred). `NEXT_PUBLIC_TURNSTILE_SITE_KEY` is inlined at build time, so the Dockerfile/build workflow needs it as a build arg before the widget shows in production (not wired yet). Needs a DNS record for `bookings.*` and the GitHub secret `BOOKINGS_SSO_CLIENT_SECRET` (optional: empty keeps sign-in off).
