# Barrels Bookings (`@barrelsgd/web-bookings`) — agent context

Port **3015**, host `bookings.${BASE_DOMAIN}` (`bookings.barrels.gd` in production). Design lane: `docs/design/bookings.md` (read before UI work). Product decision: `docs/exec-plans/product-and-hardening-handoff.md` (A1). Backend and domain: `apps/api/fastapi/src/bookings/AGENTS.md` and ADR-0024.

## Status: public booking flow and staff studio live

The app is live on production. Go-live order: `docs/operations/babydoll-cutover.md`.

`/[slug]` is the public booking flow for any business: storefront (name, services with duration, price and deposit label, providers), then the shared `@barrelsgd/bookings-web` flow (service, time, details, confirm), then `/[slug]/booking/[token]` to view, reschedule or cancel (plus `/ics` for the calendar file). The staff studio (`/studio`) is sign-in-guarded and built (see Studio below).

The page asks `loadVisitor(slug)` (`src/lib/signed-in-visitor.ts`) who is signed in (`getSession`; a fault counts as a guest and is reported). A signed-in person gets their own name (`fullName`, never the email stand-in), email and phone prefilled and still editable, a "Booking as <name>. Not you? Sign out" line (POST to `/auth/logout`, which lands on auth's signed-out page, not back here), and "Book again" shortcuts from `GET /bookings/me/businesses/{slug}/choices` called with their own token; the full service list stays below. If that call fails the session's name and email still prefill. A guest gets a blank form, the invitation and a sign-in link (below). The booking itself is unchanged: a signed-in booking with a verified matching email links the contact to the account (ADR-0058). The proxy sets `Cache-Control: private, no-store` on every response to a request that carries the session cookie, so a page with a person's details is never stored. Nothing personal goes to Sentry or logs.

For guests the page passes `accountInvite` to the booking flow; the confirmation then invites them to create an account or sign in. The link is the auth app's `/signup?returnTo=<this app>/signin?returnTo=/<slug>` (`src/lib/sign-in-links.ts`; this app's origin comes from configuration, `NEXT_PUBLIC_SITE_URL` (the deploy sets `https://bookings.${BASE_DOMAIN}`; unset gives the plain sign-up page with no return target), never from request headers, and auth refuses an origin that is not on its return-host allow-list, `AUTH_ALLOWED_RETURN_HOSTS`, which includes `https://bookings.${BASE_DOMAIN}` in the deploy compose), so a new account comes back signed in to the booking page. Guests also see a quiet "Sign in" link under the heading (`/signin?returnTo=/<slug>`). `AUTH_APP_URL` here and `AUTH_FRONTEND_URL` in the API (invitation emails) must name the same auth app; `tests/bookings/test_account_invite.py` checks the deploy compose file.

Host wiring mirrors `apps/web/babydoll`: `src/lib/booking-api.ts` (server-only, generated client, every call takes the slug), `src/lib/booking-errors.ts` (`failureFrom`), Server Actions in `src/app/[slug]/actions.ts` and `booking/[token]/actions.ts`, `src/components/booking-link.tsx` (router-aware manage link). The page binds the slug into each action (`loadSlots.bind(null, slug)`) so the package's action shapes stay unchanged; actions re-check the slug. The package carries class names only: `src/app/booking.css` is the host's side, built from the shared semantic tokens (light mode, no `--gm-*`). Turnstile site key is `NEXT_PUBLIC_TURNSTILE_SITE_KEY` (empty: no widget); the API enforces per-site policy and the honeypot. Unknown or switched-off slugs call `notFound()` (a real 404, so there is deliberately no `loading.tsx`). A `notFound()` thrown while a dynamic page renders makes Next 16 send an empty error document (`<html id="__next_error__">`) that only fills in with JavaScript, so `src/proxy.ts` answers a full page load of `/<slug>` first: a slug that cannot be a business, or one the API answers 404/422 for (`src/lib/storefront-exists.ts`, answers kept one minute), is rewritten to Next's `/_not-found`, rendered on the server with status 404. Client navigations (`RSC` header) and API failures fall through to the page. `/[slug]/booking/[token]` is handled the same way for a full page load: the proxy asks the API whether the token is known (`src/lib/booking-link-exists.ts`, nothing kept, the token is a secret) and answers an unknown one with status 404 on the same address (`rewrite` to itself), while the page itself words the dead link (`src/components/missing-booking.tsx`: names the business, says what to do next) instead of calling `notFound()`; a business with no booking page gets the plain not-found page. A valid manage page load therefore costs two API reads.

Storefront extras (public pages only): `accepting_bookings: false` renders `PausedNotice` (calm message plus the contact links) in place of the header text, contact strip, providers and flow; a `BUSINESS_PAUSED` 409 inside the flow does the same. `src/lib/booking-errors.ts` passes the API's `code` to `classifyFailure`. Business-collected deposits, the late fee and new-clients-only services are described in `packages/bookings-web/AGENTS.md`; host CSS for them is `.service-badge`, `.deposit-business`, `.deposit-instructions` and `.paused-notice` in `booking.css` (existing tokens only).

## Boundary

- `/` is public: businesses that opted in.
- `/[slug]` is the public booking page for one business (any tenant). It shows the business name from the API, never a name typed into this app. A business with no services says online booking is not open.
- `/studio` is staff only, behind a Barrels sign-in. The agenda, booking detail, New booking, Record deposit and Settings live here.
- Backend logic stays in FastAPI (`/bookings/public/*`, `/bookings/org/*`). Route handlers may only validate, proxy or render. Never add database access or booking rules here.
- Server Components by default. Client Components only for interaction. React Query only for client-side mutations and polling; generated clients and types come from `@barrelsgd/api-client`.

## Auth (ADR-0016/0017)

- Registry key `bookings`, registered in `apps/api/fastapi/src/auth/apps.py` (API config `BOOKINGS_APP_URL`, `BOOKINGS_SSO_CLIENT_SECRET`). `src/lib/auth-config.ts` (`APP_NAME`) names it. Sign-in only completes where the API has both set.
- Flow: `/signin` -> `/auth/start` -> auth.barrels.gd -> `/auth/callback` (redeems the code with `BOOKINGS_SSO_CLIENT_SECRET`; without it the callback returns 503). Session cookie `bookings_session`, host-only. `src/proxy.ts` checks only that the cookie exists for `/studio`; `src/lib/session.ts` (`requireSession`) exchanges it on the server for an app-scoped access token (`app = "bookings"`).
- Studio calls to FastAPI: send that token as the bearer plus `X-Barrels-Organisation: <organisation id>`. The API accepts the bookings session on every `/bookings/org/*` route and on `GET /bookings/me/organisations`, which lists the caller's bookings organisations for the picker (ADR-0016 amendment; `apps/api/fastapi/src/bookings/AGENTS.md`). Membership, role and entitlement are decided by FastAPI each call; this app never decides access. The studio screens are listed under Studio below.
- Reserved paths: `studio`, `signin`, `auth` and `api` are app routes and win over `/[slug]`, so a business with one of those slugs would be unreachable. Avoid them when creating a profile. The API currently rejects only `bookings` (`RESERVED_SLUGS` in `src/bookings/schemas.py`); extending it is pending.
- Never read `process.env` outside `src/env.ts` (plus the Sentry and `next.config` exceptions).

## Studio (`/studio`)

- Shell (design: `docs/design/bookings.md`, Studio): the studio is on the shared admin kit (`@barrelsgd/admin-kit`, ADR-0068, `docs/web/admin-kit.md`). `src/app/studio/layout.tsx` sets metadata (never indexed, manifest, theme colour) and mounts `ThemeBootScript` and `PreferencesStoreProvider` from `@barrelsgd/theme` for the studio routes only (light, sticky top bar; the public booking pages never carry them). `[orgSlug]/layout.tsx` draws `StudioShell` (`components/studio/studio-shell.tsx`: `AdminShell` with the business as the brand, a navy "B" mark, New booking in the top bar for owners and admins, sign out in the user menu) after reading the organisation (name, role), the profile (public page link) and the waiting count; a failed read leaves that piece out and is reported. The one navigation config is `lib/studio-navigation.tsx` (`studioNavigation`, filtered by role with `filterNavigation`; Agenda, Services and People are the phone tab bar, the kit adds More; the waiting count is Agenda's badge; "View my page" opens in a new tab). The studio is light only: its surfaces have no dark values, so the theme switcher and the layout controls (which carry mode and colour preset) are off.
- Studio navigation details: Agenda lists `activePrefixes` for `/bookings/`, so it stays current on a booking's detail page while New booking (a direct match) stays current on `/bookings/new`. The business name also sits in the top bar on phones (the `breadcrumb` slot, hidden from md up). A plain frame under `/studio/<slug>` renders its own skip link (`StudioSkipLink`), because `RootSkipLink` steps aside there.
- Studio pages and tests: `/studio` (the picker) uses `StudioPlainFrame`. Pages use the kit's `PageHeader` and `studio-ui.tsx` (`CARD`, action classes); content stays at `max-w-4xl` inside the shell. Tests mock `AdminShell` with the kit's frame (`src/test/admin-shell.tsx`) because it is an async Server Component.
- Studio agenda: it opens with `NeedsConfirming` (`pending` bookings, `lib/studio-pending.ts`, one cached call shared with the shell's count; confirming or declining revalidates the business layout so the count follows). Booking detail has Call and WhatsApp (`components/studio/contact-buttons.tsx`, `lib/phone.ts`). The install manifest is the route handler `src/app/studio-manifest.webmanifest/route.ts` (outside `/studio` because the proxy sends cookie-less requests under `/studio` to sign-in), icons in `public/studio-icons/`.
- `/studio` is the organisation picker (`listMyOrganisations`; one business goes straight on). `/studio/[orgSlug]` itself redirects to `agenda`. Under `/studio/[orgSlug]/`: `agenda` (read, grouped by local day), `bookings/[id]` (detail, confirm/change time/decline/cancel/no-show/complete in `booking-actions.tsx`; "Change time" is offered for a pending request (even after its start time, to a future time) and for a confirmed booking that has not started (`availableActions`); it asks for a date and time on the business's clock, calls `POST .../reschedule` and says the customer is emailed; a clash answers "That time is not free"; owner/admin "Record deposit received" in `record-deposit.tsx`; a deposit paid to the business is marked received in `deposit-received.tsx`, #1869), `bookings/new` (staff New booking, business-timezone today) and `settings` (profile, services, providers, weekly hours, time off per provider: `components/studio/settings/time-off.tsx`, `lib/time-off.ts`; the API has no update, so an edit is a remove and an add). Time off makes one request per provider (there is no organisation-wide list endpoint); a failure blanks only that provider's section with an inline message, and the rest of Settings stays editable. A wall-clock time in a spring-forward gap resolves to one instant (`zonedToUtcIso` moves it an hour later), never two. The organisation id always comes from the person's own list, never the URL. Server actions sit beside each page (`actions.ts`) and call FastAPI through `src/lib/studio-api.ts`; refusals map through `src/lib/studio-errors.ts` and return `ActionState` (`studio-action-state.ts`). FastAPI decides role and entitlement each call; a 403 shows plain wording, not a retry.
- Settings › Profile › Home page: "Type of business" (`business_type`) and "Cover photo" (`cover_file_id`, upload purpose `booking-cover`, 5 MB, same three-step flow as the logo) save with the profile and feed the home page type tiles and card photos (`types_available` comes from the API; the page's `type` parameter is validated against `bookingBusinessType`).
- Settings › Brand: accent and logo save with the profile; `/[slug]` shows the logo and uses the accent only if it passes 4.5:1 (`lib/storefront-brand.ts`).
- Settings is six sections (`components/studio/settings/settings-sections.tsx`, with a jump menu): Profile (name, address, prices, notices, brand colour and logo, booking-page switch), Hours (per provider, with time off), Services, People, Payments and Contact. Each has its own form and Save button. The API replaces the whole profile on each write, so `saveProfileAction` reads the stored profile (`getProfile`) and takes a hidden `section` (`profile`, `contact` or `payments`), keeping the stored values for what the section leaves out. `/studio/<slug>/services` and `/people` render the same sections on their own pages; the studio nav links them. Every section renders, empty ones with what to do next. Payments also holds `deposit_collection` (`online` or `business`, "paid to me": no payments entitlement, `deposit_instructions` max 500, shown only in that mode; the card-choice radios are hidden then), the deposit rule and the booking policy with the late fee (`late_fee_minor`, blank or 0 sends null; `late_grace_min` 0 to 240). The service form's "Also offer as an add-on" (`also_add_on`) and "This is an add-on" are mutually exclusive. A section sends a new field only when its form carries it (`formData.has`), otherwise the stored value stays.
- `customers` (Business > Customers in the nav, every member): the read-only list from `GET /bookings/org/customers` (`listCustomers`, 50 a page). A GET form searches with `q` (name, email or phone); rows stack on a phone and show name, a `tel:` link, email, bookings, last visit and next booking on the business's clock. The search is personal data: it is never part of a sign-in return address, and `redactRequestAndQuery` drops the query string from a failed call before it is reported. No detail page, export or editing yet.
- The agenda shows "Complete your setup" to owners and admins while any of five steps is open (services, hours, booking page open, brand, payment choice). `lib/setup-checklist.ts` reads the saved settings only; nothing is stored, and the card hides once all five are done.
- New booking: the service is found by search. The open start times for the chosen service, provider and day come from `loadWalkInTimesAction`, which reads the public availability of the business's own address (`getAvailability`, never a form value). The chips fill the start time, which also takes any typed time (staff bookings ignore opening hours). A closed booking page answers "closed", because the public availability is 404 while it is off; a studio availability endpoint that works while closed is an API gap.
- `plan` is Plan & billing (ADR-0065), for owners and admins only. The nav link and the page check the role; a member gets the plain refusal before any billing call. It reads `GET /billing/org/subscriptions` and starts the Bookings plan with `POST /billing/org/subscriptions/checkout` (`plan_key` from `src/lib/billing-plan.ts`, XCD only). The action redirects only to `https://checkout.stripe.com`. A pending row reads "Checkout not finished" and calls the same checkout route again, which returns the open session's URL (PR 1727 contract, merged). Refusals map through `src/lib/billing-errors.ts`; a 401 is reported and never sent to sign-in, because that would loop. Stripe returns to `<BOOKINGS_APP_URL>/studio/<slug>/plan?checkout=success|cancelled` (the API builds the URL with the slug, PR 1730), read here as `?checkout=`. The page reads state only from the list; a trial shows only when the row has a future `trial_end` (trials are per organisation).
- New clients only (service form, `new_clients_only`, lead time and categories) is staff-side only: `returning_client` (agenda tag, detail notice) never reaches a public page. `paused_at` (from the layout's org list) draws `paused-banner.tsx` above every studio page.
- Money and create actions carry an `Idempotency-Key` made on mount, kept after a timeout or server fault and rotated after a refusal (`rotatesKey` in `studio-view.ts`).
- The Settings forms keep typed values with `keepTyped` (`components/studio/settings/settings-ui.tsx`). Forms that are driven by `useActionState` and whose success redirects or unmounts submit through `keepValuesOnSubmit` (`src/lib/keep-values.ts`) so a refusal keeps what was typed. A form with only an `onSubmit` handler disables its submit until `useHydrated()` (`src/lib/use-hydrated.ts`) is true: New booking and the Settings forms that render at page load (profile, services, providers, hours, the time-off add form). The Settings time-off remove form is not gated: it exists only inside a dialog that a click opens, which is after hydration. Rules: `docs/agents/extended-rules.md`, Form patterns.

- Closed days (`closed-days.tsx`, `lib/closures.ts`): whole-business closures under Settings > Hours; the API never cancels bookings inside one.

## Env, errors and tests

- Typed env: `src/env.ts` (`docs/env.md`, section bookings). The Sentry DSN comes from the shared catalogue (`SENTRY_DSN_<APP>` in render-env).
- Unexpected errors throw to `error.tsx` / `global-error.tsx`. A caught error that shows a fallback calls `reportError(error, "<area>")` from `src/lib/report-error.ts`.
- Tests: `pnpm --filter @barrelsgd/web-bookings test` (jsdom, fixed values in `vitest.config.ts`).
- Browser journey: `e2e/booking.spec.ts` (Playwright, `pnpm --filter @barrelsgd/web-bookings run test:e2e`) books a seeded Babydoll service as a guest and opens the manage link. It needs the API with the Babydoll seed (`scripts/verification/e2e-api.sh`) and runs in the `Browser journeys` workflow; a booking with a deposit (emailed code, Stripe) is not covered. See `docs/web/development.md`, Browser journeys.
- CSP is Report-Only through `packages/ui` `APP_SOURCES.bookings` (Turnstile allowed for the booking form).

## Deployment

Compose service `web-bookings` with its own Traefik router and certificate (`bookings.${BASE_DOMAIN}`), release scope in `scripts/ci/release-scope.mjs`, service-catalogue entry in `packages/ui/src/lib/service-catalogue.json`, monitor `Production · Bookings health` in `scripts/monitoring/betterstack.json` (active entry, created once the owner deletes three old Better Stack monitors; `docs/operations/analytics-monitoring.md`, Swap). `NEXT_PUBLIC_TURNSTILE_SITE_KEY` is passed to the container at run time (`infra/docker/docker-compose.deploy.yml`) and read through `readPublicEnv`. Needs a DNS record for `bookings.*` and the GitHub secret `BOOKINGS_SSO_CLIENT_SECRET` (optional: empty keeps sign-in off).
