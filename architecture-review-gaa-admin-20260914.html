Deepening opportunities in gaa-admin

This review identifies modules whose interface asks callers and maintainers to understand too many responsibilities at once. It uses the codebase-design vocabulary: module, interface, depth, seam, adapter, leverage, and locality.

Scope: read-only scan of apps/web/gaa-admin. No files in the repository were changed for this report. Existing ADRs support a modular monolith and separate domain databases; these candidates preserve those decisions.

Top recommendation

Deepen the forecast authoring module and retire the duplicate legacy forecast editor. The same concept currently appears in product-desk.tsx, forecast-editor.tsx, forecast-document.tsx, and two data paths. One interface should own schedule, validation, publication, and presentation rules; the public GMS adapter should consume the published product contract. This has the highest leverage because it spans the exact workflow that motivated the recent work and currently has two competing implementations.

Strong

1. Forecast authoring has two competing modules

Highest leverage

Files: src/components/wxproducts/product-desk.tsx (706 lines), src/components/wxproducts/forecast-editor.tsx (470), src/components/wxproducts/forecast-document.tsx (268), src/app/(admin)/wxproducts/product-actions.ts, src/lib/wxproducts/product-input.ts.

Problem: The product desk is the live authored-product module, while the older forecast editor has a separate form model and save action. Schedule rules, field names, PDF adaptation, validation, and persistence are distributed across both paths. The deletion test says deleting the old editor would remove a full alternate implementation rather than concentrate required complexity; that is a duplication smell. The interface is shallow because each caller must know which forecast representation and save path it is using.

Deepening opportunity: Make one forecast authoring module own the issue schedule, coverage periods, field visibility, validation, and publication result. Keep the PDF/document renderer as an internal adapter. Remove or explicitly quarantine the unused editor after callsite verification.

Benefits: Higher locality for schedule changes and CAP separation; one public adapter for GMS; fewer regression seams; tests can cross the authoring interface instead of separately testing two form models.

2. ProductDesk is a whole workflow hidden in one client module

Files: src/components/wxproducts/product-desk.tsx (706 lines), product-actions.ts, visible-fields.ts, product-pdf-preview.tsx.

Problem: One module owns product kind/date selection, dirty-state protection, async loading, editor state, revision concurrency, validation/review, publication, withdrawal, history, and PDF preview. A caller cannot use a smaller interface because all of those concerns are wired directly into one component. This is a deep implementation hidden behind a very large interface to its own JSX and event handlers, which reduces locality.

Deepening opportunity: Keep ProductDesk as the small orchestration interface, with internal modules for product selection/loading, editor lifecycle, review/publication actions, and revision history. The seam should be the product lifecycle result, not individual button callbacks.

Benefits: Each change has a local home; the publication lifecycle becomes testable through one seam; the page shell becomes easy to navigate; reuse across forecasts, bulletins, and NHC products improves leverage.

3. HR dashboard combines data assembly and four operational panels

Files: src/components/hr/dashboard/hr-dashboard.tsx (681 lines), src/components/hr/dashboard/dashboard-data.ts (324), src/app/(admin)/_components/home-data.ts (324).

Problem: Dashboard modules mix data loading, permission/empty/error states, date interpretation, summary calculations, and dense panel layout. The same operational facts are assembled in adjacent data modules with overlapping terminology. The deletion test on the presentational shell says deleting the panel markup would not remove the domain calculations; those responsibilities can be concentrated behind a dashboard snapshot interface.

Deepening opportunity: Create one dashboard snapshot adapter that returns named operational facts, then keep each panel as a focused rendering module. Move date and aggregation rules behind the snapshot seam.

Benefits: Better locality when HR metrics change; panel tests can use a small snapshot; the data adapter can be reused by status strips without importing dashboard layout knowledge.

4. CAP creation page is both a form engine and a map editor

Files: src/app/(admin)/cap/admin/new/page.tsx (544 lines), src/components/cap/composer/cap-composer.tsx, src/components/cap/composer/map-section.tsx, src/components/cap/alert-map-preview.tsx.

Problem: The route owns primitive form state, area collection editing, geometry conversion, validation, submission, and page composition. The interface of the route is effectively every field and map interaction. Geometry is a distinct domain calculation with a useful internal seam, but it is currently coupled to page state.

Deepening opportunity: Put CAP draft construction and geometry normalization behind a composer interface. Let the route compose focused sections: identity, timing, affected areas, severity, review, and submission.

Benefits: Geometry tests become local; CAP lifecycle rules stay aligned with ADR-0007; the route becomes a page composition module with high locality.

5. Setup and user management modules are orchestration-heavy

Files: src/components/hr/setup/staff-setup.tsx (549), src/components/users/manage-user-dialog.tsx (463), src/components/users/users-manager.tsx (282), src/components/hr/setup/shift-types-manager.tsx (461), src/components/roles/workflow-panel.tsx (314).

Problem: These modules combine table/query state, dialogs, mutation sequencing, policy rules, and feedback rendering. “Manage user” and “staff setup” are not single concepts at the implementation level: they are coordination shells around several distinct operations.

Deepening opportunity: Keep thin route-facing orchestration modules and give each operation a focused interface: employment lifecycle, role assignment, activation, shift catalogue, department tree, and policy configuration. Use one mutation adapter per operation rather than one dialog knowing every mutation.

Benefits: More locality around authorization-sensitive changes; operation-level tests exercise the real seams; future platform-wide reuse follows ADR-0009 without importing UI state.

6. Calendar and roster views repeat interaction/state patterns

Files: src/components/calendar/event-calendar-views.tsx (532), src/components/calendar/event-calendar.tsx (265), src/components/hr/roster/duty-roster.tsx (510), src/components/hr/shift/shift-exchange-editor.tsx (510), src/components/hr/status/daily-status-editor.tsx (500).

Problem: Calendar/roster modules contain both domain-specific scheduling rules and generic navigation, selection, dialog, and pending-state mechanics. The shared-looking behaviour has not yet become a real seam because the adapters are not clearly separated from the domain rules.

Deepening opportunity: First isolate a schedule snapshot and edit-command interface. Keep calendar rendering, roster assignment, exchange eligibility, and daily status rules as separate adapters over that interface. Do not extract generic UI primitives until two concrete adapters share a real contract.

Benefits: This respects “one adapter is hypothetical, two adapters is real”; it creates leverage only where calendar and roster actually vary; tests can target schedule invariants through the seam.

7. wxproducts schema files have unclear one-file purposes

Files: src/db/wxproducts/schema/bufr.ts and bufr.schema.ts (3,050 lines each), metarSpeci.ts (873), metar-speci.schema.ts (835), taf.ts (676), taf.schema.ts (648), plus model/type companions.

Problem: The schema area contains parallel filenames and large hand-authored type/schema definitions. A maintainer must inspect imports to know whether a file is a runtime validator, TypeScript model, example, or database adapter. The interface of the schema cluster is therefore hard to discover even where each individual export is valid.

Deepening opportunity: Establish one clear purpose per file family—runtime validation, domain types, database model, and examples—and make the public barrel the only cross-family interface. This may be documentation and naming first; merging files could reduce locality if it creates giant modules.

Benefits: Better AI navigability and locality; fewer accidental imports across representation layers; schema tests can state which seam they exercise.

How to use this report

The strongest first seam is forecast authoring. The next step is to choose one candidate and inspect its constraints, dependencies, and surviving tests before designing an interface. This report intentionally does not prescribe an interface yet.
